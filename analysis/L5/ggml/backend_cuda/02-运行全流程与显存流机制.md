## 2.1 初始化流程：从进程启动到可用的 CUDA 后端

### 阶段 A：设备探测 —— `ggml_cuda_init()`（`:221`）★ 只跑一次

```cpp
static ggml_cuda_device_info ggml_cuda_init() {
    cudaGetDeviceCount(&info.physical_device_count);          // :224  物理 GPU 数
    info.device_count = info.physical_device_count;           // :235  默认 1:1

    const char * devices_env = getenv("GGML_CUDA_DEVICES");   // :237  ★ 虚拟设备
    if (devices_env != nullptr && ...) info.device_count = atoi(devices_env);
    // → 用 1 张 GPU 模拟 N 张（多卡调度代码的测试手段）
```

**关键机制 1：虚拟设备映射（`:250`）**
```cpp
for (int id = 0; id < info.device_count; ++id) {
    info.devices[id].physical_device = id % info.physical_device_count;   // 轮询绑定
    info.devices[id].virtual_index  = physical_share_count[...]++;
}
```
`device` 是**逻辑号**，任何要碰真 GPU 的地方都得先过 `ggml_cuda_get_physical_device()`（`:113`）转换。**这是所有多卡代码的第一道坑。**

**关键机制 2：逐设备属性填充（`:262` 起）**
```cpp
cuDeviceGetAttribute(&device_vmm, CU_DEVICE_ATTRIBUTE_VIRTUAL_MEMORY_MANAGEMENT_SUPPORTED, ...);  // :268
if (device_vmm) cuMemGetAllocationGranularity(&...vmm_granularity, ..., CU_MEM_ALLOC_GRANULARITY_RECOMMENDED);  // :276
info.devices[id].vmm        = !!device_vmm;               // :281  ← 决定用哪种显存池
info.devices[id].nsm        = prop.multiProcessorCount;   // :311
info.devices[id].smpb       = prop.sharedMemPerBlock;     // :312
info.devices[id].smpbo      = prop.sharedMemPerBlockOptin;// :349  ← >48KB 要用的
info.devices[id].warp_size  = prop.warpSize;              // :313  32 或 64
cudaDeviceGetAttribute(&supports_coop_launch, cudaDevAttrCooperativeLaunch, ...);  // :318
info.devices[id].cc = 100*prop.major + 10*prop.minor;     // :349  ← NVIDIA 编码 cc=8.0→80
```
> `cc` 是 ggml 自定义编码：NVIDIA `major*100+minor*10`，AMD/MUSA 各自加 `GGML_CUDA_CC_OFFSET_*`。**比较 cc 必须用 `GGML_CUDA_CC_*` 宏**。

**关键机制 3：`default_tensor_split` 累积（`:305-405`）**
```cpp

...
info.default_tensor_split[id] /= total_vram;   // :405  归一化成 0~1
```
多卡 tensor split 的默认权重（按显存比例），用户 `-ts 0.7,0.3` 覆盖的正是它。

**关键机制 4：P2P 使能（`:411`）**
```cpp

    for each pair: cudaDeviceCanAccessPeer → cudaDeviceEnablePeerAccess(id_other, 0);
```
**默认关闭**——peer access 在某些主板/驱动上会掉性能。

### 阶段 B：单例惰性 —— `ggml_cuda_info()`（`:419`）


**全模块最热门调用点**：每个算子的 `should_use_*` 都读 `ggml_cuda_info().devices[ctx.device].cc`。首次调用触发一堆 CUDA 调用，之后纯读内存。

### 阶段 C：后端实例创建 —— `ggml_backend_cuda_init(int device)`（`:5842`）


## 2.2 前向执行全链路（核心）

### 入口：`ggml_backend_cuda_graph_compute()`（`:4425`）

```cpp
static enum ggml_status ggml_backend_cuda_graph_compute(ggml_backend_t backend, ggml_cgraph * cgraph) {
    ggml_cuda_set_device(cuda_ctx->device);                        // :4428 切物理设备
    graph_key = ggml_cuda_graph_get_key(cgraph);                   // :4434 图的身份
    ggml_cuda_graph * graph = cuda_ctx->cuda_graph(graph_key);     // :4438
    if (graph->is_enabled()) {
        const bool graph_compatible = ggml_cuda_graph_check_compability(cgraph);  // :4440
        if (graph_compatible) {
            const bool properties_changed = ggml_cuda_graph_update_required(cuda_ctx, cgraph);
            // ── 热身状态机（:4446-4470）──
            if (!graph->warmup_complete) {
                if (!properties_changed) { graph->warmup_complete = true; use_cuda_graph = true; ... }
            } else {
                if (properties_changed) graph->warmup_complete = false;   // 属性变了→重置热身
                else { use_cuda_graph = true; cuda_graph_update_required = graph->instance == nullptr; }
            }
        }
    }
    if (use_cuda_graph && cuda_graph_update_required) {
        cudaStreamBeginCapture(cuda_ctx->stream(), cudaStreamCaptureModeRelaxed);   // :4474 开始录制
    }
    ggml_cuda_graph_evaluate_and_capture(cuda_ctx, cgraph, use_cuda_graph, cuda_graph_update_required, graph_key);
    return GGML_STATUS_SUCCESS;
}
```

**关键点**：
1. **`graph_compute` 结尾没有同步**！只把 kernel 排进流就返回。同步在**别处**（见 2.4）。
2. **CUDA Graph 热身状态机**：至少 **2 次属性不变**才启用图；一旦 tensor 指针/形状变了（`properties_changed`），重置热身重新学。防止录到失效地址。
3. `cudaStreamCaptureModeRelaxed` —— 捕获期间允许其他线程用 CUDA API，避免死锁。

### 主循环：`ggml_cuda_graph_evaluate_and_capture()`（`:4190`）

```cpp
while (!graph_evaluated_or_captured) {
    if (!use_cuda_graph || cuda_graph_update_required) {       // :4222 要么没图，要么在录制
        // ① 多流并发准备（:4226-4285）：重排节点顺序，把同一分支的节点聚拢
        if (should_launch_concurrent_events) { ...restore original order... }
        // ② 逐节点执行
        for (int i = 0; i < cgraph->n_nodes; i++) {
            ggml_tensor * node = cgraph->nodes[i];
            // ③ 流切换（:4290-4305）
            if (node == concurrent_event->join_node) { ...join 回主流... }
            else { cuda_ctx->curr_stream_no = concurrent_event->stream_mapping[node]; }  // ★ 切流！
            ...
            ggml_cuda_compute_forward(*cuda_ctx, node);        // ★ 逐 op 分发
        }
    }
    // ④ 录制结束 / 重放
    ...
}
```

**这是 ggml-cuda 的"调度心脏"**，三个职责：
1. **节点级遍历**：`cgraph->nodes[]` 是**拓扑序**数组，按序 launch 即满足依赖（图已拓扑排序）；
2. **多流切换**：改 `cuda_ctx->curr_stream_no` 让不同节点落不同流——**ggml 实现算子级并行的唯一手段**；
3. **图录制/重放**：`use_cuda_graph` 时，循环体第一次执行 = 录制，之后 `cudaGraphLaunch` 重放。

### 分发：`ggml_cuda_compute_forward()`（`:2068`）

```cpp
static bool ggml_cuda_compute_forward(ggml_backend_cuda_context & ctx, struct ggml_tensor * dst) {
    switch (dst->op) {
        case GGML_OP_MUL_MAT:  ggml_cuda_mul_mat(ctx, dst->src[0], dst->src[1], dst);  break;   // :2260
        ...
        default: return false;      // :2424  不支持的 op
    }
    cudaError_t err = cudaGetLastError();       // :2427  ★ 唯一统一的错误检查点
    if (err != cudaSuccess) { GGML_LOG_ERROR(...); CUDA_CHECK(err); }
    return true;
}
```

**注意 `cudaGetLastError()` 是异步的**——只检查"kernel 启动有没有报错"，**不检查 kernel 执行有没有崩**。执行期错误（越界、非法访存）要等同步时才暴露。**这是调试 CUDA 算子最反直觉的一点**（见 2.6）。


## 2.3 显存调度机制

### 三条独立的显存通道

| 通道 | 分配者 | 生命周期 | 用途 |
|---|---|---|---|
| **权重/张量 buffer** | `ggml_backend_cuda_buffer_type_alloc_buffer`（`:881`）→ `ggml_cuda_device_malloc` | 模型级，全程 | 模型权重、KV cache |
| **计算 buffer（compute）** | ggml-alloc（`ggml-alloc.c`）+ CUDA buft | 单次 graph 执行 | 中间激活 |
| **算子临时显存** | `ctx.pool()` → `ggml_cuda_pool_alloc<T>` | 单算子调用 | workspace、scratch |

前两者走 `cudaMalloc`，第三者走池。别混。

### 池的选择与复用（`new_pool_for_device`）

```cpp
if (ggml_cuda_info().devices[device].vmm)  → new ggml_cuda_pool_vmm(device)   // :536
else                                        → new ggml_cuda_pool_leg(device)   // :419
```

**VMM 池分配流程（现代路径）**：
```
alloc(size, &actual_size):
  1. size 向上取整到 granularity（通常 2MB）
  2. 若 pool_used + size > pool_size → 扩容：
       cuMemAddressReserve 预留虚拟地址（一次 32GB 上限）
       cuMemCreate + cuMemMap 映射物理页
  3. 返回 pool_addr + pool_used，pool_used += size
  4. actual_size = 取整后的 size   ← ★ 所以 actual_size ≥ 申请值
```
**无碎片**：地址单调递增，物理页按需映射。`free` 只回退 `pool_used`（LIFO，因算子临时显存是栈式生命周期）。

**LEG 池分配流程（回退路径）**：
```
alloc: 在 buffer_pool[256] 里找 size 最接近且 ≥ 需求的空闲块（best-fit）
       命中 → 复用；未命中 → cudaMalloc 新块塞进空槽
free:  标记槽位为空（不 cudaFree，留着复用）
```
**碎片风险**：反复申请大小差异大的块会把 256 槽位耗尽。

### 量化模型显存优化逻辑

- **权重以量化块存储**（如 `block_q4_0` = 18 字节/32 权重），**永不反量化到显存**——反量化在 kernel 内即时做；
- Q4_K_M 的 7B 模型权重仅 ~4GB，F16 需 ~14GB；
- **计算中间结果仍是 F32/F16**——量化只省权重，不省激活；
- MMVQ/MMQ 从量化块**直接算点积**（`vecdotq.cuh`），跳过显式反量化。

## 2.4 并行与同步机制

### 多流架构（8 条流/设备）

```cpp
cudaStream_t streams[GGML_CUDA_MAX_DEVICES][GGML_CUDA_MAX_STREAMS];  // 16 × 8, common.cuh:1460
int curr_stream_no = 0;                                              // 当前活跃流号
```

### 算子级并行：concurrent_events（`ggml-cuda.cu:4770` 填充）

**ggml-cuda 唯一的"自动并行"机制**，用于 Attention 里 Q/K/V 三路互不依赖的计算：

```
检测到 fork-join 结构（:4770-4810）：
  fork_node（如 attn_norm）
    ├─ branch 0: QMul → QNorm → QRope
    ├─ branch 1: KMul → KNorm → KRope
    └─ branch 2: VMul → VNorm
  join_node（如 attn）

建立 concurrent_event：
  fork_event  ← 主流上 record
  stream_mapping[node] = 分支流号（1/2/3）
  join_events[i] ← 各分支流 record
```

**运行时（`ggml_cuda_graph_evaluate_and_capture`）**：
```cpp
// ① 到达 fork 点
cudaEventRecord(concurrent_event->fork_event, main_stream);          // :4211
for (i=1..n) cudaStreamWaitEvent(cuda_ctx->stream(dev, i), fork_event);  // :4215 分支流等 fork

// ② 遍历分支节点
cuda_ctx->curr_stream_no = concurrent_event->stream_mapping[node];   // :4305  ★ 切流

// ③ 到达 join 点
for (i=1..n) { cudaEventRecord(join_events[i-1], stream(dev,i));     // :4297
               cudaStreamWaitEvent(cuda_ctx->stream(), join_events[i-1]); }  // :4299 主流等分支
cuda_ctx->curr_stream_no = 0;                                        // 回主流
```

**要点**：
1. 这是**图级静态分析**出的并行度，不是动态调度；
2. `GGML_ASSERT(cuda_ctx->curr_stream_no == 0)`（:4210）——fork 时**必须**在主流；
3. **自定义算子若处在 fork 区域内，会自动跑在分支流上**——所以必须用 `ctx.stream()` 拿流，写死流号会破坏并行。

### 跨后端拷贝：copy_event（`:2537`）

```cpp
// 设备→设备（不同后端，如 CUDA0 → CUDA1）
cudaMemcpyPeerAsync(dst->data, dst_physical, src->data, src_physical, ..., cuda_ctx_src->stream());  // :2526
if (!cuda_ctx_src->copy_event)
    cudaEventCreateWithFlags(&cuda_ctx_src->copy_event, cudaEventDisableTiming);   // :2535
cudaEventRecord(cuda_ctx_src->copy_event, cuda_ctx_src->stream());                 // :2537
cudaStreamWaitEvent(cuda_ctx_dst->stream(), cuda_ctx_src->copy_event, 0);          // :2540
```
**跨卡拷贝同步范式**：源流 record → 目标流 wait。`cudaEventDisableTiming` 更轻量。

### 同步点清单（★ 调试必备）

| 位置 | 代码 | 语义 |
|---|---|---|
| `ggml_backend_cuda_synchronize`（`:2548`） | `cudaStreamSynchronize(ctx.stream())` | **后端级同步**，graph 执行后由上层调用 |
| H2D 上传（`:790`） | `cudaMemcpyAsync(..., cudaStreamPerThread)` + `cudaStreamSynchronize(cudaStreamPerThread)` | **同步**上传（per-thread 流） |
| D2H 下载（`:798`） | 同上，方向相反 | **同步**下载 |
| 跨卡拷贝（`:2537/2540`） | event record/wait | 流间依赖 |
| 图内 kernel 间 | 无显式同步 | 同流串行保证 |
| **`graph_compute` 返回** | **无同步** | kernel 仍在飞 |

**关键洞察**：
- buffer 的 set/get_tensor 用 `cudaStreamPerThread` 且同步——与 `ctx.stream()` 完全隔离；
- compute 全异步，只在 `synchronize()` 收口；
- 测单算子耗时，**必须在前后各插 event + synchronize**。

### CUDA Graph 复用（性能关键）

`ggml_cuda_graph`（`common.cuh:1271`）把整个 decode step 的 N 个 kernel 录制为一张图：
- **消除逐 kernel 的 CPU 启动开销**（每个 ~5-10μs，100 层模型就是 ms 级）；
- 小 batch（decode）提速 10~30%；
- **LRU 淘汰**（`:1477`）：每 5s 扫描，10s 未用则销毁，防止 prefill/decode 两种图形态撑爆显存。

## 2.5 量化算子特殊机制（预览，模块三展开）

```
权重：block_q4_0 { half d; uint8_t qs[16]; }   // 32 权重压成 18 字节
        │
        ▼  不反量化到显存！
kernel 内即时计算：
  MMVQ (mmvq.cu)：src1 先量化成 q8_1（block_q8_1），
                  然后 vec_dot_q4_0_q8_1(q4_block, q8_block)   ← vecdotq.cuh
                  —— 纯整数点积 + 两个 scale 相乘，无浮点反量化
  MMQ  (mmq.cu) ：mma PTX 指令直接吃量化 tile（mmq-load-tiles.cuh 搬块进 smem）
```
**加速本质**：把"反量化→FP 点积"融合成"整数点积 + 标量缩放"，减少 4~8 倍访存 + 消除反量化指令。

## 2.6 学习重点 + 易错点

### 必须记住的 6 条

| # | 结论 | 依据 |
|---|---|---|
| 1 | 初始化全部惰性，`ggml_cuda_init()` 只跑一次（magic static） | `:419` |
| 2 | `device` 是逻辑号，碰真 GPU 前必须 `ggml_cuda_get_physical_device()` | `:113` |
| 3 | `graph_compute` **异步**，返回 ≠ 算完；同步在 `synchronize()` | `:4425` / `:2548` |
| 4 | 算子级并行靠 **8 条流 + concurrent_events**（fork/join event） | `:4770` / `:4211` |
| 5 | 计算全异步用 `ctx.stream()`；buffer 上传下载用 `cudaStreamPerThread` 且同步 | `:790` vs `:1548` |
| 6 | CUDA Graph 需 **2 次属性稳定** 才启用，属性变则重置热身 | `:4446` |

### 易错点（源码级）

| 易错 | 现象 | 正确做法 |
|---|---|---|
| 以为 `graph_compute` 返回就算完 | 计时偏小、读到脏数据 | 测速在 `synchronize()` 后收口，或用 event |
| 用 `cudaGetLastError()` 判 kernel 是否崩 | 越界/非法访存检查不到 | 同步后检查，或 `compute-sanitizer` |
| 把 `curr_stream_no` 写死为 0 | 破坏 fork 并行 | 用 `ctx.stream()` |
| 忘了 `ggml_cuda_set_device()` | 多卡下 kernel 排到错的设备 | 每个会碰 GPU 的入口先 set_device |
| 直接 `cudaMalloc` 要临时显存 | 每次调用都真分配，极慢 | 用 `ggml_cuda_pool_alloc<T>` |
| 认为 `actual_size == size` | 量化算子地址错位 | 用 `actual_size` 算 stride |

## 2.8 补充：多卡通信、事件与 CUDA Graph 的边界（审计新增）

### NCCL / internal allreduce / butterfly 三层通信

CUDA backend 通过动态 proc address 暴露通信接口（`ggml-cuda.cu:5756-5776`）：

```text
ggml_backend_comm_init
    ↓
ggml_backend_cuda_comm_init_*（:1158 起）
    ├─ NCCL：ggml_backend_cuda_comm_allreduce_nccl（:1001）
    ├─ internal：ggml_backend_cuda_comm_allreduce_internal（:1077）
    └─ none/butterfly fallback（:1158）
```

`ggml_backend_cuda_comm_context`（`:969`）保存：

```text
backends[]
try_allreduce 函数指针
NCCL communicators（若启用）
internal allreduce pipeline（若启用）
```

NCCL 路径使用 `ncclGroupStart/End`，把多个设备的 allreduce 批量提交到各自 `ctx.stream()`；大 tensor 还会使用 BF16 临时缓冲，不能把它误认为普通 peer copy。

`allreduce.cu:25` 的 `ggml_cuda_ar_allreduce` 是内部通信算法入口。**多卡有三种不同层次的机制：**

```text
P2P：设备之间能否直接访问显存
copy_event：一次跨设备 copy 的依赖
allreduce：多个设备对同一 tensor 做求和
```

### CUDA Graph 的不兼容边界

以下行为会让 graph capture 失效或必须走 graph 外路径：

```text
MUL_MAT_ID 排序 fallback
  └─ Device→Host 拷贝 ids + cudaStreamSynchronize
动态改变 tensor pointer/shape/stride
不兼容的 host API 或同步点
```

所以 `ggml_cuda_mul_mat_id_needs_sync`（`:1882`）不仅是性能 heuristic，也是 CUDA Graph 安全判断。修改 MoE/通信路径时必须检查：

```text
是否发生 D2H
是否调用 cudaStreamSynchronize
是否使用固定 workspace
是否能在 capture 期间调用
```

### backend event 与 stream synchronize 的区别

```text
backend event：跨 backend / 跨 stream 的依赖对象
cudaStreamSynchronize：等待一个 stream 的全部工作
cudaEventSynchronize：等待一个 event 前的工作
```

实现位置：

```text
ggml_backend_cuda_event_record       ggml-cuda.cu:4484
ggml_backend_cuda_event_wait         :4490
ggml_backend_cuda_device_event_synchronize :5654
```
