# 模块一：目录结构 + 核心数据结构逐层拆

## 0. ggml-cuda 在 ggml 五层架构里的坐标

**核心认知：ggml-cuda 不自己管理计算图，它只是 `ggml-backend` 抽象接口的一个实现。**

```
┌─ L0  include/ggml.h ──────────────────────────────────────────────┐
│    ggml_tensor / ggml_cgraph / enum ggml_op / ggml_type          │
│    纯数据结构 + 图构建 API，不含任何后端逻辑                        │
└──────────────────────────────────────────────────────────────────┘
┌─ L1  src/ggml-backend-impl.h + include/ggml-backend.h ────────────┐
│    5 个 C 结构体虚表（接口契约）：                                  │
│    ggml_backend_buffer_type_i  :17   ← 一种"显存类型"(如 CUDA0)    │
│    ggml_backend_buffer_i       :46   ← 一块显存的行为(set/get/cpy) │
│    ggml_backend_i             :121   ← 一次会话(stream/graph_compute)│
│    ggml_backend_device_i      :176   ← 一张设备(supports_op/alloc) │
│    ggml_backend_reg_i         :230   ← 注册中心(枚举设备)           │
└──────────────────────────────────────────────────────────────────┘
┌─ L2  src/ggml-backend.cpp + ggml-backend-reg.cpp ─────────────────┐
│    调度器 ggml_backend_sched：用 supports_op 决定每个 op 落哪个后端 │
└──────────────────────────────────────────────────────────────────┘
┌─ L3  src/ggml-cuda/*.cu  ← 本模块，实现 L1 的 5 张虚表            │
│    ggml-cuda.cu 负责"后端骨架"，各算子 .cu 负责"算得快"            │
└──────────────────────────────────────────────────────────────────┘
┌─ L4  src/ggml-cuda/*.cuh 里的 __device__ 核函数                    │
└──────────────────────────────────────────────────────────────────┘
```

**你写的自定义算子，不改 L0/L1/L2。只需三步：**
1. 在 L3 加一个 `ggml_cuda_op_xxx()` 入口；
2. 在 `ggml-cuda.cu` 的 `ggml_cuda_compute_forward()` switch 里挂上它；
3. 在 `ggml_backend_cuda_device_supports_op()` 里声明"我能算这个 op"。

### 1.3 算子层（每个 op 一对 `.cu` + `.cuh`，约 80 组）★ 最重要的工程约定

```
xxx.cuh  →  声明 + 设备端 functor/模板 + 内联小工具   （被 #include）
xxx.cu   →  模板实例化 + 主机端启动逻辑 + ggml_cuda_op_xxx() 入口（编译单元）
```

**`unary.cu` 是这条约定的最佳标本（721 行）——三段式结构：**

```cpp
// ① 设备端 functor —— 只描述"每个元素做什么"
static __device__ __forceinline__ float op_gelu(float x) {
    return ggml_cuda_op_gelu_single(x);        // unary.cu:21
}
// ② 通用启动器模板 —— 只描述"怎么铺线程"
template <typename T, float (*op)(float)> ...
// ③ 主机端入口 —— 只描述"读哪些指针、怎么算元素数"
void ggml_cuda_op_unary(ggml_backend_cuda_context & ctx, ggml_tensor * dst) {  // unary.cu:138
    const ggml_tensor * src = dst->src[0];
    cudaStream_t stream = ctx.stream();
    const int k = ggml_nelements(src);
    unary_cuda<op_silu>((const float *)src->data, (float *)dst->data, k, stream);
}
```

**记住这个分工**：`op_xxx`（算什么）→ `xxx_cuda<>`（怎么并行）→ `ggml_cuda_op_xxx`（取指针、算规模、选 stream）。
写新算子时，就是往这三个坑里各填一个函数。

### 1.4 模板实例层 `template-instances/`（121 文件！）★ 新手避坑

**里面每个文件平均只有 7 行**，例如：

```cpp
// template-instances/mmq-instance-iq1_s.cu（5 行）
#include "../mmq.cuh"
template void ggml_cuda_mul_mat_q_switch_type<GGML_TYPE_IQ1_S>(...);
```

**设计原因**：CUDA 模板必须编译期实例化。若所有量化类型都在 `mmq.cu` 里 instantiate，单编译单元会爆内存且编译奇慢。拆成 121 个独立编译单元后：
- 可**并行编译**（多核加速）；
- 可用 `GGML_CUDA_FA_ALL_QUANTS` 等开关**裁剪**不用的组合；
- 改一个量化类型只重编一个小文件。

`fattn-mma-f16-instance-ncols1_*-ncols2_*.cu` 同理——FlashAttention 的 tile 形状组合爆炸，必须拆。

> **新手避坑**：第一次读源码时**直接跳过整个 `template-instances/`**。它不是逻辑，是编译工程技巧。改量化类型时再回来。

### 1.5 厂商抽象层 `vendors/`（3 文件）

```c
vendors/cuda.h   // #define cudaMalloc ... → 真实 CUDA API
vendors/hip.h    // 同一套源码 → 映射到 HIP API
vendors/musa.h   // 同一套源码 → 映射到 MUSA API
```

**这是 ggml-cuda 能"一套源码跑三家 GPU"的机制**：源码里只写 `cudaMalloc`、`cudaStream_t`，编译时通过 `-include vendors/hip.h` 让预处理器替换符号。

## 2. 核心数据结构逐层拆（按生命周期顺序）

### 2.1 进程级：`ggml_cuda_device_info`（`common.cuh:1177`）

由 `ggml_cuda_init()`（`ggml-cuda.cu:221`）在**首次调用时**填充，全局单例（`ggml_cuda_info()`）。

```cpp
struct ggml_cuda_device_info {
    int device_count;           // 暴露给 ggml 的（虚拟）设备数
    int physical_device_count;  // 物理 GPU 数（虚拟化时二者不等）
    struct cuda_device_info {
        int     cc;                          // compute capability，所有分支的判据
        int     nsm;                         // SM 数 → 决定 grid 上限
        size_t  smpb;                        // 每 block 最大 shared mem
        size_t  smpbo;                       // opt-in 后上限（>48KB 需 cudaFuncSetAttribute）
        bool    integrated;                  // 集显（UMA）
        bool    vmm;                         // 支持虚拟显存 → 决定用 vmm 池
        size_t  vmm_granularity;             // VMM 映射粒度（通常 2MB）
        size_t  total_vram;
        int     warp_size;                   // 32(CUDA) / 64(CDNA)，跨厂商关键
        bool    supports_cooperative_launch; // 协作组启动
        int     physical_device;             // 虚拟→物理映射
        int     physical_share_count;
        int     virtual_index;
    };
    cuda_device_info devices[GGML_CUDA_MAX_DEVICES];   // 16
    std::array<float, GGML_CUDA_MAX_DEVICES> default_tensor_split;
};
```

**`cc` 和 `warp_size` 是全场最重要的两个字段**：
- `cc` 决定 kernel 分支——`ggml_cuda_should_use_mmq()`、`should_use_mmvf()`、`should_use_mmf()` 第一参数都是 `cc`；
- `warp_size` 在 AMD CDNA 上是 64 而非 32，所有 `__shfl_down_sync` 归约都依赖它。

> **实战**：自定义算子若要按架构走不同实现，**判据必须读 `ggml_cuda_info().devices[ctx.device].cc`**，不能用 `__CUDA_ARCH__`（host 代码里无效）。

### 2.2 后端会话级：`ggml_backend_cuda_context`（`common.cuh:1455`）★ 全模块核心

**一个后端实例一个 context**，是所有 `ggml_cuda_op_*()` 函数的第一个参数。持有 4 类惰性资源：

```cpp
struct ggml_backend_cuda_context {
    int device;
    std::string name;
    cudaEvent_t copy_event = nullptr;   // 跨流拷贝同步用

    // ① 流：8 条 × 16 设备，惰性创建
    cudaStream_t streams[GGML_CUDA_MAX_DEVICES][GGML_CUDA_MAX_STREAMS];
    int curr_stream_no = 0;             // ← 当前活跃流号

    // ② cuBLAS 句柄 + 工作区
    cublasHandle_t cublas_handles[GGML_CUDA_MAX_DEVICES][GGML_CUDA_MAX_STREAMS];
    void *         cublas_workspaces[GGML_CUDA_MAX_DEVICES][GGML_CUDA_MAX_STREAMS];
    size_t         cublas_workspace_sizes[GGML_CUDA_MAX_DEVICES]; // Hopper 32MB, 其他 4MB

    // ③ 显存池：16 设备 × 8 流，惰性创建
    std::unique_ptr<ggml_cuda_pool> pools[GGML_CUDA_MAX_DEVICES][GGML_CUDA_MAX_STREAMS];

    // ④ CUDA Graph（USE_CUDA_GRAPH 时）
    std::unordered_map<const void *, std::unique_ptr<ggml_cuda_graph>> cuda_graphs;
};
```

**四个惰性访问器（理解它们 = 理解 ggml-cuda 资源哲学）：**

```cpp
cudaStream_t stream() {                       // common.cuh:1548
    if (streams[device][curr_stream_no] == nullptr) {
        cudaStreamCreateWithFlags(&streams[device][curr_stream_no],
                                  cudaStreamNonBlocking);   // ← 非阻塞流，关键
    }
    return streams[device][curr_stream_no];
}
cublasHandle_t cublas_handle() { ... }        // 首次调用才 cublasCreate + setWorkspace
ggml_cuda_pool & pool() { ... }               // 首次调用才 new_pool_for_device()
```

**要点**：
1. **`cudaStreamNonBlocking`** —— 不与非默认流隐式同步，是算子并发的前提；
2. **"用到才建"** —— 不推理的进程不会分配 cuBLAS 工作区，省显存；
3. `curr_stream_no` 是**可变状态**，`ctx.stream()` 取决于当前被设成几号流。

> **实战**：自定义算子里**永远用 `ctx.stream()`**，绝不 `cudaStreamSynchronize(0)` 或建自己的流。用默认流会打断流水线，性能直接崩。

### 2.3 显存池层：抽象 + 两实现

**抽象基类 `ggml_cuda_pool`（`common.cuh:1207`）：**
```cpp
struct ggml_cuda_pool {
    virtual ~ggml_cuda_pool() = default;
    virtual void * alloc(size_t size, size_t * actual_size) = 0;  // 返回真实尺寸
    virtual void free(void * ptr, size_t size) = 0;
};
```

**RAII 包装 `ggml_cuda_pool_alloc<T>`（`common.cuh:1215`）★ 极重要：**
```cpp
template<typename T> struct ggml_cuda_pool_alloc {
    ggml_cuda_pool * pool;  T * ptr;  size_t actual_size;
    ~ggml_cuda_pool_alloc() { if (ptr) pool->free(ptr, actual_size); }  // 出作用域自动归还
    T * alloc(size_t size) { ptr = (T*)pool->alloc(size*sizeof(T), &actual_size); ... }
    // 拷贝/移动全部 = delete  ← 防双重释放
};
```
用法范式（几乎每个算子开头都有）：
```cpp
ggml_cuda_pool_alloc<float> tmp(ctx.pool(), n);   // 借
...  kernel 用 tmp.get() ...
// 函数返回时自动还，无需手写 cudaFree
```
> **易错点**：`actual_size` 可能**大于**申请 size（池返回整块）。传给别的 kernel 做 stride 计算时**必须用 `actual_size`**。这是量化算子错位的常见根因。

**实现 A：`ggml_cuda_pool_leg`（`ggml-cuda.cu:419`）—— 固定槽位池**
```cpp
struct ggml_cuda_pool_leg : public ggml_cuda_pool {
    static const int MAX_BUFFERS = 256;      // 硬上限
    struct ggml_cuda_buffer { void * ptr; size_t size; };
    ggml_cuda_buffer buffer_pool[MAX_BUFFERS];
    size_t pool_size = 0;
};
```
策略：256 槽位做**最佳适配（best-fit）**，命中复用，否则 `cudaMalloc`。简单，碎片化后可能退化。

**实现 B：`ggml_cuda_pool_vmm`（`ggml-cuda.cu:536`）—— 虚拟地址池 ★ 现代路径**
```cpp
struct ggml_cuda_pool_vmm : public ggml_cuda_pool {
    static const size_t CUDA_POOL_VMM_MAX_SIZE = 1ull << 35;   // 32 GB 虚拟地址
    CUdeviceptr pool_addr = 0;   // 一次 cuMemAddressReserve 保留整段虚拟地址
    size_t pool_used = 0, pool_size = 0, granularity;
};
```
策略：**一次性预留 32GB 虚拟地址**，按 `granularity`（通常 2MB）`cuMemMap` 物理页。无碎片、可超额预留。
触发条件：`devices[i].vmm == true`。选择逻辑在 `new_pool_for_device()`。

> **实战**：想省显存/降碎片，改的是**池策略**而非算子。注意 VMM 池是进程级共享地址空间，自定义算子持裸指针跨 kernel 生命周期时，必须确保 `pool_alloc` 生命周期覆盖所有使用点。

### 2.5 执行期辅助结构

**`ggml_cuda_kernel_launch_params`（`common.cuh:1594`）**

配合 PDL（`ggml_cuda_pdl_config`, `:1610`，Hopper+ 的 Programmatic Dependent Launch）可让连续 kernel 重叠启动。

**`ggml_cuda_graph`（`common.cuh:1271`）+ context 里的 `cuda_graphs` map**
- key 是 **graph 首个节点的指针**，支持一个 context 挂多张图；

- 作用：把整个 decode step 的 kernel 序列录制成 CUDA Graph，**消除逐 kernel 启动开销**（小 batch 提速 10~30%）。

**`ggml_tensor_extra_gpu`（`common.cuh:1265`）**

## 3. 依赖链路：从 ggml 图到 CUDA kernel 的完整调用链 ★ 主干，背下来

```
用户: ggml_mul_mat(ctx, w, x)                    ← 只建图节点，不计算
        │
        ▼
ggml_backend_sched_graph_compute(sched, graph)   ← ggml-backend.cpp
        │  对每个节点问：谁支持我？
        ▼
ggml_backend_cuda_device_supports_op(dev, op)    ← ggml-cuda.cu:5136
        │  ├─ :5141 检查所有 src 是否都在本 device（多卡正确性）
        │  └─ switch(op->op) 逐 op 声明支持性 + 类型/连续性约束
        ▼  （sched 决定：这个 op 归 CUDA0 算）
ggml_backend_cuda_graph_compute(backend, cgraph) ← ggml-cuda.cu（backend_i 虚表）
        │  ├─ 尝试复用/录制 CUDA Graph
        │  └─ 逐节点 → ggml_cuda_compute_forward(ctx, node)
        ▼
ggml_cuda_compute_forward(ggml_backend_cuda_context&, ggml_tensor*) ← :2068
        │  switch (dst->op)  ← 全模块总分发，~150 个 case
        ▼
    case GGML_OP_MUL_MAT:  ggml_cuda_mul_mat(ctx, src0, src1, dst);   ← :2260
        ▼
ggml_cuda_mul_mat()  ← :1824  ★ 最典型的"多路分发"
        │
        ├─ hint == HADAMARD        → ggml_cuda_op_fwht()            :1827
        ├─ 类型不匹配/坏 padding   → ggml_cuda_mul_mat_cublas()     :1840
        ├─ should_use_mmvf         → ggml_cuda_mul_mat_vec_f()      :1848  (F16 GEMV)
        ├─ should_use_mmf          → ggml_cuda_mul_mat_f()          :1868  (F16 GEMM)
        ├─ should_use_mmvq         → ggml_cuda_mul_mat_vec_q()      :1870  (量化 GEMV)
        ├─ should_use_mmq          → ggml_cuda_mul_mat_q()          :1873  (量化 GEMM)
```

### 必须记住的 5 条

| # | 结论 | 依据 |
|---|---|---|
| 1 | `.cuh`=声明/设备 functor，`.cu`=实例化/主机启动/op 入口 | `unary.cu` 三段式 |

| 4 | 临时显存用 `ggml_cuda_pool_alloc<T>`，RAII 自动归还，**注意 `actual_size`** | `common.cuh:1215` |
| 5 | 架构分支判据统一读 `ggml_cuda_info().devices[i].cc` / `.warp_size` | `common.cuh:1177` |

### 新手易错点（源码级）

| 易错 | 后果 | 正确做法 |
|---|---|---|
| 直接 `#include <cuda_runtime.h>` | 破坏 HIP/MUSA 跨厂商编译 | 依赖 `vendors/*.h`，只用 `cudaXxx` 符号名 |
| 用默认流 `0` 或自建流 | 打断流水线，性能崩 | 一律 `ctx.stream()` |
| 忘记在 `supports_op` 声明 | 算子永远不被调度（静默走 CPU 或报错） | 同步改 `:5136` |
| `ggml_cuda_pool_alloc` 拷贝/移动 | 编译报错（已 `=delete`） | 按引用传递或用 `get()` |
| 改 CUDA buft 的 `get_name` | `buft_is_cuda` 失效，多卡误调度 | 别动它 |
| 一次读完 `template-instances/` | 浪费 2 天，那里没有逻辑 | 跳过，改量化类型时再看 |

## 6. 补充：Backend 注册、设备能力与 buffer 生命周期（审计新增）

前文覆盖了四类 CUDA context，但还需要把它们如何真正注册到 GGML backend registry 讲完整。

### 6.1 注册链路

```text
ggml_backend_cuda_reg()                         ggml-cuda.cu:5787
  ├─ ggml_cuda_info()                           触发设备探测
  ├─ 为每个逻辑设备创建 ggml_backend_device
  │   └─ ggml_backend_cuda_device_interface
  └─ ggml_backend_cuda_reg_interface
       ├─ get_name
       ├─ get_device_count
       ├─ get_device
       └─ get_proc_address

ggml_backend_cuda_init(device)                  :5842
  └─ ggml_backend_cuda_context
       └─ ggml_backend_cuda_interface
```

`GGML_BACKEND_DL_IMPL(ggml_backend_cuda_reg)`（`:5864`）将注册器作为动态 backend 导出。**因此新增 CUDA 算子不是“只改 CUDA 文件”就一定完成：如果新增的是 backend 能力、通信接口或 buffer 行为，还必须进入对应 interface/reg/proc-address。**

### 6.2 device interface 与 offload 策略

`ggml_backend_cuda_device_interface` 负责：

```text
get_name / get_description
memory_get_free
supports_op
supports_buft
offload_op
event_new / event_free / event_synchronize
```

`op_offload_min_batch_size` 从 `GGML_OP_OFFLOAD_MIN_BATCH` 读取（`:5795` 附近），用于小 batch 时是否值得把算子卸载到 GPU。**supports_op 表示能力，offload_op 表示策略，两者不是一回事。**

### 6.3 buffer 与 host buffer

| 对象 | 作用 | 关键位置 |
|---|---|---|
| CUDA buffer type | 按设备分配 tensor buffer | `ggml-cuda.cu:869` |
| CUDA buffer | set/get/copy/memset tensor | `:727`、`:785-851` |
| CUDA host buffer | pinned host memory，提升 H2D/D2H | `:1273` 起 |
| tensor extra GPU | 多卡 device pointer + events | `common.cuh:1265` |

Host buffer 通过注册器 proc address 暴露：

```cpp
"ggml_backend_register_host_buffer"   // ggml-cuda.cu:5768
"ggml_backend_unregister_host_buffer"
```

它与普通 `cudaMalloc` 显存不同：**pinned host buffer 仍在主机，但允许更高效的异步 DMA**。做大模型权重加载/异步拷贝时，应区分三种内存：device、pinned host、普通 pageable host。

### 6.4 动态注册的 feature 信息

`ggml_backend_cuda_get_features()`（`:5701` 起）把编译/运行能力暴露给上层，包括：

```text
ARCHS
FORCE_MMQ / FORCE_CUBLAS
NO_VMM / NO_PEER_COPY
USE_GRAPHS
FA_QUANTS
BLACKWELL_NATIVE_FP4
```

这对排查“同一二进制在不同机器表现不同”非常重要：先读取 backend features，再解释 heuristic 行为。
