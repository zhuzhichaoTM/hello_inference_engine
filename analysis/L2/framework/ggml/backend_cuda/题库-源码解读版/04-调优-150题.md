## 第一部分 · 基础题（1–45）

### 第 1 题
【题型：单选题】【难度：基础】
【题干】GGML-CUDA 运行时把显存划分为三条独立通道，下列哪一项**不属于**「算子临时显存」通道？
【选项】
A. `ctx.pool()` 经 `ggml_cuda_pool_alloc<T>` 分配的 workspace
B. MMVQ 里量化激活用的 `q8_1` 缓冲（`mmvq.cu:1421` 附近分配）
C. 模型权重 buffer（`ggml_backend_cuda_buffer_type_alloc_buffer`，`ggml-cuda.cu:881`）
D. FlashAttention 放在 `dst` 分配尾部的 F16 K/V workspace
【正确答案】C
【详细解析】
1. **核心考点**：三条通道 = ①权重/张量 buffer（模型级，`cudaMalloc`）②计算 buffer（`ggml-alloc` 管理，单次 graph 执行）③算子临时显存（`ctx.pool()`，单算子调用）。C 属于第①条，生命周期是模型级，绝不该走池。
2. **错项分析**：A、B、D 都是「单算子调用内申请、用完即还」的栈式生命周期，正是池服务的对象；B 是 MMVQ 每步都建的激活缓冲，D 是 FA 的尾部 workspace，都走池或 `dst` 尾部规划。
3. **落地补充**：判断一块显存该走哪条通道，只看**生命周期**——模型级用 `cudaMalloc` 一次性分配，单算子级用 `ggml_cuda_pool_alloc`。混用（如把权重塞进池）会因池的 LIFO 语义被误释放。

### 第 2 题
【题型：单选题】【难度：基础】
【题干】`ggml_cuda_pool_alloc<T>(ctx.pool(), n)` 中参数 `n` 的含义是？
【选项】
A. 申请的字节数
B. 申请的 **T 类型元素个数**，内部再乘 `sizeof(T)`
C. 量化块个数
D. 32bit int 的个数
【正确答案】B
【详细解析】
1. **核心考点**：`common.cuh:1215` 的 `ggml_cuda_pool_alloc<T>` 构造签名是 `(pool, size_t size)`，这里的 `size` 是**元素个数**，RAII 析构时归还。这是模块一登记的第 28 号易错点。
2. **错项分析**：A 是最常见的误解——若把字节数当元素数传，会多申请 `sizeof(T)` 倍；C、D 与接口定义无关，池只认元素个数。
3. **落地补充**：写自定义算子时统一按「我要几个 `T`」思考；若手里是字节数，必须自己先 `/ sizeof(T)` 换算，否则不是浪费显存就是越界。

### 第 3 题
【题型：多选题】【难度：基础】
【题干】下列哪些做法能避免「热路径 `cudaMalloc`」这一性能陷阱？（多选）
【选项】
A. 临时显存统一用 `ggml_cuda_pool_alloc<T>`
B. 把 workspace 需求预先算进 `dst` 分配的尾部（如 `fattn.cu:719` 的 `get_alloc_size`）
C. 每次前向里对临时缓冲 `cudaMalloc` + `cudaFree`
D. 复用 `ctx.pool()` 的 LIFO 栈式分配
【正确答案】ABD
【详细解析】
1. **核心考点**：`cudaMalloc`/`cudaFree` 是驱动层同步操作，单次可达数十~数百 μs，放进 decode 每步的热路径会累积成 ms 级开销。正确做法是池化（A、D）或把空间规划进已有分配（B）。
2. **错项分析**：C 正是被禁止的写法——每步真分配、真释放，既慢又易碎片化，是「推理卡顿且显存缓慢增长」的典型根因。
3. **落地补充**：GGML 的哲学是「零预热、按需生长」，但**生长只在首次**；稳定运行期不应有任何新的 `cudaMalloc`。用 `GGML_CUDA_DEBUG=1` 观察池命中情况即可验证。

### 第 4 题
【题型：单选题】【难度：基础】
【题干】`ggml_backend_cuda_context::new_pool_for_device`（`ggml-cuda.cu:685`）选择显存池实现的依据是？
【选项】
A. 无论设备一律建 LEG 池
B. 读 `devices[device].vmm`，支持虚拟内存管理则建 VMM 池，否则建 LEG 池
C. 依据 `cc` 计算能力号
D. 依据模型权重大小
【正确答案】B
【详细解析】
1. **核心考点**：`ggml_cuda_init()` 在 `ggml-cuda.cu:268` 用 `cuDeviceGetAttribute(..., CU_DEVICE_ATTRIBUTE_VIRTUAL_MEMORY_MANAGEMENT_SUPPORTED, ...)` 探测并把结果写进 `devices[id].vmm`；`new_pool_for_device` 据此 `new ggml_cuda_pool_vmm(device)`（`:689`）或 `new ggml_cuda_pool_leg(device)`（`:692`）。
2. **错项分析**：A 忽略了 VMM 回退路径；C、D 与池选择无关——`cc` 影响的是 kernel 路径（MMQ/mma/PDL），不是池类型。
3. **落地补充**：排查「同二进制不同机器显存行为不同」时，第一件事就是确认该机的 `vmm` 属性，它决定了走无碎片的 VMM 还是 best-fit 的 LEG。

### 第 5 题
【题型：单选题】【难度：基础】
【题干】`ggml_backend_cuda_graph_compute()`（`ggml-cuda.cu:4425`）返回时，GPU 的真实状态是？
【选项】
A. 所有 kernel 已执行完毕
B. kernel 只是排进了 `ctx.stream()`，**可能仍在执行**
C. 函数内已隐式 `cudaDeviceSynchronize`
D. 只有最后一个 kernel 尚未完成
【正确答案】B
【详细解析】
1. **核心考点**：`graph_compute` 结尾**没有同步**，它只是把节点逐个 `launch` 到流里就返回 `GGML_STATUS_SUCCESS`。真正的等待发生在 `ggml_backend_cuda_synchronize`（`:2548` 的 `cudaStreamSynchronize`）。
2. **错项分析**：A、C 是「异步语义」这一 P0 知识点的典型误判；D 想当然地以为只有尾 kernel 未完成，实际上**全部**都可能还在飞。
3. **落地补充**：这就是「测速必须在 `synchronize()` 后收口」的根本原因。任何在 `graph_compute` 返回后立刻读 `dst` 或打时间戳的代码，测的都是「排程时间」而非「执行时间」。

### 第 6 题
【题型：多选题】【难度：基础】
【题干】关于 GGML-CUDA 的同步点，下列描述正确的是？（多选）
【选项】
A. `ggml_backend_cuda_synchronize`（`:2548`）内部是 `cudaStreamSynchronize(ctx.stream())`
B. buffer 的 H2D/D2H 上传下载走 `cudaStreamPerThread` 且**同步**（`:790`/`:798`）
C. `graph_compute` 返回前会强制同步一次
D. 跨卡拷贝用 event 的 record/wait 建立流间依赖（`:2537`/`:2540`）
【正确答案】ABD
【详细解析】
1. **核心考点**：同步点清单 = 后端级 `synchronize`（A）、buffer 上传下载（B）、跨卡拷贝 event（D）。热路径（compute）全异步，冷路径（set/get_tensor、跨卡）才同步。
2. **错项分析**：C 与源码相反——`graph_compute`（`:4425`）结尾没有任何同步调用，这正是它「返回 ≠ 算完」的由来。
3. **落地补充**：`cudaStreamPerThread` 与 `ctx.stream()` 完全隔离，这是 buffer 传输不干扰计算流的保证。要统计「推理一次到底多久」，只能以 `synchronize()` 为收口点。

【选项】
A. 8
B. 32

【正确答案】C

### 第 9 题
【题型：多选题】【难度：基础】
【题干】下列哪些现象说明当前推理处于「decode 访存瓶颈」？（多选）
【选项】
A. 每个 token 只把权重读一遍，算力利用率很低
B. 更激进的量化（减少权重字节）能直接提速
C. tensor core 算力成为唯一瓶颈
D. 提升 SM 频率收益有限，而提升显存带宽收益明显
【正确答案】ABD
【详细解析】
1. **核心考点**：decode（batch=1）计算强度极低，是典型的**访存密集**：耗时由「读一遍权重」的字节数决定，故量化（减少字节）直接提速（B），算力富余（A、D）。
2. **错项分析**：C 恰好说反——访存瓶颈下算力是富余的，只有当 batch 增大、计算强度上升后，算力才可能成为瓶颈。
3. **落地补充**：用 roofline 判断——计算强度 = FLOPs / Bytes。decode 落在带宽墙一侧，prefill 落在算力墙一侧，两者的优化手段完全不同（量化 vs tensor core）。

### 第 10 题
【题型：单选题】【难度：基础】
【题干】prefill（长 prompt 一次性处理）阶段的主要瓶颈性质是？
【选项】
A. 访存瓶颈，量化最有效
B. 计算瓶颈，cuBLAS / tensor core 的 FP16 吞吐更关键
C. 受 PCIe 带宽限制
D. 受 CPU 单线程限制
【正确答案】B

### 第 12 题
【题型：单选题】【难度：基础】
【题干】用 CUDA event 测单个算子耗时，正确做法是？
【选项】
A. 记录 start/stop 两个 event 即可直接读耗时
B. record start → 执行 → record stop → **`cudaEventSynchronize(stop)` 后再** `cudaEventElapsedTime`

### 第 13 题
【题型：多选题】【难度：基础】
【题干】关于 `ggml_cuda_dp4a`（`common.cuh:720`），下列说法正确的是？（多选）
【选项】
A. `__dp4a(a,b,c)` 语义是 `c + Σ a[i]*b[i]`（i=0..3），一条指令算 4 个乘加
B. 在 NVIDIA 上是 Pascal 及以后提供的整数点积指令

### 第 14 题
【题型：单选题】【难度：基础】
【题干】`block_q8_1` 中字段 `s`（`ggml-common.h:259`）的物理含义是？
【选项】
A. 该 block 的 scale `d`
B. 预计算的块和 `d * Σq`（近似为 Σx）
C. padding 占位
D. 量化零点（zero-point）
【正确答案】B
【详细解析】
1. **核心考点**：`s` 是量化激活时就算好的「块和」，让 Q4_0 的 `-8` 偏移项在点积里变成一次乘法：`return d4 * (sumi * ds8f.x - (8*vdr/QI4_0) * ds8f.y)`（`vecdotq.cuh:136`）。没有它就得在 kernel 里累加 q8。
2. **错项分析**：A 是 `d` 字段；D 是 Q4_1 的 min 概念，Q8_1 是对称量化无零点；C 与定义不符（`ds` 是 `half2`，d 与 s 打包）。
3. **落地补充**：注意 `quantize_q8_1`（`quantize.cu:54`）里 `sum` 初值是原始 float `xi` 而非量化后的 `q`，故 `s` 严格说是 Σx，近似等于 `d·Σq8`。

### 第 15 题
【题型：单选题】【难度：基础】
【题干】「量化推理能提速」的本质原因，下列表述最准确的是？
【选项】
A. 权重以整数块存储、**永不展开成 float**，把权重带宽降低 4~8 倍
B. 大幅减少激活显存
C. 显著减少浮点计算量（FLOPs）
D. 直接压缩了 KV cache
【正确答案】A
【详细解析】
1. **核心考点**：量化把「反量化 + FP 点积」融合成「整数点积 + 标量缩放」，权重字节数降 4~8 倍（模块四 §4.0）。decode 是访存瓶颈，故直接受益。
2. **错项分析**：B 错——激活量化（q8_1）本身还会**增加**一点临时显存；C 错——计算量未必减少，dp4a 只是换了指令形态；D 错——KV cache 是否量化取决于 FA 路径，与权重量化不是一回事。
3. **落地补充**：量化省的是**权重带宽**，不省激活显存。理解这一点，才能解释「为什么 prefill 反而不该用量化 kernel」。

### 第 19 题
【题型：单选题】【难度：基础】
【题干】在小 batch（decode）场景下，CUDA Graph 带来的典型端到端提速幅度是？

A. 1~3%

D. 基本无收益
【正确答案】B
