## 第一部分 · 基础题（第 1–60 题）

### 第 1 题
【题型：单选题】【难度：基础】
【题干】GGML-CUDA 每个算子遵循"三段式"结构，其中**主机端入口**（取指针、算元素数、选流）应放在哪个文件？
【选项】
A. `xxx.cuh`
B. `xxx.cu`
C. `common.cuh`
D. `ggml-backend-impl.h`
【正确答案】B
【详细解析】
1. **核心考点**：`xxx.cuh` = 声明 + 设备端 functor/模板 + 内联小工具（被 `#include`）；`xxx.cu` = 模板实例化 + 主机端启动逻辑 + `ggml_cuda_op_xxx()` 入口（独立编译单元）。三段式中的 ③ 主机端入口属于 `.cu`。
2. **错项分析**：A 只放设备端 functor 与声明，不含主机启动逻辑；C 是全模块共享设施（宏、traits、context），不属于单个算子；D 是 backend 抽象接口层，与具体算子无关。
3. **落地补充**：判断某个函数该放哪，只问一句"它是 device 端还是 host 端"：`op_xxx`（算什么，`__device__`）和模板声明进 `.cuh`，`xxx_cuda<>` 启动器和 `ggml_cuda_op_xxx` 进 `.cu`。`unary.cu`（721 行）是这条约定的最佳标本。

### 第 2 题
【题型：单选题】【难度：基础】
【题干】所有 CUDA 算子主机端入口的**固定签名**（铁律）是？
【选项】
A. `void ggml_cuda_op_xxx(ggml_tensor * dst, cudaStream_t stream)`
B. `void ggml_cuda_op_xxx(ggml_backend_cuda_context & ctx, ggml_tensor * dst)`
C. `bool ggml_cuda_op_xxx(ggml_backend_cuda_context & ctx, ggml_tensor * dst, int nargs)`
D. `void ggml_cuda_op_xxx(ggml_backend_cuda_context * ctx, const ggml_tensor * src0)`
【正确答案】B
【详细解析】
1. **核心考点**：签名铁律为 `void ggml_cuda_op_xxx(ggml_backend_cuda_context & ctx, ggml_tensor * dst)`，返回值 `void`，`ctx` 是**引用**，`dst` 是**非 const 指针**。正因为所有入口签名一致，`ggml-cuda.cu` 的 switch 才能用统一的函数指针表挂载它们。
2. **错项分析**：A 少了 ctx 且把 stream 当参数（stream 必须从 `ctx.stream()` 取）；C 返回值 `bool` 不符合铁律（是否支持由 `supports_op` 回答，不由入口回答）；D `ctx` 传指针、`dst` 传 const 且丢掉 dst 语义，均错。
3. **落地补充**：新增算子时**照抄** `void ggml_cuda_op_silu(ggml_backend_cuda_context & ctx, ggml_tensor * dst)` 这一行改个名字即可。签名写错会在 switch 注册时报编译错，属于"最友好的错"。

### 第 3 题
【题型：单选题】【难度：基础】
【题干】算子入口要读取输入张量，正确的方式是？
【选项】
A. 通过入口的第三、第四个参数传入
B. 从 `dst->src[i]` 取，如 `const ggml_tensor * src0 = dst->src[0];`
C. 从全局变量 `g_src0` 取
D. 通过 `ctx` 提供的 `ctx.src(0)` 取
【正确答案】B
【详细解析】
1. **核心考点**：GGML 张量把操作数存在 `src[GGML_MAX_SRC]` 数组里，算子入口**没有任何额外参数**，所有输入一律 `dst->src[i]`（如 `unary.cu` 里 `src0 = dst->src[0]`）。
2. **错项分析**：A 与"签名铁律"直接矛盾；C ggml-cuda 里不存在这种全局张量句柄；D `ggml_backend_cuda_context` 只有 device/stream/pool/cublas/graph 等资源，不持有张量。
3. **落地补充**：这也解释了为什么入口能统一签名——操作数从 dst 反查，不需要逐个传参。写融合算子（如 `unary_gated_op` 读 `src0`、`src1`）时同样如此。

### 第 4 题
【题型：单选题】【难度：基础】
【题干】三段式中的"① 设备端 functor"，其正确写法特征是？
【选项】
A. `__global__ void op_silu(float x)`，内部自己算线程索引
B. `static __device__ __forceinline__ float op_silu(float x)`，纯标量数学、无内存访问
C. `static void op_silu(float x)`，主机端普通函数
D. `template <typename T> __host__ __device__ void op_silu(T x)`
【正确答案】B
【详细解析】
1. **核心考点**：functor 只描述"每个元素做什么"：`__device__ __forceinline__`，纯标量数学、无线程概念、无内存访问，例如 `unary.cu` 的 `op_silu` 直接 `return ggml_cuda_op_silu_single(x);`（`ggml_cuda_op_silu_single` 定义在 `unary.cuh:98`，公式 `x / (1 + expf(-x))`）。
2. **错项分析**：A 用 `__global__` 是 kernel 不是 functor，且内部不该出现线程索引；C 缺 `__device__`，且无返回值；D 模板化不是必要条件（functor 只需满足 `float(float)` 原型），`__host__ __device__` 也非必需。
3. **落地补充**：`__forceinline__` 是硬要求——functor 以**模板参数** `float (*op)(float)` 传入时，必须内联才能让编译器把公式直接摊平进 kernel，否则会退化成函数指针间接调用。

### 第 5 题
【题型：单选题】【难度：基础】
【题干】`unary.cu` 中 functor 以**模板参数** `template <float (*op)(float), typename T>` 传入，而不是运行时函数指针参数。主要收益是？
【选项】
A. 减少编译时间
B. 每个 op 生成独立 kernel 实例，编译器可完全内联，消除间接调用开销
C. 允许在 kernel 内动态选择激活函数
D. 避免使用共享内存
【正确答案】B
【详细解析】
1. **核心考点**：模板参数使每个 op 生成**独立 kernel 实例**，公式被完全内联展开；若写成运行时函数指针参数，会引入间接调用（无法内联、无法常量传播）。
2. **错项分析**：A 相反，模板实例化会**增加**编译量与时间（这也是 `template-instances/` 存在的根源）；C 运行时选择恰恰是模板参数**做不到**的——模板必须编译期确定；D 与共享内存无关。
3. **落地补充**：这就是 `ggml_cuda_op_silu` 和 `ggml_cuda_op_gelu` 是**两个不同 kernel**、却只写一个 `unary_cuda` 的原因。新增一元激活时"kernel 零改动、只写 functor + 2 行封装"。

### 第 6 题
【题型：单选题】【难度：基础】
【题干】算子启动 kernel 时，正确做法是？
【选项】
A. 直接写 `kernel<<<grid, block, 0, stream>>>(...)`
B. 走 `ggml_cuda_kernel_launch(kernel, launch_params, args...)`（`common.cuh:1699`）
C. 用 `cudaLaunchKernel` 裸调
D. 用 `cudaGraphLaunch` 单独启动
【正确答案】B
【详细解析】
1. **核心考点**：`ggml_cuda_kernel_launch`（`common.cuh:1699`）是统一启动封装，内部处理 **PDL**（Hopper+ 的 Programmatic Dependent Launch，让连续 kernel 重叠启动）。`unary.cu:134`、`norm.cu` 的 rms_norm 等均已改走它。
2. **错项分析**：A 直接 `<<<>>>` 会**丢掉 PDL 路径**（Hopper 上损失 kernel 间隔优化）；C 裸调等价于绕开封装，同样丢 PDL 且易出错；D CUDA Graph 是 `graph_compute` 层面的事，不是单算子启动方式。
3. **落地补充**：`launch_params` 用 `ggml_cuda_kernel_launch_params((dim3)num_blocks, block, shmem, stream)`（`common.cuh:1594`）构造。注意：老算子（如 `rope_norm`）仍有 `<<<>>>` 残留，新代码应一律走封装。

### 第 7 题
【题型：单选题】【难度：基础】
【题干】算子内获取当前应使用的 CUDA stream，正确做法是？
【选项】
A. `cudaStream_t stream = 0;`
B. `cudaStream_t stream = ctx.stream();`
C. `cudaStream_t stream; cudaStreamCreate(&stream);`
D. `cudaStream_t stream = cudaStreamLegacy;`
【正确答案】B
【详细解析】
1. **核心考点**：`ctx.stream()`（`common.cuh:1455` 的 `ggml_backend_cuda_context` 成员）按 `curr_stream_no` 返回当前活跃流；`unary.cu:141` 就是 `cudaStream_t stream = ctx.stream();`。并发 fork 区域内 `curr_stream_no` 会被切成 1/2/3。
2. **错项分析**：A/D 用默认流会**破坏 fork-join 并发**并强制与非默认流同步；C 自建流不在 ggml 同步体系内，引入竞态。
3. **落地补充**：`ctx.stream()` 惰性创建且用 `cudaStreamNonBlocking` 标志（`common.cuh:1548`）。自定义算子**永远**用 `ctx.stream()`，绝不 `cudaStreamSynchronize(0)`。

### 第 8 题
【题型：单选题】【难度：基础】
【题干】1D 展平索引的元素级 kernel 中，`if (i >= k) return;` 这行边界检查的作用是？
【选项】
A. 提升 occupancy
B. 处理 grid 向上取整后多出来的线程，防止越界访存
C. 让编译器展开循环
D. 触发 PDL 同步
【正确答案】B
【详细解析】
1. **核心考点**：grid 用 `(k + BLOCK - 1) / BLOCK` 向上取整，末尾 block 会多出线程；`if (i >= k) return;` 让这些线程直接退出，防止 `x[i]`/`dst[i]` 越界。`unary.cu:118` 的 `unary_op_kernel` 就是这么写的。
2. **错项分析**：A occupancy 由寄存器/共享内存/block 大小决定，与本行无关；C 循环展开靠 `#pragma unroll`；D PDL 同步是 `ggml_cuda_pdl_sync()`。
3. **落地补充**：**漏掉边界检查是 illegal memory access 的头号根因**，且报错常滞后到下一个同步点（"出错的是前面第 N 个 kernel"）。调试用 `compute-sanitizer --tool memcheck`。

### 第 9 题
【题型：单选题】【难度：基础】
【题干】元素级算子的 block 大小为什么建议定义成宏（如 `#define CUDA_SILU_BLOCK_SIZE 256`）而不是字面量 256？
【选项】
A. 宏可以跨编译单元共享，便于统一调优与复用
B. 字面量会被编译器报错
C. 宏能提升寄存器数量
D. 宏是 CUDA 的强制要求
【正确答案】A
【详细解析】
1. **核心考点**：`unary.cuh:4-20` 为每个激活定义了 `CUDA_XXX_BLOCK_SIZE`（`CUDA_NEG_BLOCK_SIZE`、`CUDA_SILU_BLOCK_SIZE`…均为 256），集中在 `.cuh` 里便于统一调优，且 host 与 device 代码共享同一常量。
2. **错项分析**：B 字面量完全合法；C 宏与寄存器分配无关；D CUDA 无此强制要求。
3. **落地补充**：调优时改一处宏即可全局生效。注意 `unary.cu:132` 用的是 `CUDA_NEG_BLOCK_SIZE`——一元算子在 ggml 里复用了同一套 block size 宏。

### 第 10 题
【题型：单选题】【难度：基础】
【题干】关于 PDL 三件套，`ggml_cuda_pdl_lc()` 与 `ggml_cuda_pdl_sync()` 的正确使用纪律是？
【选项】
A. 两者都放在 kernel 最开头
B. `pdl_lc()` 放 kernel 开头提前取 launch 控制，`pdl_sync()` 必须放在**第一次读全局内存之前**
C. `pdl_sync()` 放 kernel 末尾
D. 两者可省略，PDL 自动生效
【正确答案】B
【详细解析】
1. **核心考点**：`common.cuh:139` 的 `ggml_cuda_pdl_lc()` 读取 launch 依赖让 kernel 提前开始；`common.cuh:133` 的 `ggml_cuda_pdl_sync()` 在真正读输入前等前序 kernel 写完。`unary.cu:118` 调 lc、`:125` 调 sync，恰好夹住第一次读 `x[i]`。
2. **错项分析**：A 若 sync 放开头就失去"提前启动"的意义；C sync 放末尾则读数据时可能拿到未写完的结果（错误结果而非崩溃，更难查）；D 必须显式调用，且仅 Hopper+ 生效（低架构上为空操作）。
3. **落地补充**：**写 PDL kernel 的唯一纪律**——`pdl_sync()` 之前不许读全局内存。含义是"启动"与"读数据"解耦，连续 kernel 可重叠启动。

### 第 12 题
【题型：单选题】【难度：基础】
【题干】只在 `compute_forward` 注册了新算子、却忘了改 `supports_op`，最可能的后果是？
【选项】
A. 编译报错
B. 算子永远不被调度到 CUDA（scheduler 认为不支持，走 CPU 或报错），但不崩溃
C. 显存泄漏
D. kernel 结果算错
【正确答案】B
【详细解析】
1. **核心考点**：`ggml_backend_sched` 靠 `supports_op` 决定每个 op 落哪个后端。`supports_op` 未声明 → scheduler 认为 CUDA 不支持 → 该 op 被分给 CPU 或整体报错。这是**静默失效**：`compute_forward` 的 case 永远走不到。
2. **错项分析**：A 编译正常（case 存在）；C/D 与调度层无关，是执行层问题。
3. **落地补充**：注意 `supports_op` 除了"是否支持"还检查**设备归属**（`:5141` 遍历 `op->src[i]->buffer->buft` 是否属于本 device）、类型组合、`nb[0]` 连续性、stride/layout、op_params 限制。"支持"≠"执行"。

### 第 13 题
【题型：单选题】【难度：基础】
【题干】在 `supports_op` 里声明了支持、却忘了在 `compute_forward` 的 switch 加 case，后果是？
【选项】
A. 编译期报错
B. scheduler 会把 op 分到 CUDA，但执行时 `compute_forward` 落到 `default` 返回 false，报"不支持/无法计算"
C. 自动回退 CPU
D. 结果正确但变慢
【正确答案】B
【详细解析】
1. **核心考点**：`compute_forward` 的 `switch (dst->op)` 末尾 `default: return false;` 表示不支持。scheduler 已按 `supports_op` 把 op 分给 CUDA，执行时却无 case → 返回 false → 上层报错。这是**两处不一致**的典型症状。
2. **错项分析**：A 编译能过；C scheduler 不会在"已分配"后再回退；D 根本不会执行。
3. **落地补充**：两处必须**成对**修改。写完后用 `test-backend-ops test -b CUDA0 -o XXX` 验证——它同时检验"能否调度"和"结果是否正确"。

### 第 15 题
【题型：单选题】【难度：基础】
【题干】新增一元激活 `GGML_UNARY_OP_SOFTSIGN` 时，枚举应加在哪个文件？
【选项】
A. `include/ggml.h` 的 `enum ggml_unary_op`（`:607`）
B. `src/ggml-cuda/unary.cuh`
C. `src/ggml-cuda/ggml-cuda.cu`
D. `src/ggml-cpu/ops.cpp`
【正确答案】A
【详细解析】
1. **核心考点**：枚举定义在 L0 层 `include/ggml.h` 的 `enum ggml_unary_op`（`:607`），在 `GGML_UNARY_OP_COUNT` 之前插入 `GGML_UNARY_OP_SOFTSIGN,`。改错地方会导致 CUDA/CPU 两侧枚举值不一致。
