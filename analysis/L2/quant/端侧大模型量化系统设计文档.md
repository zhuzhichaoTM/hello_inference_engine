## 一、为什么需要量化

> **本篇定位**：从零建立大模型量化的通用知识体系——数学基础、粒度选择、训练策略、
> 主流算法、KV Cache 与 FP8。本篇不依赖任何特定框架，是后续端侧部署篇的**理论地基**。
>
> **与 03/04 的分工**：本篇讲"量化是什么、为什么这样设计"的**通用原理**；
> 03 讲 ggml/llama.cpp 的**机制全景**；04 讲 `ggml-quants.c` 的**逐函数代码**。

### 1.1 模型规模问题

大模型推理面临的第一性矛盾是**参数量增长快于内存容量增长**：

| 模型规模 | FP16 | Q8_0 (8.5 bpw) | Q4_K_M (4.8 bpw) | Q2_K (2.625 bpw) |
|---------|------|----------------|------------------|------------------|
| 1.5B | 3.0 GB | 1.6 GB | 0.9 GB | 0.49 GB |
| 7B | 14.0 GB | 7.4 GB | 4.2 GB | 2.30 GB |
| 13B | 26.0 GB | 13.8 GB | 7.8 GB | 4.27 GB |
| 70B | 140.0 GB | 74.4 GB | 42.0 GB | 22.97 GB |

> BPW 采用**实际有效值**（含 block 元数据开销，见 §2.4），
> 而非标称位宽。例如 Q8_0 标称 8 bit，实际 8.5 bpw；
> Q4_K_M 标称约 4 bit，实际因混合精度策略为 4.8 bpw。

**计算式**：

$$\text{权重内存} = \frac{\text{参数量} \times \text{BPW}}{8}$$

其中 BPW（bits per weight）是每权重平均比特数。注意实际值略高于标称位宽，
因为每个 block 还要存 scale/min 元数据（见 §2.4 的 BPW 精确计算）。

**关键结论**：70B 模型在 FP16 下需要 140 GB——超过任何单张消费级 GPU（24 GB）；
即使 8×A100 80GB 也仅能勉强装下。而 Q4_K_M 后降至 42 GB，
**单张 48 GB 卡即可承载**，这是量化最直接的收益。

注意上表的**非线性压缩关系**：从 FP16 → Q8_0 只减半（2×），
但从 FP16 → Q4_K_M 减小 3.3×，→ Q2_K 减小 6.1×。
低 bit 需要 imatrix 支撑（见 §5），否则质量退化会抵消容量收益。

### 1.2 端侧显存限制

端侧设备的可用内存远小于服务器，且需与操作系统、应用共享：

| 设备类型 | 典型总内存 | LLM 可用预算 | FP16 可跑上限 | INT4 可跑上限 |
|---------|-----------|-------------|--------------|--------------|
| 旗舰手机 | 12–16 GB | 4–8 GB | ~2B | ~7B |
| 中端手机 | 6–8 GB | 2–4 GB | ~1B | ~3B |
| 车机 SoC | 8–16 GB | 6–12 GB | ~3B | ~13B |
| 嵌入式 | 2–4 GB | 1–2 GB | 不可行 | ~1.5B |
| 笔记本（核显共享） | 16–32 GB | 8–20 GB | ~5B | ~20B |

**结论**：**INT4 是把可用模型规模放大 3–4 倍的关键手段**。
没有量化，端侧只能跑 1–2B 小模型；有了量化，7B 级别模型才可能落地。

### 1.3 带宽瓶颈驱动

**这是 LLM 推理中最容易被低估的约束**。自回归 decode 阶段每生成一个 token，
都需要读取**全部权重一次**：

$$\text{单 token 带宽需求} = \text{参数量} \times \text{bytes\_per\_param}$$

| 模型 | FP16 每 token 读取 | Q4_K_M 每 token 读取 | 理论 decode 上限（500 GB/s 带宽） |
|------|------------------|---------------------|--------------------------------|
| 7B | 14.0 GB | 4.2 GB | FP16: 35.7 → Q4_K_M: 119.0 tok/s |
| 13B | 26.0 GB | 7.8 GB | FP16: 19.2 → Q4_K_M: 64.1 tok/s |
| 70B | 140.0 GB | 42.0 GB | FP16: 3.6 → Q4_K_M: 11.9 tok/s |

> 上表为**理论天花板**（假设带宽 100% 用于权重读取）。
> 实际可达值受 KV Cache 读取、算子开销、带宽利用率（通常 60–80%）影响。

**roofline 分析**：decode 阶段算术强度极低（每读取一个权重只做约 2 次浮点运算），
远低于 GPU 的拐点，因此**性能由带宽而非算力决定**。

```text
decode 时间 ≈ 权重字节数 / 有效带宽
→ 权重减半 = decode 提速接近 2 倍（带宽充足时）
```

**这解释了为什么量化的主要收益在 decode 而非 prefill**：
prefill 阶段是计算密集（batch 内所有 token 并行），
算术强度高，此时算力而非带宽是瓶颈，量化收益相对有限。

**三类瓶颈的对比总结**：

| 瓶颈 | 触发场景 | 量化收益 | 缓解手段 |
|------|---------|---------|---------|
| **容量** | 模型装不下 | 直接降低内存占用 | 量化 + 分片 + offload |
| **带宽** | decode 阶段 | 近乎线性提速 | 量化（首选）+ 批处理 |
| **算力** | prefill / 小模型 | 收益有限甚至为负 | 算子融合 + 并行 |

## 二、量化数学基础

### 2.1 量化公式

量化的核心是把连续浮点值映射到有限的离散整数集合。

**通用非对称线性量化**：

$$q = \text{clamp}\left(\text{round}\left(\frac{x}{s}\right) + z,\; q_{\min},\; q_{\max}\right)$$

| 符号 | 含义 |
|------|------|
| $x$ | 原始浮点值（FP32/FP16） |
| $q$ | 量化后的整数码（int8/uint8/int4…） |
| $s$ | **scale（缩放因子）**——浮点与整数之间的步长 |
| $z$ | **zero-point（零点）**——浮点 0 对应的整数码 |
| $[q_{\min}, q_{\max}]$ | 整数码的表示范围 |

**对称量化**（去掉 zero-point，$z = 0$）：

$$q = \text{clamp}\left(\text{round}\left(\frac{x}{s}\right),\; -2^{b-1},\; 2^{b-1}-1\right), \qquad s = \frac{\max|x|}{2^{b-1}-1}$$

其中 $b$ 是位宽。int8 时 $s = \max|x| / 127$。

**关键直觉**：`round` 引入的是**不可避免的量化误差**，其上界为 $s/2$。
因此**减小 $s$ 就减小误差**，而 $s$ 由该量化组内的最大值决定——
**这正是"量化粒度"要解决的问题**（见 §3）。

### 2.2 反量化公式

$$\hat{x} = s \cdot (q - z)$$

反量化把整数码还原为近似浮点值。注意 $\hat{x} \neq x$，
误差 $|x - \hat{x}| \le s/2$（均匀量化假设下）。

**推理中的关键工程事实**：主流方案（尤其 llama.cpp）**并不真的把权重反量化到 FP32 再计算**，
而是在**整数域**完成点积运算：

$$y = \sum_i w_i a_i \approx \sum_i \left[s_w(q_{w,i} - z_w)\right] \cdot a_i
= s_w \sum_i q_{w,i} a_i - s_w z_w \sum_i a_i$$

即：**先整数乘加，最后一次性乘缩放因子**。这样做的收益：

```text
① 避免 4 倍内存流量（INT4 反量化到 FP32 后再读）
② 整数乘加吞吐通常高于浮点
③ 缩放因子每 block 只用一次，浮点乘法从"每元素"降到"每 block"
```

具体实现见 04 §11.2（`ggml_vec_dot_q4_0_q8_0_generic` 的 `sumi * d_w * d_a` 模式）。

### 2.3 对称 vs 非对称选择

| 维度 | 对称量化 | 非对称量化 |
|------|---------|-----------|
| 公式 | $q = \text{round}(x/s)$ | $q = \text{round}(x/s) + z$ |
| 存储 | 仅 $s$ | $s$ + $z$（或 $s$ + min） |
| 零点 | 恒为 0 | 可映射到任意码值 |
| 整数码范围 | $[-2^{b-1}, 2^{b-1}-1]$ | 全范围 $[0, 2^b-1]$ |
| 表达非对称分布 | 差（一半动态范围浪费） | 好 |
| 计算开销 | 低（无零点修正项） | 稍高（需额外减/加 min 项） |
| 典型类型 | `q4_0` / `q5_0` / `q8_0` / `q3_K` / `q6_K` | `q4_1` / `q5_1` / `q2_K` / `q4_K` / `q5_K` |

**选择判据**：

```text
权重分布近似零均值对称 → 对称量化（如 ReLU 后的激活、多数层权重）
权重分布明显偏移       → 非对称量化（如某些层的权重、GELU 后的激活）
```

**llama.cpp 的实际选择**：同一份权重会同时存在对称与非对称版本供选择。
例如 `q4_0`（对称）vs `q4_1`（非对称），后者多存一个 fp16 的 min，
每 32 个权重多耗 2 字节（4.5 → 5.0 bpw），换来对偏移分布的更好拟合。

**为什么非对称的代价在扩展性上更明显？** 在 K-quant 中，
非对称意味着每个子块要同时存 scale 与 min 两套元数据，
这直接导致了 `q4_K` 的 12 字节复杂打包设计（见端侧篇 §12.3）。

### 2.4 量化误差的数学分解

理解误差来源是选择量化策略的基础。总误差可分解为三层：

```text
┌─ 第一层：量化码取整误差
│    |x - s·q| ≤ s/2
│    减小手段：减小粒度（per-group 而非 per-tensor）
│
├─ 第二层：scale/min 自身的表示误差
│    scale 用 fp16 存 → 相对误差约 2^-11
│    在 K-quant 中 scale 还被二级量化 → 额外 6-bit 截断误差
│    减小手段：更高精度的 scale 编码（q6_K 用 8-bit scale）
│
└─ 第三层：编码/解码不一致误差
     若量化时用浮点 scale 算 q，但存储时 scale 被截断
     → 解码用截断后的 scale，与量化时的假设不符
     消除手段：**重量化（requantize）**——用实际存储值重算 q
```

**第三层最容易被忽略**。llama.cpp 的所有 K-quant 参考实现都在最后一步做重量化
（见 [04 §5.3](04-ggml-quants源码详细分析.md)），
即用 `GGML_FP16_TO_FP32(y[i].d) * sc` 重新计算量化码。

**BPW 的精确计算**：

$$\text{BPW} = \frac{8 \times \text{type\_size}}{\text{blck\_size}}$$

| 类型 | type_size | blck_size | 精确 BPW |
|------|-----------|-----------|---------|
| `q4_0` | 18 B | 32 | 4.5 |
| `q4_K` | 144 B | 256 | 4.5 |
| `q6_K` | 210 B | 256 | 6.5625 |
| `q8_0` | 34 B | 32 | 8.5 |
| `q2_K` | 84 B | 256 | 2.625 |

注意 `q4_0` 与 `q4_K` 的**标称位宽相同、BPW 也相同**，但精度差异显著——
**BPW 相同的两种类型，精度可以差很多**，因为元数据的**组织方式**不同
（`q4_K` 用 8×32 子块 + 二级 scale，`q4_0` 只有 32 元素单 scale）。
这是 §3 要解释的核心。

## 三、量化粒度选择

**粒度（granularity）= 多少个权重共享一套 scale/min**。
这是量化设计中**最重要的单一决策**，直接决定精度、速度和存储开销的平衡。

### 3.1 Per-Tensor 为什么最快

整个张量共享一套 `s`（和 `z`）：

```text
权重张量 W[4096, 4096]（约 16M 权重）
  → 全局 max|x| → 1 个 scale
  → 全部 16M 权重用同一个 scale 量化
```

| 优点 | 缺点 |
|------|------|
| 元数据开销趋近于 0（16M 权重只存 1 个 scale） | **精度最差** |
| 反量化最简单：一个 scale 应用到全张量 | 单个离群值会毁掉整个张量的动态范围 |
| SIMD 最友好 | 权重分布不均匀时误差极大 |

**为什么精度差**：`s = max|x|/127`。若张量中有一个值为 100 的离群权重，
而 99.9% 的权重都在 `[-1, 1]` 内，则 $s \approx 0.79$，
大部分权重被量化到 0 或 ±1，**有效位宽坍塌到 1-2 bit**。

**适用场景**：激活值量化（配合校准可缓解）、或权重分布本身很均匀的层。

### 3.2 Per-Channel 为什么精度好

每个输出通道（通常是权重矩阵的一行或一列）共享一套 scale：

```text
W[4096, 4096] → 4096 个 scale（每行一个）
```

| 优点 | 缺点 |
|------|------|
| 精度显著优于 per-tensor | 元数据 4096 × 2B = 8 KB（相对 16M 权重可忽略） |
| 隔离行间差异（大模型不同通道的幅度可差 100×） | 反量化需按行索引 scale |
| 是 LLM 激活量化的标准做法 | 对行内离群值仍无抵抗力 |

**关键洞察**：LLM 权重的**行间方差远大于行内方差**。
不同通道承担不同功能，幅度天然差异大。Per-channel 恰好隔离了这种差异。

**LLM.int8() 的发现**：激活中约有 0.1% 的**离群通道**幅度是其他的 100 倍以上，
且集中在特定维度（与位置编码相关）。这催生了 §5.4 的混合精度方案。

### 3.3 Per-Group 为什么 LLM 选

在 per-channel 基础上，把每个通道再切成小组（group），每组一个 scale：

```text
W[4096, 4096] → 每行切为 4096/group_size 组 → 每组一个 scale
group_size = 32  →  4096/32 × 4096 = 524288 个 scale
```

**llama.cpp 的选择**：group_size ∈ {32, 256}，即 `QK_0 = 32`（经典系列）与 `QK_K = 256`（K-quant 超块）。

**为什么 LLM 最终选 per-group？**

```text
① 行内也存在局部差异：相邻若干列可能共现（如 FFN 的神经元分组）
   per-group 能捕捉这种局部动态范围
② 块内 max 更小 → scale 更小 → 量化步长更细 → 精度提升
③ 硬件友好：组大小取 32/64 对齐 SIMD 宽度，反量化可完全向量化
④ 元数据开销可控：group=32 时元数据占 1/16（q4_0 的 2B/16B）
```

**量化的核心权衡公式**：

$$\text{总比特数} = \underbrace{N \times b}_{\text{量化码}} + \underbrace{\frac{N}{g} \times b_{meta}}_{\text{元数据}}$$

| 粒度 | group 大小 | 元数据开销（int4 + fp16 scale） | 有效 BPW |
|------|-----------|------------------------------|---------|
| per-tensor | N | ≈ 0 | 4.00 |
| per-group | 128 | 16/128 = 0.125 bit/w | 4.125 |
| per-group | 32 | 16/32 = 0.5 bit/w | 4.50 |
| per-group | 16 | 16/16 = 1.0 bit/w | 5.00 |

**结论**：group 越小精度越好，但元数据开销线性上升。
**32 是在"精度收益"与"元数据成本"之间的工程最优点**——
这正是 llama.cpp 经典系列选 `QK=32` 的原因。

**llama.cpp 的两级粒度设计**：K-quant 在 32 元素子块之上再加一层 256 元素超块，
并对子块 scale 做二级量化（§2.4 的"第二层误差"由此引入，
但因为 scale 本身被压缩存储，整体 BPW 反而更低）。

| 层次 | 覆盖元素 | 存储内容 | 目的 |
|------|---------|---------|------|
| 超块 | 256 | `d`, `dmin` (fp16) | 二级缩放的基准 |
| 子块 | 32 | 6-bit scale + 6-bit min | 局部动态范围 |
| 元素 | 1 | 4-bit 量化码 | 实际权重 |

详细位布局见端侧篇 §12.3（`scales[12]` 的 96-bit 紧凑打包）。

## 四、PTQ vs QAT

### 4.1 PTQ 优劣

**PTQ（Post-Training Quantization，训练后量化）**：模型训练完成后，直接用校准数据或纯统计信息
确定量化参数，无需反向传播。

| 优点 | 缺点 |
|------|------|
| **零训练成本**：分钟到小时级 | 低 bit（≤3 bit）精度损失明显 |
| 无需训练数据（仅需少量校准集） | 无法适应量化的非线性影响 |
| 与现有训练管线解耦 | 各层独立量化，忽略层间误差传播 |
| 可快速迭代多档位 | 对分布敏感的层难以处理 |
| 生态成熟（GPTQ/AWQ/llama.cpp 原生） | 极端压缩需要辅助手段（imatrix） |

**PTQ 的三类实现**：

```text
① 纯统计型：只看权重分布（min/max/直方图）
   → 代表：llama.cpp 的 q4_0/q4_K（无 imatrix）
   → 特点：快、确定性、无需数据

② 校准型：用少量数据统计激活分布
   → 代表：llama.cpp 的 imatrix 加权量化
   → 特点：需要校准集，精度明显提升

③ 误差补偿型：逐层/逐列补偿量化误差
   → 代表：GPTQ（二阶）、AWQ（激活感知）
   → 特点：需要前向传播，精度最好
```

### 4.2 QAT 优劣

**QAT（Quantization-Aware Training，量化感知训练）**：在训练/微调时模拟量化操作（前向量化、
反向用 STE 直通估计器），让模型学会适应量化误差。

| 优点 | 缺点 |
|------|------|
| 低 bit（2-4 bit）精度显著优于 PTQ | 需要训练资源（GPU 集群 + 数据） |
| 模型可学习"量化友好"的权重分布 | 训练管线复杂，需插入伪量化算子 |
| 可端到端优化（考虑层间误差传播） | 迭代周期长（天级） |
| 是极低 bit 的唯一可靠方案 | 与基座模型强耦合，换模型需重训 |

**QAT 的典型流程**：

```text
① 加载预训练模型
② 在权重/激活上插入伪量化节点（fake quant）
     forward:  x → quantize → dequantize → x'   （模拟量化误差）
     backward: 梯度直通（STE），忽略 round 的不可导性
③ 微调若干 epoch
④ 导出真实量化模型（去掉伪量化节点，替换为整数算子）
```

### 4.3 为什么 LLM 主流用 PTQ

**这是 LLM 与视觉模型的根本差异**，原因有四：

```text
① 训练成本悬殊
   LLM 微调动辄数百 GPU·天，QAT 会让成本再翻倍
   视觉模型（ResNet 等）几小时可完成 QAT
   
② LLM 权重的量化友好性更好
   参数量巨大 → 冗余度高 → 单点误差被"平均掉"
   实测：7B 模型 Q4 通常仅退化 1-3% PPL
   而视觉模型 INT8 就可能掉点明显
   
③ 大模型对量化的敏感度集中在少数离群通道
   用 imatrix / 混合精度可精准保护，无需全模型重训（见 §5.2、§5.4）
   
④ 生态与工程现实
   PTQ 工具链成熟（llama.cpp / GPTQ / AWQ / AutoGPTQ）
   QAT 需要框架支持伪量化 + 与推理引擎对齐
```

**例外与边界**：

| 场景 | 推荐 | 原因 |
|------|------|------|
| ≥4 bit（Q4/Q5/Q6/Q8） | **PTQ** | 精度损失可接受，成本优势压倒性 |
| 3 bit（Q3_K） | PTQ + imatrix | 需要校准引导 |
| 2 bit（Q2_K/IQ2） | PTQ + imatrix（**必需**） | 无 imatrix 会产出垃圾 |
| ≤1.6 bit（IQ1/TQ） | PTQ + imatrix，或 **QAT** | 三值模型（BitNet）必须 QAT |
| NPU 固定 INT4 算子 | **QAT 建议** | NPU 无 imatrix 机制，只能靠训练补偿 |

**llama.cpp 的定位**：**纯 PTQ 路线**，通过"非均匀分层量化 + imatrix + 混合精度"
把 PTQ 的能力推到 2 bit 附近。这避免了 LLM 重训成本，代价是极低 bit 下不如 QAT。

## 五、LLM 量化算法

本节介绍四个**奠定 LLM 量化基础**的代表性算法。它们的核心思想已被 llama.cpp 以不同形式吸收。

### 5.1 GPTQ（二阶信息）

**核心思想**：把量化视为**逐列的最小二乘问题**，用量化误差补偿后续列。

**数学推导**。目标是最小化层输出误差：

$$\arg\min_{\hat{W}} \|WX - \hat{W}X\|_2^2$$

对权重矩阵按列量化。当第 $j$ 列被量化后，其误差会传播到剩余列。
GPTQ 用 **Hessian 矩阵** $H = 2XX^\top$ 的逆来最优地补偿：

$$\delta_j = \frac{w_j - \text{quant}(w_j)}{[H^{-1}]_{jj}}, \qquad
w_{k} \leftarrow w_k - \delta_j \cdot [H^{-1}]_{jk} \quad (k > j)$$

**关键点**：

| 要素 | 说明 |
|------|------|
| **二阶信息** | 用 $H^{-1}$ 而非简单均匀分配误差——考虑参数间的相关性 |
| **逐列贪心** | 每列量化后立即补偿，误差不累积 |
| **校准集** | $X$ 来自少量校准数据（通常 128 条） |
| **Cholesky 分解** | 实际实现用 Cholesky 避免显式求逆，降低数值误差 |

**优劣**：

```text
✅ 3-4 bit 下精度接近无量化（优于 RTN）
✅ 有开源实现（AutoGPTQ / GPTQ-for-LLaMA）
❌ 需要前向传播 + Hessian 计算，耗时（7B 约 10-30 分钟）
❌ 需要校准数据（但量少）
❌ 原始版本按列串行量化，难以并行
```

**与 llama.cpp 的关系**：llama.cpp **未实现 GPTQ**（无跨列误差反馈），
其量化是**行/块独立**的。llama.cpp 用 **imatrix** 这一更轻量的方式
近似 GPTQ 的"重要性加权"效果（见 §5.2）。

### 5.2 AWQ（激活感知）

**核心洞察**：**不是所有权重同等重要——激活幅度大的通道，其权重误差影响更大**。

$$\text{OutputError} \propto \sum_i \left( \underbrace{|a_i|}_{\text{激活幅度}} \cdot (w_i - \hat{w}_i) \right)^2$$

因此量化步长应按通道重要性分配，而非均匀分配。

**数学形式**。AWQ 引入逐通道缩放因子 $s$：

$$W \cdot \text{diag}(s)^{-1} \cdot \text{diag}(s) \cdot X$$

即把权重按通道缩放、激活反向缩放（保持乘积不变），
使**重要通道的权重量化更精细**：

$$\min_s \left\| \text{quant}\left(W \cdot \text{diag}(s)^{-1}\right) \cdot \text{diag}(s) X - WX \right\|$$

**关键点**：

| 要素 | 说明 |
|------|------|
| **激活感知** | 重要性来自激活统计，非权重自身幅度 |
| **逐通道缩放** | 只优化一个对角矩阵，比 GPTQ 的 Hessian 便宜 |
| **保护 1% 显著通道** | 实测识别出的重要通道占比极小 |
| **无需反向传播** | 比 GPTQ 更快 |

**llama.cpp 的对应实现**：**imatrix**。
imatrix 记录每个输入通道的激活重要性，量化时作为加权系数传入量化 helper，
即 **最终权重 = imatrix 值 × √(块方差 + 元素幅度²)**。
第二项是"自身显著度"补偿（避免 imatrix 在某通道过小时完全忽略权重幅度）。
具体融合公式与代码位置见 [04 §8.1](04-ggml-quants源码详细分析.md)。

**AWQ 与 imatrix 的差异**：

| 维度 | AWQ | llama.cpp imatrix |
|------|-----|------------------|
| 缩放位置 | 对权重做逐通道缩放变换 | **不改变权重**，只影响量化时的误差分配 |
| 是否可逆 | 需在推理时反向缩放（或融合进相邻层） | 无额外推理开销（量化后 imatrix 即丢弃） |
| 精度上限 | 更高（真正的通道级重分配） | 稍低（仅在量化决策时加权） |
| 实现复杂度 | 高（需修改权重并处理算子融合） | 低（一个 float 数组贯穿量化函数） |

**这是 llama.cpp 的核心设计取舍**：用"更弱的数学手段 + 更简单的工程实现"
换取零推理开销与零算子改动。

### 5.3 SmoothQuant（异常值平滑）

**核心洞察**：激活中的**离群值**是 INT8 量化的主要障碍。
激活的动态范围比权重宽得多（可达 100×），而权重分布相对温和。

**解决方案**：**把量化的难度从激活迁移到权重**。
引入逐通道平滑因子 $s$：

$$Y = (X \cdot \text{diag}(s)^{-1}) \cdot (\text{diag}(s) \cdot W)$$

- $X \cdot \text{diag}(s)^{-1}$：**缩小**激活中的离群值 → 激活更好量化
- $\text{diag}(s) \cdot W$：**放大**对应的权重通道 → 权重承担更多难度

**最优 $s$ 的选择**（平衡激活与权重的难度）：

$$s_j = \frac{\max|X_j|^\alpha}{\max|W_j|^{1-\alpha}}, \qquad \alpha \in [0, 1]$$

$\alpha = 0.5$ 时两者难度相等。$\alpha$ 是调优超参（论文推荐 0.5）。

**优劣**：

```text
✅ 让激活也能量化到 INT8（W8A8），端到端提速明显
✅ 数学优雅，只优化一个向量
✅ 是 W8A8 量化的标准前置步骤
❌ 需要校准数据统计激活分布
❌ 引入额外的缩放算子（需融合进前序算子才无开销）
❌ 需要修改模型结构，与 llama.cpp 的"零改动量化"哲学冲突
```

**与 llama.cpp 的关系**：**未采用**。
llama.cpp 的激活是**推理时即时量化**（FP32 → `q8_0`/`q8_K`），
不做校准、不做平滑变换。它通过**独立量化每个 block** 而非 per-tensor，
天然对激活离群值有一定抵抗力（离群值只污染它所在的那个 block）。

### 5.4 LLM.int8()（混合精度）

**核心发现**：LLM 激活中存在**系统性的离群特征维度**。

```text
实测（OPT-175B / BLOOM-176B）：
· 约 0.1% 的激活通道，其幅度是其余通道的 100 倍以上
· 这些离群维度高度集中（少数固定维度）
· 与位置编码、特定 token 类型相关
· 若整体用 INT8 量化，这些离群值会毁掉动态范围
```

**解决方案：按通道分组，分别处理**。

```text
对矩阵乘 X·W：
  ① 检测离群维度（幅度 > 阈值 α，典型 α = 6.0）
  ② 离群维度：用 FP16 保留（保精度）
  ③ 其余维度：用 INT8 量化（保速度）
  ④ 两部分结果相加
```

**关键点**：

| 要素 | 说明 |
|------|------|
| **混合精度** | 0.1% 的维度用 FP16，99.9% 用 INT8 |
| **额外开销极小** | 因为离群维度极少，FP16 部分计算量可忽略 |
| **无需校准数据** | 阈值 α 在推理时动态检测 |
| **无需修改权重** | 只处理激活侧 |

**优劣**：

```text
✅ 首次让 LLM 的 INT8 推理质量接近 FP16
✅ 无需校准、无需训练、权重零改动
✅ 是"训练后 + 零数据"量化的典范
❌ 需要为混合精度写专门 kernel（实现复杂）
❌ 只解决激活量化，权重仍需单独处理
❌ 阈值 α 需调优
```

**与 llama.cpp 的关系**：**部分借鉴**。
llama.cpp 中"敏感张量不量化"的策略（`_norm.weight`、`output.weight`、
`ffn_gate_inp` 保持高精度，见端侧篇 §11.3.2）与 LLM.int8() 的思想同源——
**都是"识别少数敏感部分，让它们保持高精度"**。
但 llama.cpp 的粒度是**张量级**（而非通道级），因为张量级的实现成本低得多。

### 5.5 四算法对比与 llama.cpp 的取舍

| 维度 | GPTQ | AWQ | SmoothQuant | LLM.int8() |
|------|------|-----|-------------|------------|
| **解决对象** | 权重量化 | 权重量化 | 激活量化 | 激活量化 |
| **核心手段** | 二阶误差补偿 | 激活感知加权 | 难度迁移 | 混合精度 |
| **需要校准** | ✅ 少量 | ✅ 少量 | ✅ 中等 | ❌ 不需要 |
| **需要前向传播** | ✅ | ✅ | ✅ | ❌ |
| **推理额外开销** | 无 | 需反向缩放 | 需缩放算子 | 混合 kernel |
| **llama.cpp 是否采用** | ❌ | ⚠️ 以 imatrix 近似 | ❌ | ⚠️ 思想借鉴（张量级） |
| **llama.cpp 对应机制** | 无（块独立量化） | **imatrix** | 无（块独立抗离群） | 敏感张量排除 |

**llama.cpp 统一的设计哲学**：

```text
① 零训练依赖 —— 只用统计信息 + 可选校准，不涉及反向传播
② 零推理开销 —— 量化后所有辅助信息（imatrix）即丢弃，模型文件自包含
③ 块独立量化 —— 每个 block 独立，可完全并行、可任意分块
④ 极高的确定性 —— 相同输入必然产生逐位相同的输出文件
⑤ 极简 kernel —— 拒绝需要额外算子的方案（SmoothQuant 的缩放变换）

代价：3 bit 以下必须依赖 imatrix，且精度上限略低于 GPTQ/AWQ/QAT
收益：任意模型可量化、跨硬件可复现、推理零额外成本
```

**这个取舍对端侧尤其关键**：端侧没有训练资源、没有校准基础设施，
而 llama.cpp 的方案只需要一次离线量化 + 一个可选的 imatrix 文件。

## 六、KV Cache 量化

### 6.1 为什么 KV Cache 需要单独量化

**KV Cache 是长上下文场景下的内存主导项**，其增长是**线性于上下文长度**的：

$$M_{KV} = 2 \times n_{layer} \times n_{ctx} \times n_{head\_kv} \times d_{head} \times b$$

其中 $2$ 覆盖 K 与 V 两份缓存，$b$ 是每元素字节数。

**关键工程事实**：在长上下文场景下，**KV Cache 可能超过模型权重**：

| 模型 | 层数 | 权重 (FP16) | KV @ 4K | KV @ 32K | KV @ 128K |
|------|------|-----------|---------|----------|-----------|
| 7B  | 32 | 14 GB | 0.5 GB | 4.0 GB | **16.0 GB** |
| 13B | 40 | 26 GB | 0.6 GB | 5.0 GB | 20.0 GB |
| 70B | 80 | 140 GB | 1.2 GB | 10.0 GB | 40.0 GB |

> 计算参数：GQA `n_head_kv = 8`、`d_head = 128`、FP16（2 B/element）。
> 公式见 §6.1，`2×` 覆盖 K 与 V 两份缓存。

**结论**：128K 上下文时，7B 模型的 KV Cache（16.0 GB）**已超过权重（14 GB）**。
即便 32K 上下文，7B 的 KV 也达 4.0 GB——在 8 GB 端侧设备上，
权重（Q4_K_M 约 4.2 GB）+ KV（4.0 GB）已逼近上限。
**不量化 KV，长上下文在端侧直接不可行**。

### 6.2 KV Cache 的量化的特殊性

KV 量化在三个维度上比权重更难：

```text
① 动态性：KV 在推理时持续写入，无法离线分析分布
   → 权重可以预先统计 min/max，KV 不行
   → 只能用在线统计或固定量化参数
   
② 热路径：每个 token 都要读写全部历史 KV
   → 反量化必须极快（比权重的反量化更敏感）
   → 这解释了为什么 KV 支持的类型远少于权重（见 §6.4）
   
③ 误差累积：KV 的量化误差会沿序列传播
   → 早期 token 的误差影响所有后续 token 的 attention
   → 长上下文下误差累积效应显著
```

### 6.3 K 与 V 的差异化处理

**实测结论**：**K 和 V 对量化的敏感度不同**。

| 维度 | K 的敏感度 | V 的敏感度 |
|------|-----------|-----------|
| 作用 | 与 Q 做点积决定 attention 权重 | 参与加权求和产生输出 |
| 量化误差影响 | 改变 attention 分布（间接） | 直接进入输出（直接） |
| 敏感性 | 较低 | **较高** |
| 常见配置 | 可更激进（Q4_0） | 相对保守（Q8_0 或 FP16） |

**实践中的非对称配置**：

```text
保守：-ctk q8_0 -ctv q8_0     （两者都减半，精度损失极小）
激进：-ctk q4_0 -ctv q8_0     （K 更激进，V 保守）
极限：-ctk q4_0 -ctv q4_0     （需实测验证质量）
```

### 6.4 KV 量化的类型选择为何受限

权重支持 27 种量化类型，而 KV **仅支持 9 种**（见端侧篇附录 D）。
这个限制是**刻意的**：

| 被排除的类型 | 排除原因 |
|-------------|---------|
| 所有 K-quant（`q4_K`/`q5_K`/`q6_K`…） | 超块反量化需要解包 `scales[12]`，开销过大 |
| 所有 IQ 格点（`iq2_*`/`iq3_*`/`iq1_*`） | 需要格点查表 + 符号处理，热路径不可接受 |
| `mxfp4` / `nvfp4` | 共享指数的解包开销 + 硬件支持有限 |
| `tq1_0` / `tq2_0` | 三值解码需要整数除法/移位 |

**保留的 9 种**（`f32`/`f16`/`bf16`/`q8_0`/`q4_0`/`q4_1`/`iq4_nl`/`q5_0`/`q5_1`）
共同特征是：**反量化只需简单的乘加，无查表、无多级解包**。

```text
q8_0 反量化：y = d * (int8)q                ← 1 次乘
q4_0 反量化：y = d * ((q & 0xF) - 8)        ← 1 次乘 + 1 次减
iq4_nl 反量化：y = d * kvalues_iq4nl[q]      ← 1 次查表 + 1 次乘（16 项表，可常驻 L1）
```

### 6.5 KV 量化的误差缓解技术

| 技术 | 原理 | llama.cpp 支持 |
|------|------|---------------|
| **非对称 K/V 配置** | K 激进、V 保守 | ✅ `-ctk`/`-ctv` 独立设置 |
| **正交旋转（Hadamard）** | 旋转 K/V 使能量分散，消除离群通道 | ✅ `ggml_gen_hadamard` |
| **分组量化** | K/V 按 head_dim 分组，每组独立 scale | ✅ `q4_0`/`q8_0` 的块结构 |
| **层间差异化** | 不同层用不同精度 | ❌ 需手动逐层配置 |
| **滑动窗口 + 量化** | 近期 token 保持高精度，远的量化 | ⚠️ 通过 ISWA/SWA 架构支持 |

**Hadamard 旋转的原理**（`src/llama-kv-cache.cpp:20-22`）：

```text
问题：KV 中某些通道存在离群值（与权重激活的离群通道同源）
方案：K/V 在写入缓存前，先与正交 Hadamard 矩阵 H 相乘
      K' = K·H     （H 是正交矩阵，H·Hᵀ = I）
效果：能量分散到所有通道 → 消除离群 → 逐通道量化误差更均匀
为何无损：H 正交，attention 计算中包含 Q·K'ᵀ，可通过同时在 Q 侧施加 H 抵消
```

这与 SmoothQuant 的"难度迁移"思想同源，但用**正交变换**保证信息不丢失。

## 七、FP8 量化（新趋势）

### 7.1 Hopper 原生支持

FP8 是 NVIDIA 从 Hopper 架构（H100）起**硬件原生支持**的 8-bit 浮点格式：

| 架构 | FP8 支持 | 说明 |
|------|---------|------|
| Ampere (A100) | ❌ | 需软件模拟 |
| **Hopper (H100)** | ✅ | Transformer Engine，原生 FP8 矩阵乘 |
| Ada (RTX 40) | ✅ | 部分支持 |
| Blackwell (B200) | ✅ | 进一步优化 |

**与 INT8 的本质区别**：INT8 是**定点**格式（均匀分布），
FP8 是**浮点**格式（指数分布，动态范围大得多）。

| 格式 | 总位宽 | 符号 | 指数 | 尾数 | 动态范围 | 精度（尾数决定） |
|------|-------|------|------|------|---------|----------------|
| INT8 | 8 | 1 | — | — | 均匀，$[-128,127]$ | 1.0（整数） |
| **E4M3** | 8 | 1 | 4 | 3 | $\pm 448$ | 约 2^-3 |
| **E5M2** | 8 | 1 | 5 | 2 | $\pm 57344$ | 约 2^-2 |
| FP16 | 16 | 1 | 5 | 10 | $\pm 65504$ | 约 2^-10 |

### 7.2 E4M3 vs E5M2

两种 FP8 格式是**精度与范围的权衡**：

| 维度 | E4M3 | E5M2 |
|------|------|------|
| 指数位 | 4 | 5 |
| 尾数位 | 3 | 2 |
| 动态范围 | 较小（±448） | **较大**（±57344） |
| 相对精度 | **较高**（2^-3） | 较低（2^-2） |
| 典型用途 | **权重 + 前向激活** | **反向梯度** |
| 归一化方式 | 需 per-tensor/per-channel scale | scale 需求弱 |

**选择判据**：

```text
权重（分布集中、需精度）      → E4M3
前向激活（分布宽、需范围）    → E4M3（配 scale）或 E5M2
反向梯度（范围极大、无需高精度）→ E5M2
KV Cache                     → E4M3（精度优先）
```

**工程实践**：主流方案（Transformer Engine、vLLM）默认**前向用 E4M3，反向用 E5M2**。

### 7.3 为什么 FP8 是未来

FP8 相对 INT8 与 INT4 的核心优势：

| 优势 | 说明 |
|------|------|
| **硬件原生加速** | Hopper/Blackwell 的 FP8 张量核吞吐是 FP16 的 2 倍 |
| **无需 imatrix/校准** | 浮点格式动态范围大，离群值影响远小于 INT8 |
| **动态范围大** | 同一 scale 可覆盖更宽的数值分布，减少分组需求 |
| **精度介于 INT8 与 FP16 之间** | 质量损失小于 INT8→INT4，接近 FP16 |
| **训练推理统一** | 同一格式可用于 QAT 与推理，管线简化 |

**为什么 FP8 仍未取代 INT4？**

```text
① FP8 = 8 bit，体积是 INT4 的 2 倍
   → 容量受限场景（端侧）仍必须用 INT4
② 硬件门槛：需 Hopper 及以上
   → 端侧设备（手机/车机 NPU）普遍不支持 FP8
③ 端侧 NPU 主流是 INT8/INT4 定点算子
   → FP8 的浮点指数运算对 NPU 不友好
```

**趋势判断**：

```text
云端 / 数据中心：  FP8 正在成为新标准（替代 FP16 与 INT8 的部分场景）
端侧 / 边缘：      INT4/INT8 仍将长期主导（硬件成本 + 能效）
未来可能：         FP8 下移到高端移动 SoC；FP4（E2M1）在端侧出现
                   → llama.cpp 已支持 mxfp4 / nvfp4（后者 ftype 尚未接线，见端侧篇附录 F）
```

**llama.cpp 中的 FP4 系列**：

| 类型 | 格式 | 缩放因子 | BPW | 说明 |
|------|------|---------|-----|------|
| `mxfp4` | E2M1（4 bit 浮点） | E8M0（8-bit 共享指数） | 4.25 | OCP MX 规范，MoE 场景 |
| `nvfp4` | E2M1 | UE4M3（每 16 元素） | 4.5 | NVIDIA 规范，更细粒度缩放 |

两者都是**浮点 4-bit**（而非定点 INT4），代表了"浮点量化下移到 4 bit"的趋势。
E2M1 的动态范围是 $\{0, 0.5, 1, 1.5, 2, 3, 4, 6\}$（含符号），
比 INT4 的均匀 16 级更能匹配权重的类高斯分布。

## 八、量化技术全谱系总览

### 8.1 从位宽看量化

| 位宽 | 格式族 | 代表 | 模型体积（7B） | 精度退化 | 端侧可行性 |
|------|-------|------|--------------|---------|-----------|
| 16 bit | FP16 / BF16 | — | 14.0 GB | 无（基线） | 小模型 |
| 8.5 bit | INT8 对称 | `q8_0` | 7.4 GB | 极小 | ✅ |
| 8 bit | FP8 | E4M3 / E5M2 | 7.0 GB | 极小 | ⚠️ 硬件受限 |
| 6.56 bit | INT 非对称 | `q6_K` | 5.7 GB | 极小 | ✅ |
| 5.5 bit | INT 非对称 | `q5_K` | 4.8 GB | 很小 | ✅ |
| 4.5–4.8 bit | INT 非对称 | `q4_K_M` / `q4_0` | 4.2 GB | 小 | ✅ **主力** |
| 4.25–4.5 bit | FP4 | `mxfp4` / `nvfp4` | 3.8 GB | 小 | ⚠️ MoE/新硬件 |
| 3.44 bit | INT 非对称 | `q3_K` | 3.0 GB | 中 | ✅ |
| 2.63 bit | INT 两级 scale | `q2_K` | 2.3 GB | 明显 | ✅ 需 imatrix |
| 2.31–2.56 bit | 格点码本 | `iq2_xs` / `iq2_s` | 2.1 GB | 明显 | ⚠️ 需 imatrix |
| 1.69–2.06 bit | 三值 | `tq1_0` / `tq2_0` | 1.5 GB | 需 QAT | ⚠️ 仅 BitNet |
| 1.56 bpw | 1-bit 格点 | `iq1_s` | 1.4 GB | 显著 | ❌ 需 imatrix |

### 8.2 量化决策树

```text
需要量化吗？
├─ 否 → 显存/内存充足且延迟可接受 → 用 FP16/BF16
└─ 是 → 先确定瓶颈
        │
        ├─ 容量瓶颈（装不下）
        │   └─ 目标 BPW = (可用内存 - KV - 运行时) / 参数量 × 8
        │       ├─ ≥ 6 bit  → q6_K / q8_0
        │       ├─ 4-5 bit  → q4_K_M（端侧默认）
        │       ├─ 3 bit    → q3_K + imatrix
        │       └─ ≤ 2.5 bit → q2_K / IQ2 + imatrix（必需）
        │
        ├─ 带宽瓶颈（decode 慢）
        │   └─ 量化直接提速，收益近似线性
        │       优先选 kernel 覆盖好的类型（K-quant 系列）
        │
        └─ 算力瓶颈（prefill 慢 / 小模型）
            └─ 量化收益有限，甚至因反量化开销变慢
                优先算子融合、批处理，而非更激进的量化

补充维度：
├─ 后端是 NPU？ → 只能用 INT8/INT4，考虑 QAT
├─ 需要 FP8？   → 需 Hopper+ 硬件
├─ 上下文很长？ → 必须同时量化 KV Cache
└─ 模型是 MoE？ → 考虑 mxfp4
```

### 8.3 本章小结

**核心结论回顾**：

```text
① 量化的三大驱动力：容量（装得下）、带宽（跑得快）、功耗（不烫手）
   —— 其中带宽是 decode 阶段的主导约束

② 数学基础：q = round(x/s) + z，误差上界 s/2
   —— 减小误差的核心是减小 s，即缩小量化组（粒度）

③ 粒度是核心决策：per-tensor（快）→ per-channel（准）→ per-group（LLM 选择）
   —— group=32 是精度与元数据开销的工程最优点

④ PTQ 主导 LLM：训练成本 + 权重冗余度 + 离群通道可精准保护
   —— 4 bit 以上 PTQ 足够；2 bit 需 imatrix；三值需 QAT

⑤ 四大算法的心智模型：
   GPTQ  → 用二阶信息补偿量化误差（逐列）
   AWQ   → 按激活重要性分配量化误差（逐通道）
   Smooth→ 把量化难度从激活迁移到权重
   int8()→ 少数离群维度保 FP16，其余 INT8

⑥ KV Cache 必须单独对待：动态、热路径、误差累积
   —— 类型受限（9 种）是刻意的工程取舍

⑦ FP8 是云端趋势（硬件原生 + 无需校准），
   INT4 仍是端侧主流（体积 + 硬件成本）
```

**通向端侧部署**：本篇建立了量化的通用理论。
接下来的第二部分将聚焦**端侧特有的问题**：
在给定的设备预算下如何做档位决策、llama.cpp 的量化类型体系如何映射到端侧需求、
KV Cache 与稀疏注意力如何与量化协同、以及三端（CPU/GPU/NPU）的实际部署路径。

## 九、端侧量化的约束与判据

### 9.1 硬约束

端侧设备相比云端服务器有六项硬约束（整合自 `llama-edge-quantization-system-design.md` §1.1）：

```text
内存/显存有限       → 模型必须压缩到可装载
DRAM 带宽有限       → 权重读取成为瓶颈（decode 阶段的主因）
算力有限           → 不能大量增加反量化/特殊计算
功耗/发热受限      → 数据搬运和计算都要省
存储有限           → 安装包体积要小
无/弱互联网         → 模型需预置
```

### 9.2 量化的本质与代价结构

```text
用更少的 bit 表示权重（和激活 / KV），以损失少量精度为代价，
换取 容量↓、带宽↓、功耗↓、速度可能↑。
```

**"速度可能↑"是关键的不确定性**：量化对延迟是**双面**的（`llama-quant-analysis.md` §13.3）：

| 方向 | 机制 |
|------|------|
| **有利** | 权重更小 → 内存带宽压力降低 → decode 变快；cache 命中率提高；更多权重可驻留缓存 |
| **不利** | 反量化（dequantize）计算开销；低 bit 需要特殊 kernel；IQ 系列反量化更复杂 |

```text
端侧/带宽受限 → 量化通常更快（尤其 decode）
算力受限      → 量化收益可能被反量化开销抵消
结论：必须实测，不能只看 BPW。
```

### 9.3 成功判据（五个必须同时满足）

```text
① 能装下   —— 容量在设备预算内
② 跑得动   —— decode tok/s 达到交互要求
③ 不烫手   —— 功耗/温度在热限内
④ 质量可接受 —— 困惑度/任务指标退化可控
⑤ 首字够快 —— TTFT 满足交互
```

只追求"装得下"或"跑得快"都是片面的。这五条构成了后续所有决策的**验收标准**。

### 9.4 干系人与职责

| 干系人 | 关注点 | 需要的产出 |
|--------|--------|-----------|
| 端侧开发者 | 量化、部署、集成 | 可复现的量化命令、多档位产物 |
| 算法工程师 | 质量评估、选档位 | PPL/任务报告、误差分布 |
| 设备厂商 | NPU 工具链、硬件规格 | 算子支持矩阵、工具链版本 |
| 产品 | 交互延迟、内存、安装包预算 | 档位决策依据、检查清单 |

## 十、系统架构与分层模型

### 10.1 架构模式选型

**Pattern: Layered Pipeline（分层流水线）+ Strategy（策略模式）**

选型理由（`llama-edge-quantization-architecture.md` §2.2）：

- **Layered**：量化流程天然分阶段（转换 → 决策 → 执行 → 评估 → 部署），每层可独立替换；
- **Strategy**：`llama_ftype` → `ggml_type` 的映射、以及"张量类别 → 目标类型"规则是**可替换策略**，
  分别对应 `llama_ftype_get_default_type()` 与 `llama_tensor_get_type_impl()`；
- **组合而非继承**：量化工具是"流程编排"，不是"对象继承树"。

**被拒绝的备选**：

| 备选 | 拒绝理由 |
|------|---------|
| 单体脚本 | 简单但不可复用、难评估、难多端适配 |
| 微服务 | 端侧离线工具链过重 |
| 自研量化引擎替换 llama.cpp | 成本高、生态断裂（保留 llama.cpp 作为执行核心） |

### 10.2 端侧量化体系的六个层次

端侧量化不是单一动作，而是一个多层次体系。**这是本文档的核心架构视图**：

```text
┌──────────────────────────────────────────────────────────────────┐
│                    端侧量化体系层次                                 │
│                                                                    │
│  L1 权重量化       → 减小模型权重体积        【llama.cpp 已覆盖】   │
│      Q8/Q4/Q5/Q2/IQ/MXFP4/NVFP4/TQ                                 │
│                                                                    │
│  L2 激活/动态量化   → 降低计算中间精度        【llama.cpp 部分覆盖】 │
│      f32 激活 → q8_0 / q8_1 / q8_K（运行时即时量化）                 │
│                                                                    │
│  L3 KV 量化        → 减小缓存体积、降长上下文带宽 【已覆盖】         │
│      Q8_0 / Q4_0 / Q4_1 / Q5_0 / Q5_1 / IQ4_NL / F16 / BF16        │
│      + 可选 Walsh-Hadamard 旋转（非 Hadamard 量化）                  │
│                                                                    │
│  L4 稀疏/结构压缩   → 减少参与计算的权重/激活  【部分覆盖】          │
│      SWA / DSV4 / DSA 稀疏注意力 / MoE 稀疏                         │
│                                                                    │
│  L5 知识蒸馏/剪枝   → 训练阶段压缩（配合量化）【训练侧，不在范围】    │
│                                                                    │
│  L6 运行时策略      → mmap、offload、batch、缓存复用 【已覆盖】      │
└──────────────────────────────────────────────────────────────────┘
```

| 层次 | llama.cpp 覆盖状态 | 关键实现 |
|------|-------------------|---------|
| L1 权重 | ✅ 完整 | `src/llama-quant.cpp` + `ggml-quants.c`（见 03/04） |
| L2 激活 | ⚠️ 仅推理期即时量化 | `type_traits_cpu[].from_float`（03 §7.3） |
| L3 KV | ✅ 完整 | `src/llama-kv-cache.cpp`、`-ctk/-ctv`（见 10.4） |
| L4 稀疏 | ⚠️ 部分架构 | `llama-kv-cache-{iswa,dsv4,dsa}.cpp` |
| L5 蒸馏 | ❌ 训练侧 | — |
| L6 运行时 | ✅ 完整 | mmap / `-ngl` / backend 调度 |

**L2 的重要澄清**：llama.cpp **不做激活量化训练**（无 QAT），
L2 仅指推理时把 f32 激活**即时量化**为 `q8_*` 以配合整数点积（详见 03 §7.3）。
真正的激活量化（INT8 校准）发生在 NPU 路径，属模型导出环节（见 10.3）。

### 10.3 架构驱动因素 → 层次映射

| 驱动 | 描述 | 主要影响层次 |
|------|------|-------------|
| 内存容量 | 端侧 4–16 GB，模型必须可装载 | L1 + L3 + L6 |
| 性能（延迟） | TTFT < 500 ms、decode 达交互 | L1 + L6 + 后端 kernel |
| 吞吐 | decode ≥ 交互阈值 | L1（降带宽）+ kernel 优化 |
| 功耗 | 满载发热受限 | L1 + L4 + L6 |
| 精度保持 | 退化可控 | L1（imatrix + 分层）+ L4 |
| 可移植性 | 多设备（CPU/GPU/NPU） | 多后端 + fallback |
| 可维护性 | 可复现迭代 | 参数化 CLI + dry-run + commit 记录 |
| 可靠性 | 不产出损坏模型 | 量化后校验 + imatrix 强校验 |

### 10.4 端侧部署的"组合拳"

实际端侧部署几乎从不是"只做权重量化"：

```text
权重量化（Q4_K_M）         → 权重变小
+ KV 量化（-ctk q8_0）     → 缓存变小、长上下文带宽下降
+ 稀疏注意力（若架构支持）   → 计算变少
+ mmap / offload           → 内存策略
+ batch / context 控制      → 峰值内存控制
= 可落地的端侧方案
```

### 11.2 组件 ①：模型接入

**职责**：把原始模型转换为可量化的 GGUF，并校验元数据。

**接口**
```bash
convert_hf_to_gguf.py <model_dir> --outtype f16 --outfile model-f16.gguf
```

**关键约束（已核验）**：`convert_hf_to_gguf.py` 的 `--outtype` **仅支持 7 个取值**
（`convert_hf_to_gguf.py:60`）：

```text
choices = ["f32", "f16", "bf16", "q8_0", "tq1_0", "tq2_0", "auto"]，默认 "auto"
```

**这是端侧工作流的重要架构事实**：转换阶段**只做 F32/F16/BF16 以及 q8_0/tq1_0/tq2_0**，
**其余所有量化档位（Q4_K/Q5_K/IQ 等）必须经 `llama-quantize` 二次处理**。
源文档中"转换阶段可产出任意量化档位"的暗示不准确。

**元数据校验项**：架构、层数、维度、RoPE 配置、词表。

### 11.3 组件 ②：量化参数决策

**职责**：为每个张量决定目标量化类型。这是整个系统**精度策略的落点**。

#### 11.3.1 决策为何是有状态的

量化参数决策**不是无状态的静态查询**——它依赖两类运行时状态：

| 状态类别 | 内容 | 为什么必需 |
|---------|------|-----------|
| **全局计数** | attention-v 类张量总数、`ffn_down`/`ffn_gate`/`ffn_up` 总数 | 分层规则需要知道"总共有几层"才能计算比例阈值 |
| **进度计数** | 当前已处理的 attention-v 序号、各类 FFN 序号 | 规则依赖**相对位次**（如"前两个 attn_v 用 Q5_K"） |
| **模型属性** | 是否有 imatrix、是否 tied embeddings | 影响保护策略分支 |
| **用户覆盖** | `--tensor-type` 的编译后正则列表 | 最高优先级的类型覆盖 |

**为什么需要进度计数？** 分层量化规则按"第几个/第几层"决定比特分配。
例如某 K-quant 策略下，只有前两个 `attn_v` 张量提升到 Q5_K，其余保持 Q4_K。
若无状态计数器，纯函数无法获知当前处理进度——这是决策层必须持有状态的根本原因。

**决策结果的缓存**：预遍历阶段会为每个张量计算并缓存一份元数据，
包含目标类型、张量类别、重映射后的 imatrix 键名、是否允许量化、是否强制要求 imatrix。
主遍历直接复用，**避免重复的字符串匹配与规则求值**（这是可维护性 NFR 的落点，见 §16.2）。

---

#### 11.3.2 张量白名单与敏感排除机制

**设计目标**：不是所有张量都适合量化。对敏感张量保留高精度，
能显著提升整体质量而只付出很小的容量代价。

**准入判据（按顺序）**：

```text
① 仅复制模式（COPY）→ 全部不量化
② 张量维度 < 2（1D 张量：偏置、norm 缩放因子）→ 不量化
③ 张量名必须以 "weight" 结尾
④ 通过下方的敏感排除清单
```

**敏感排除清单**（每项一个具体原因）：

| 排除张量 | 原因 | 类别 |
|---------|------|------|
| `_norm.weight` | LayerNorm / RMSNorm 的缩放因子，误差会放大到全网络 | 功能敏感 |
| `output.weight` | 输出层直接决定 logits 分布（除非 `--leave-output-tensor` 显式允许量化） | 功能敏感 |
| `ffn_gate_inp.weight` | MoE 路由门控，决定专家选择，极敏感 | 功能敏感 |
| 位置嵌入 / token_type | 位置与类型信息的载体，不可逆损失 | 结构敏感 |
| `attn_rel_b.weight` | T5 相对位置偏置 | 结构敏感 |
| `altup` / `laurel` | 极小矩阵（如 4×4），量化收益趋近于 0 但误差占比高 | 尺寸过小 |
| `per_layer_model_proj` | 体量本就不大，保留原精度更划算 | 尺寸过小 |
| `ssm_conv1d` / `shortconv.conv.weight` | Mamba / Kimi 的小型 1D 卷积核 | 尺寸过小 |
| `time_mix_*`（RWKV 系列） | RWKV 的敏感混合参数，小而关键 | 尺寸过小 + 敏感 |
| `.position_embd` / `.patch_embd` 等多模态张量 | 多模态位置编码、SAM 相关张量 | 结构敏感 |

**设计原理的三条线索**：

```text
① 功能敏感 → 排除：这些张量的量化误差会直接破坏模型能力
② 尺寸过小 → 排除：量化收益微小（占比 < 0.1%）但误差代价不低
③ 结构特殊 → 排除：位置/类型编码等非权重语义的张量
```

完整的匹配判定实现（含所有子串检查）见 [04 说明]；本文只保留排除清单这一**策略契约**。
修改该清单时应同步更新 `tests/test-quant-type-selection.cpp` 的回归断言。

#### 11.3.3 层裁剪与重编号（`--prune-layers` 的配套机制）

`--prune-layers` 可物理删除模型的指定层（用于裁剪模型深度或做消融实验），
但这引入两个**必须协调解决的问题**：

| 问题 | 后果 | 解决机制 |
|------|------|---------|
| **张量名层号不连续** | 删除第 3 层后，`blk.4` 之后的名字仍有空洞，GGUF 的 `n_layer` 与实际不符 | **层重编号**：把保留的层从前向后重排为连续序号 |
| **imatrix 键名失配** | imatrix 是在**未裁剪的原始模型**上采集的，键名用的是原始层号 | **imatrix 反查**：用重编号映射表反查出原始层号再查 imatrix |

**两条关键设计约束**：

```text
① 被裁剪的层映射为空名 → 主遍历时识别到空名即丢弃该张量（自然实现"裁剪"）
② imatrix 反查失败时必须**硬失败**（GGML_ABORT）而非静默跳过
   → 静默跳过会导致部分层用错 imatrix 或不用 imatrix，产出质量不可预期的模型
```

**端侧意义**：层裁剪与量化可以组合使用（如"砍掉 1/4 层 + Q4_K_M"），
是极端容量受限场景的补充手段。注意裁剪会改变模型能力，需重新评估质量。

#### 11.3.4 张量分类与匹配顺序陷阱

**分类的设计**：量化规则表需要按张量的**功能角色**而非精确名称来决策，
这样同一套规则可覆盖所有模型架构。分类维度包括：

```text
TOKEN_EMBD（词嵌入）        ATTENTION_Q / K / V / QKV / KV_B（注意力的各投影）
ATTENTION_OUTPUT（注意力输出投影）  FFN_UP / FFN_GATE / FFN_DOWN（前馈网络三段）
OUTPUT（输出层）            OTHER（其他）
```

**与精确张量名机制的区别**：llama.cpp 另有一套按架构生成精确张量名的工具，
但分类**刻意使用粗粒度**——因为规则表要写成"V 类比 Q/K 多给比特"，
而不是"llama 架构的第 N 层 attn_v 张量"。前者跨架构通用，后者需要为每种架构单独编写。

**⚠️ 匹配顺序陷阱（真实的实现风险）**：

分类依据张量名中的**子串匹配**。由于 `attn_qkv`（QKV 融合投影）
同时包含 `"q"` 与 `"kv"`，`attn_kv_b` 也包含 `"v"`，
因此**必须先检查更具体的模式**：

```text
正确顺序：attn_qkv → attn_kv_b → attn_v → attn_k → attn_q
错误顺序：若先检查 attn_q，则 "attn_qkv.weight" 会被误判为 ATTENTION_Q
```

**后果**：一旦分类错误，该张量会应用**错误的比特预算**（如本应作为 V 类受保护，
却被当作 Q 类降比特），导致质量退化且难以定位——因为模型仍能正常推理，
只是精度下降。

**"V 敏感性"的定义**：`ATTENTION_V`、`ATTENTION_QKV`、`ATTENTION_KV_B`
三者共享"V 类敏感"标签——它们都直接或部分承载 attention 的 value 投影。
在低 bit 量化中，这三类会获得更高比特（见 §17.3 的敏感度模型）。

#### 11.3.5 决策优先级链

类型决策按**严格的优先级顺序**执行，高优先级短路低优先级：

```text
1. 准入检查       不允许量化 → 保持原类型
2. --token-embedding-type   显式指定且张量为词嵌入 → 直接采纳
3. --output-tensor-type     显式指定且张量为输出层 → 直接采纳
4. --pure                   纯净模式 → 跳过非均匀决策，全体用 default_type
5. --tensor-type            正则覆盖 → 命中即强制覆盖（优先于规则表）
6. 非均匀分层规则表         进入核心决策（见 §11.3.6）
7. 形状兜底                 整除校验与降级（见 §15.5）
```

**为什么这样排序？** 三层控制权的划分：

| 层级 | 手段 | 控制粒度 | 适用场景 |
|------|------|---------|---------|
| **用户显式** | `--output-tensor-type` / `--token-embedding-type` | 单张量类别 | 需要精确控制特定层 |
| **用户规则** | `--tensor-type`（正则） | 任意张量集合 | 批量定制（如"所有 attn_q 用 q8_0"） |
| **用户全局** | `--pure` | 全体 | 做对照实验、排除规则干扰 |
| **内建规则** | 非均匀分层规则表 | 自动 | 默认行为，开箱即用 |

即：**用户控制始终优先于内建规则**，且越具体的控制越优先。

#### 11.3.6 非均匀分层规则

**四维决策输入**：`ftype` × 张量类别 × 层位置 × 模型架构超参
（GQA 分组数、专家数、层数、模型规模类型）。

**层位置启发式**——"哪些层值得多给比特"的判据：

```text
前 1/8 层            → 高比特（靠近输入，表示质量影响全局）
后 1/8 层            → 高比特（靠近输出，直接影响 logits）
中间段的每 3 层之 1  → 高比特（经验性的周期性加密）
其余中间层           → 可更激进量化（误差被后续层平均）
```

**设计依据**：模型的**前几层与后几层**对输出质量影响更大，给予更多比特；中间层可更激进量化。
这个 1/8 + 1/8 + 周期性 的模式是**经验调优的结果**，而非理论推导——它由回归测试固定为契约。

**关键分支的行为约定**：

```text
OUTPUT / tied TOKEN_EMBD：
  默认 Q8_0 或 Q6_K（输出层敏感）
  IQ 系列 ftype 下统一降到 Q5_K；tied embeddings 时词嵌入必须与输出层同类型

MXFP4_MOE：
  MoE 张量（ne[2] > 1）→ MXFP4
  其他张量            → Q8_0

TOKEN_EMBD：
  低 bit ftype → 提升到 Q2_K / IQ3_S / Q4_K

ATTENTION_V 类：
  给比 K/Q 更高的精度（V 更敏感）
  n_gqa() >= 4 时进一步提升（见下表）
  70B 模型因 8 head 共享 V（张量仅 1/8 大小）→ 升到 Q5_K
  n_expert == 8 → Q8_0

ATTENTION_Q / ATTENTION_K：
  IQ3_XS → IQ3_XXS；IQ3_XXS → IQ2_S
  n_expert == 8 → Q8_0

FFN_DOWN：
  分层策略，前后层更高精度（如 Q3_K_M 时前 1/16 层用 Q5_K）
  Falcon 架构有独立的层档规则

ATTENTION_QKV：
  Q3_K_M / Q3_K_L / IQ3_M → Q4_K
  Q4_K_M → Q5_K；Q5_K_M → Q6_K

FFN_GATE / FFN_UP：
  IQ3_XS 时中间层（1/8 ~ 7/8）→ IQ3_XXS
```

**关键策略速查表**：

| 策略 | 条件 | 效果 |
|------|------|------|
| GQA 增益 | `n_gqa() >= 4` | `attn_v` 从 Q3_K 提到 Q4_K（权重张量按 KV head 缩小，高 bit 代价小） |
| 70B 特判 | `model.type == LLM_TYPE_70B` | `attn_v` 的 Q3_K/Q4_K 提到 Q5_K（8 head 共享 V，张量仅 1/8 大小） |
| MoE 特判 | `n_expert == 8` | `attn_v`/`attn_k` 提到 Q8_0（"trades just ~128MB"） |
| tied embeddings | 无 `output.weight` | 词嵌入与输出层强制同类型（否则无法共享权重） |
| 首 2 层 attn_v | `Q3_K_M` | `i_attention_wv < 2` 时用 Q5_K，其余 Q4_K |
| Falcon 特判 | `arch == LLM_ARCH_FALCON` | `ffn_down` 在 Q4_K_M 下用独立档位规则 |

**核心思想**：

```text
量化不是"统一给每个张量同样 bit"，而是按张量敏感度分配 bit：
  V > Q/K 敏感
  output/norm 敏感
  前后层敏感
  expert gate 敏感
```

这种"非均匀量化"是 llama.cpp 精度损失小的关键，也是 `Q4_K_M` 优于"纯 Q4_K"的原因。

#### 11.3.7 imatrix 强制要求矩阵

哪些目标类型**强依赖** imatrix（缺失即报错终止）：

| 目标类型 | 是否强制 imatrix | 说明 |
|---------|----------------|------|
| IQ3_XXS / IQ2_XXS / IQ2_XS / IQ2_S / IQ1_M / IQ1_S | ✅ **强制** | 缺失即报错终止，不产出模型 |
| Q2_K | ⚠️ 仅当 ftype 为 `Q2_K_S` | K-quant 通常不需要 imatrix，唯一例外是 `Q2_K_S` |
| 其他所有类型 | ❌ 不强制 | 提供 imatrix 仍有精度收益 |

**两条豁免规则（重要的设计细节）**：

```text
① 词嵌入（token_embd）与输出层（output.weight）豁免强制要求
   原因：这两者在极低 bit ftype 下会被规则表提升为较高精度类型
        （如 IQ 系列 ftype 下输出层统一降到 Q5_K）
        → 它们实际不会用到"需要 imatrix 的类型"，故无需强制
② 强制判断基于**目标类型**而非 ftype
   原因：同一 ftype 下不同张量可能被提升到不同精度
        例如 IQ2_XS ftype 下，attn_v 可能被提到 Q4_K（不需 imatrix）
        而其他层仍是 IQ2_XS（需要）
```

**端侧工程含义**：若计划使用 IQ2/IQ1 档位，**必须**准备校准集并生成 imatrix，
否则量化会在预遍历阶段直接报错退出（这是"提前失败"设计，见 §15.3）。

#### 11.3.8 ftype → 默认 ggml_type 映射表

每个 ftype 都有一个**基准类型（default type）**，它是非均匀决策的起点——
规则表在此基础上按张量类别与层位置做升降：

| ftype | 默认类型 | 备注 |
|-------|---------|------|
| `ALL_F32` / `MOSTLY_F16` / `MOSTLY_BF16` | F32 / F16 / BF16 | 非量化 |
| `MOSTLY_Q1_0` / `MOSTLY_Q2_0` | Q1_0 / Q2_0 | 实验性极低比特 |

```text

ftype = IQ2_M   →  默认类型 = IQ2_S
```

**⚠️ `LLAMA_FTYPE_MOSTLY_NVFP4` 当前不可用（已核验）**：

`include/llama.h:156` 定义了 `LLAMA_FTYPE_MOSTLY_NVFP4 = 39`，但
`llama_ftype_get_default_type()`的 switch 中
**没有任何 case 处理它**，因此落入 `default: return GGML_TYPE_COUNT;`。
而量化驱动在入口处会把 `GGML_TYPE_COUNT` 视为**非法输出类型**并直接抛出异常。

**结论**：`GGML_TYPE_NVFP4` 作为**量化类型**已完整实现，
但**尚不能通过 `llama-quantize` 的 ftype 参数产出 NVFP4 模型**——
该 ftype 虽在枚举中占位，却未接入量化驱动。
端侧若需 NVFP4，目前只能经 `--tensor-type`/`--tensor-type-file` 逐张量显式指定类型来绕过。
这与源文档"NVFP4 是可选档位"的暗示不符，此处更正。

## 十二、量化目标决策：选型流程

### 12.1 七步决策流程

```text
① 明确硬件规格：内存、带宽、算力、功耗、存储
② 明确业务需求：上下文长度、并发、TTFT、tok/s
③ 确定模型：参数量、架构（是否 MLA/MoE/稀疏）
④ 计算内存预算：
     权重 + KV + 激活 + 运行时 ≤ 设备可用内存
⑤ 计算带宽预算：
     decode 需读所有权重 → 带宽需求 ≤ 设备带宽
⑥ 选择量化档位：满足 ④⑤ 且质量可接受
⑦ 实测验证：容量 / 速度 / 质量 / 功耗
```

### 12.2 内存预算公式

```text
权重内存 ≈ 参数量 × BPW / 8
KV 内存  ≈ 2 × KV层数 × n_ctx × n_embd_kv_gqa × dtype_bytes
激活内存 ≈ 受 n_batch / n_ubatch 和上下文影响的峰值
运行时   ≈ 词表矩阵、临时 buffer、workspace
```

**KV 内存的 GQA 修正很重要**：`n_embd_kv_gqa = n_embd_head_k × n_head_kv`，
而非 `n_embd`。GQA 模型（如 Qwen2.5-1.5B，`n_head=12, n_head_kv=2`）的 KV 内存
只有同规模 MHA 模型的 1/6。这直接决定了长上下文场景是否可行。

**KV 量化的收益**：

```text
F16 KV → Q8_0 KV：缓存减半
F16 KV → Q4_0 KV：缓存降至 1/4
```

### 12.3 档位选择逻辑

```text
精度优先 → F16 / Q8_0
均衡     → Q5_K_M / Q4_K_M          ← 端侧主力
内存紧张 → Q4_0 / Q2_K
极致压缩 → IQ2 / IQ1（需 imatrix）
MoE      → MXFP4
```

**端侧默认推荐 Q4_K_M 的三条理由**：

1. **Pareto 最优点**：同时受容量/带宽/功耗约束时，Q4_K_M 在 4.5–4.8 BPW 处
   提供最佳的"容量-精度"折衷（见 §14.7 对比）；
2. **kernel 覆盖最广**：CPU（全架构）、CUDA、Metal、Vulkan、SYCL 均有 Q4_K 原生 kernel；
3. **非均匀加成**：`Q4_K_M` 并非纯 Q4_K——它对 `ffn_down`/`attn_v` 的关键层自动提升到 Q5_K/Q6_K
   （见 §17.3），实际精度优于"纯 Q4_K"。

## 十三、端侧量化技术体系

### 13.1 基本原理

**对称 vs 非对称**：

```text
对称（symmetric）：
  x_q = round(x / scale)          scale = max(|x|) / (2^(b-1)-1)
  零点 = 0，实现简单，适合零均值分布

非对称（asymmetric）：
  x_q = round(x / scale) + zero_point      （或存 min 偏移）
  能覆盖非对称分布，代价是额外存储 min
```

**Block 量化（llama.cpp 核心）**：

```text
把权重分成 block（32 / 64 / 128 / 256 个元素）
每个 block 共享一个 scale（非对称时再加一个 min）
  → 局部精度高，实现简单，反量化可 SIMD 化
```

在 llama.cpp 中，block 的完整类型定义与比特预算是 03 §4 的内容；本文只保留端侧决策所需的结论。

### 13.2 算法族与端侧适用性

整合 03 §5 的分类与端侧视角：

| 族 | 代表类型 | BPW 范围 | 端侧适用性 | imatrix |
|----|---------|---------|-----------|---------|
| **经典线性** | Q8_0 / Q5_0 / Q4_0 / Q4_1 | 4.5–8.5 | ✅ kernel 最简最快，精度一般 | 可选 |
| **K-quant** | Q6_K / Q5_K / Q4_K / Q3_K / Q2_K | 2.625–6.5625 | ✅✅ **端侧主力**，精度/速度最佳平衡 | 可选（`Q2_K_S` 必需） |
| **三值** | TQ1_0 / TQ2_0 | 1.6875–2.0625 | ⚠️ 仅限 BitNet 类三值训练模型 | 否 |
| **IQ 格点** | IQ4_XS / IQ3_S / IQ2_S / IQ2_XS / IQ1_S / IQ1_M | 1.5625–4.25 | ⚠️ 极致压缩，kernel 覆盖有限 | **IQ2/IQ1 必需** |
| **非线性** | IQ4_NL / IQ4_XS | 4.25–4.5 | ✅ NL 版 kernel 覆盖好，KV cache 可用 | 可选 |
| **MX/NV FP4** | MXFP4 / NVFP4 | 4.25–4.5 | ⚠️ MoE 场景（MXFP4）；NVFP4 面向新硬件 | 否 |

**端侧三条重要提醒**：

1. **K-quant 是端侧唯一"无短板"选择**：kernel 覆盖最全（含 NPU 导出路径的参考）、
   精度/体积平衡最优、CPU 上反量化开销最低。
2. **IQ 系列的隐藏成本**：反量化需要格点查表 + 符号处理，**算力受限设备上可能反而更慢**；
   且 IQ2/IQ1 强依赖 imatrix，imatrix 质量直接决定成败。
3. **TQ 系列不是通用压缩方案**：TQ1_0/TQ2_0 只对**训练时已约束为三值**的模型有效
   （BitNet b1.58），对普通 FP16 模型强行三值量化会导致严重退化。

### 13.3 PTQ vs QAT

| 维度 | PTQ（训练后量化） | QAT（量化感知训练） |
|------|------------------|-------------------|
| 流程 | 直接量化权重 | 训练时模拟量化误差 |
| 成本 | 低（分钟~小时级） | 高（需训练资源与数据） |
| 精度（低 bit） | 受限 | 显著更好 |
| llama.cpp 支持 | ✅ 原生全流程 | ❌ 需外部工具链（如 BitNet） |

**端侧决策**：

```text
默认走 PTQ（llama.cpp 路线）
NPU 固定 INT4/INT8 算子 + 质量敏感任务 → 引入 QAT
三值模型（BitNet）→ 本身就是 QAT 产物，用 TQ1_0/TQ2_0 承载
```

### 13.4 先进量化思想参考

| 思想 | 核心原理 | llama.cpp 中的工程落地 |
|------|---------|----------------------|
| **AWQ（激活感知量化）** | 权重误差的影响被激活幅度放大，按重要性 `|a_i|` 分配步长 | imatrix 通道 + `quant_weights` 参数（见 §17.4） |
| **GPTQ（误差反馈量化）** | 按列量化，把当前列的量化误差反馈到未量化列进行补偿 | **未采用**：ggml 以行/块独立量化为主，无跨列误差反馈 |
| **SmoothQuant** | 将激活的难度迁移到权重（`W/α · X·α`），让两侧都易量化 | **未采用**：需全局变换矩阵，与块独立量化架构冲突 |
| **LLM.int8()** | 离群维度用 FP16 保留，其余 INT8 | **部分思想**：敏感张量（norm/output）不量化的策略与之同源 |
| **Hadamard 旋转** | 正交旋转 K/V 改善量化条件数 | `ggml_gen_hadamard`（正交旋转预处理，见 §13.5） |

llama.cpp 的路线是**无训练依赖的块级 PTQ + 非均匀分层 + imatrix**，
与上述学术方法相比牺牲了部分理论最优性，换取了：
零外部依赖、任意模型可量化、跨硬件复现、极简推理 kernel。

### 13.5 KV Cache 量化技术细节（L3）

**llama.cpp 支持的 KV 类型（共 9 种，已核验）**：

```text
浮点：f32, f16, bf16
整数量化：q8_0, q4_0, q4_1, q5_0, q5_1
非线性查表：iq4_nl
```

**KV 量化类型集远小于权重量化类型集**——这是**刻意的设计**，
因为 KV cache 在推理热路径上被每个 token 读写，其反量化必须极快。
被排除的类型包括：所有 K-quant（super-block 反量化开销过大）、
所有 IQ 格点（查表开销）、MXFP4/NVFP4。

**默认值**：K 与 V **均为 `f16`**（未显式指定 `-ctk`/`-ctv` 时）。

**CLI 参数**：

```bash
-ctk, --cache-type-k TYPE     # K cache 类型
-ctv, --cache-type-v TYPE     # V cache 类型
--spec-draft-type-k/-v TYPE   # 草稿模型（投机解码）的 KV 类型
```

**Flash Attention 约束（已核验）**：
当启用 FA（`flash_attn_type != DISABLED`）且 `type_k` 是量化类型时，
要求 `ggml_blck_size(type_k)` 能整除 `n_embd_head_k`，否则报错：

判据是：**`n_embd_head_k` 必须能被该量化类型的块大小整除**，
否则启用 FA 时直接报错退出，而非静默降级。

**实践建议（端侧）**：

```text
K cache：Q8_0 最常用（精度损失极小，体积减半）
V cache：Q8_0 或 Q4_0（V 对量化更敏感，Q4_0 需实测）
长上下文（≥32K）：强烈建议 KV 量化，否则 KV 内存可能超过权重
```

**关于 Hadamard**：`llama-kv-cache.cpp:20-22` 存在 `ggml_gen_hadamard`
（"orthonormal Walsh-Hadamard rotation matrix"），用于
**旋转 K/V 以改善量化条件数**（`llama-graph.cpp` 的 `llama_mul_mat_hadamard`），
是**正交旋转预处理，而非一种名为 "Hadamard" 的量化类型**。
其作用原理：K/V 在量化前先与预生成的正交 Hadamard 矩阵相乘，
把能量分散到所有通道（消除离群通道），使逐通道量化误差更均匀——
这与 SmoothQuant 的"难度迁移"思想同源，但用正交变换保证不损失信息。
源文档中"F16 KV + Hadamard 量化"的表述不准确，此处更正。

## 十四、K-Quant 深度解析（端侧主力算法）

> 本节完整迁移自 `llama-kquant-visual-guide.md`，含逐步算法详解与数字实例。
> 更深的逐行源码分析见 [04-ggml-quants源码详细分析.md](04-ggml-quants源码详细分析.md) §13。

### 14.1 为什么端侧主力是 K-Quant

K-quant 用**"大 block + 二级 scale/min + 加权最小二乘"**换取同 bit 下明显更高的精度。
相比 Q4_0 的"32 元素单 scale"，Q4_K 的额外开销仅为 12 字节 scales + 4 字节 d/dmin，
但精度提升显著——这是端侧默认选 Q4_K_M 的技术根据。

### 14.2 K-Quant 家族一览

| 类型 | 子块结构 | 量化值域 | scale 精度 | min | 有效 BPW | 端侧定位 |
|------|---------|---------|-----------|-----|---------|---------|
| Q2_K | 16 × 16 | 2 bit | 4 bit | ✅ | 2.625 | 极限压缩 |
| Q3_K | 16 × 16 | 3 bit | 6 bit | ❌（对称） | 3.4375 | 小体积 |
| Q4_K | 8 × 32 | 4 bit | 6 bit | ✅ | 4.5 | **主力** |
| Q5_K | 8 × 32 | 5 bit | 6 bit | ✅ | 5.5 | 高保真 |
| Q6_K | 16 × 16 | 6 bit | 8 bit | ❌（对称） | 6.5625 | 近无损 |

### 14.3 Q4_K 的 block 内存结构

```text
block_q4_K（144 字节 / 256 权重 = 4.5 BPW）
┌──────┬───────┬──────────────┬────────────────────────────────┐
│  d   │ dmin  │  scales[12]  │          qs[128]               │
│ 2B   │  2B   │     12B      │   256 × 4bit = 128B            │
└──────┴───────┴──────────────┴────────────────────────────────┘
   │       │           │                    │
   │       │           │                    └─ 8 个子块 × 32 元素的 4bit 量化值
   │       │           └─ 8 组 6bit scale + 8 组 6bit min（紧凑打包，零浪费）
   │       └─ 二级 min 的超级缩放（fp16）
   └─ 二级 scale 的超级缩放（fp16）
```

**8 个 32 元素子块**：每个子块有独立的 `scale` 与 `min`，
反量化为 `w ≈ dl × q - ml`，其中 `dl = d × (子块 scale 解包值)`、`ml = dmin × (子块 min 解包值)`。

**12 字节如何装下 8×(6+6) bit**：这是 `get_scale_min_k4` 的位打包设计，
96 bit 精确填满，零冗余。打包代码：

**打包策略（设计要点，而非实现）**：

```text
每个 6bit 的 scale/min 被拆成两半存储：
  低 4bit → 集中放在字节 8-11（每字节装 2 个子块的低 4bit）
  高 2bit → 进位到字节 0-7（每字节的高 2bit 位段）

字节 0-3：scale0-3 的低 6bit，高 2bit 位段留给 scale4-7
字节 4-7：min0-3   的低 6bit，高 2bit 位段留给 min4-7
字节 8-11：scale4-7 与 min4-7 的低 4bit（各占一个 nibble）
```



**`scales[12]` 完整布局**：

```text
字节 0:  scale0(低6bit) | scale4 高2bit
字节 1:  scale1(低6bit) | scale5 高2bit
字节 2:  scale2(低6bit) | scale6 高2bit
字节 3:  scale3(低6bit) | scale7 高2bit
字节 4:  min0(低6bit)   | min4 高2bit
字节 5:  min1(低6bit)   | min5 高2bit
字节 6:  min2(低6bit)   | min6 高2bit
字节 7:  min3(低6bit)   | min7 高2bit
字节 8:  scale4 低4bit  | min4 低4bit
字节 9:  scale5 低4bit  | min5 低4bit
字节 10: scale6 低4bit  | min6 低4bit
字节 11: scale7 低4bit  | min7 低4bit

即：每个 6bit 的 scale/min 拆成 [低 4bit 存字节 8-11] + [高 2bit 进位到字节 0-7]
```

**设计的三个要点**：

1. **信息密度零浪费**：12 字节 = 96 bit，恰好等于 8×(6+6) bit，无冗余位；
2. **解码可批量重排**：低 4bit 集中、高 2bit 集中，使反量化能用位运算批量还原
   （详见 [04 §5.3](04-ggml-quants源码详细分析.md)）；
3. **存在隐式顺序约束**：高位使用"或等"写入，故必须先写低位（子块 0-3）再写高位（子块 4-7）。
   实现中依赖循环从 0 递增的隐含前提——**调整循环顺序会静默产生错误结果**，
   这是该结构最需要注意的维护陷阱。

### 14.4 完整流程：一行 256 元素如何变成 block

#### 14.4.1 Step 1：整体统计

对整行 256 个权重计算两个统计量：

```text
sum_x2 = Σx²                  该行的平方和
sigma2 = 2 × sum_x2 / QK_K    2 倍均方值（乘 2 用于后续权重放大）
av_x   = sqrt(sigma2)         该行的 RMS 幅值
```

```text
示例数值（简化）：
  x = [0.1, 0.4, -0.2, 0.8, ..., 1.5]  256 个值
  sum_x2 ≈ 300
  sigma2 = 2*300/256 ≈ 2.34
  av_x ≈ 1.53

用途：av_x 是"无 imatrix 时的权重参考基准"，
     让大值获得更大权重，使量化误差按重要性分配（见 Step 2）。
```

#### 14.4.2 Step 3：scale/min 二级量化

**这是 K-quant 的核心设计**——把每个子块的浮点 scale/min 再做一次量化：

```text
输入：8 个子块的 scale[0..7]（或 mins[0..7]）——上一步的浮点结果
     8 个子块的权重和 sw[0..7]  ——供加权最小二乘使用
输出：二级超级缩放因子 d_p + Ls[0..7]（或 Lm[0..7]，各 6bit）

原理：8 个 scale 再次共享一个"超 scale" d_p，
      每个 scale 量化为 6bit (0..63)：Ls[j] = round(scale[j] / d_p)
```

```text
图形化：

  scale[0] scale[1] ... scale[7]        （8 个原始子块 scale，浮点）
     │       │            │
     └───────┴───┬────────┘
                 ▼
      ┌──────────────────────┐
      │  二级量化            │
      │  ① 极值扫描找 d_p     │
      │  ② 每个 scale → 6bit  │
      │  ③ 坐标下降再优化     │
      └──────────┬───────────┘
                 ▼
      d_p（超 scale）  +  Ls[0..7]（各 6bit）
```

**为什么必须二级量化？** 关键在 scale 数量的倍增效应。Q4_K 有 8 个子块，
每个子块需要 1 个 scale + 1 个 min：

```text
方案 A（直接存浮点）：8×fp16(scale) + 8×fp16(min) = 16 + 16 = 32 字节
方案 B（二级量化）：  2×fp16(d, dmin) + 12 字节打包的 6bit 值 = 4 + 12 = 16 字节
                      → 每 block 省 16 字节

对比 block 总量：
  方案 A: 2+2+32+128 = 164 字节 / 256 权重 = 5.125 bpw
  方案 B: 2+2+12+128 = 144 字节 / 256 权重 = 4.5   bpw
  → 省 0.625 bpw，即同精度下体积减少约 12%
```

**信息密度验证**：12 字节 = 96 bit，而 8×(6+6) = 96 bit —— **精确填满，零浪费**。
这是 K-quant 能在"尽量小的空间内"保持 scale 精度的关键设计。
`make_qp_quants` 的内部算法（极值扫描 + 坐标下降）详见 [04 §2.8](04-ggml-quants源码详细分析.md)。

#### 14.4.3 整体五步流程

```text
输入：一行 256 个 fp32 权重
   │
   ▼
┌─────────────────────────────────────────────────────────┐
│ Step 1  整体统计                                           │
│   sum_x2 = Σx²，sigma2 = 2·sum_x2/256，av_x = sqrt(sigma2) │
└───────────────────────┬─────────────────────────────────┘
                        ▼
┌─────────────────────────────────────────────────────────┐
│ Step 2  逐 32 子块加权量化（make_qkx3_quants）             │
│   权重：weights[l] = av_x + |x[l]|          （无 imatrix） │
│        weights[l] = qw[l]·sqrt(sigma2+x²)   （有 imatrix）│
│   迭代求解每个子块的 scale[j] / mins[j]                    │
└───────────────────────┬─────────────────────────────────┘
                        ▼
┌─────────────────────────────────────────────────────────┐
│ Step 3  二级量化（make_qp_quants）                         │
│   把 8 个 scale 压成 6bit → Ls[8]，并求 d_block            │
│   把 8 个 mins  压成 6bit → Lm[8]，并求 m_block            │
└───────────────────────┬─────────────────────────────────┘
                        ▼
┌─────────────────────────────────────────────────────────┐
│ Step 4  打包 scales 到 12 字节（见 §14.3 布局表）            │
│   d = fp16(d_block)，dmin = fp16(m_block)                 │
└───────────────────────┬─────────────────────────────────┘
                        ▼
┌─────────────────────────────────────────────────────────┐
│ Step 5  重量化 + 写入 4bit qs                              │
│   用**实际存储的** d/dmin/scales 重新计算 L，再交错打包     │
└─────────────────────────────────────────────────────────┘
```

**Step 5 的"重量化"是精度的关键**：Step 2 得到的最优 `L` 基于**浮点** scale，
但最终存储的是 fp16 + 6-bit 截断后的值。若不重新量化，
编码与解码会使用不同的 scale，引入额外误差。04 §5.1 展示了这一模式。

### 14.5 子块加权量化算法（Step 2 核心）

> **本节定位**：说明"为什么这样设计"。
> `make_qkx3_quants` 的逐段代码走读见 [04 §2.7](04-ggml-quants源码详细分析.md)。

#### 14.5.1 优化目标：非对称线性模型

量化不是把最大/最小值等分，而是寻找一个**非对称线性模型**并最小化加权误差：

```text
拟合模型：x[i] ≈ min + scale × L[i]

目标函数：
  E(scale, min, L) = Σᵢ w[i] × (min + scale×L[i] - x[i])²

其中：
  x[i]  = 原始浮点权重
  L[i]  = 4bit 整数，0..15（离散变量）
  scale = 子块步长（连续变量）
  min   = 子块偏移，通常 ≤ 0（连续变量）
  w[i]  = 权重（imatrix 或启发式）
```

**三个变量的性质决定了算法结构**：

| 变量 | 类型 | 求解方式 |
|------|------|---------|
| `L[i]` | **离散**（0..15） | 给定 scale/min 后取整即可 |
| `scale` | 连续 | 给定 `L` 后有闭式解（最小二乘） |
| `min` | 连续（带约束 ≤ 0） | 同上有闭式解 |

**离散与连续混在一起 → 无法直接求导 → 必须采用交替优化**。

#### 14.5.2 加权机制（设计核心）

权重的来源决定了量化误差如何分配：

| 场景 | 权重公式 | 设计意图 |
|------|---------|---------|
| **无 imatrix** | `av_x + \|x[l]\|` | RMS 基准 + 自身幅度：让大权重误差惩罚更大 |
| **有 imatrix** | `qw[l] × √(sigma2 + x²)` | 激活重要性 × 自身显著度 |

两条公式都遵循**同一设计原则**：

```text
w 越大 → 该元素的量化误差代价越大 → 算法倾向让它落入更精确的位置
w 越小 → 允许更大误差 → 可以"牺牲"它换取整体的更优解
```

**关键澄清**：加权**不是**给某个元素更多比特（4bit 是固定的），
而是**调整整个子块的量化网格**（scale/min），使重要元素恰好落在网格上更准的位置。
这是一种"零额外存储成本"的精度优化——网格参数本来就要存。

````text
直觉示例（4 个数、2bit 示意）：
  原始 x = [0.10, 0.40, 0.80, 1.00]
  权重 w = [1, 1, 1, 10]          ← 最后一个值最重要

  优化时 10 倍权重使算法优先保证 1.00 的精度，
  代价是前几个不重要元素的误差略增——这正是期望的行为。
````

#### 14.5.3 算法结构：五阶段

`make_qkx3_quants` 采用**"扫描候选尺度 + 交替优化"**的结构，可分五个阶段：

```text
┌─ 阶段 1：扫描统计
│    求 min/max 得到初始覆盖范围；若全部为正则把 min 钳到 0
│    退化保护：max ≤ min（全零块）→ 直接输出全零码，返回 scale=0
│
├─ 阶段 2：生成初始解
│    iscale = nmax / (max - min)，量化全部元素得到初始 L
│    计算初始加权误差作为基准
│
├─ 阶段 3：候选尺度扫描           ← 避免陷入初始解的局部最优
│    在 [nmax+rmin, nmax+rmin+nstep×rdelta] 范围内扫描多个候选尺度
│    （Q4_K 用 rmin=-0.9, rdelta=0.05, nstep=36 → 扫 36 个候选）
│
├─ 阶段 4：给定 L，闭式求最优 scale/min     ← 交替优化的"连续"一步
│    加权最小二乘解：
│      scale = (Σw·ΣwLx − Σwx·ΣwL) / D
│      min   = (ΣwL²·Σwx − ΣwL·ΣwLx) / D
│      D     = Σw·ΣwL² − (ΣwL)²
│    带约束投影：若解出 min > 0，则固定 min = 0 退化为单参数解
│
└─ 阶段 5：误差比较与提交
     用候选参数重算加权误差，**严格更优才提交**
     → 保证搜索过程单调不劣化
```

**设计要点的三条线索**：

| 设计 | 解决的问题 |
|------|-----------|
| **候选尺度扫描**（而非只用初始解） | 初始 `iscale` 由 `max` 决定，而 `max` 可能受单个离群值影响 → 扫描可跳出 |
| **闭式最小二乘**（而非梯度下降） | 固定 `L` 后问题退化为线性回归，有解析解 → 无需迭代、无收敛问题 |
| **约束投影 min ≤ 0** | block 解码约定要求 min 非正（零点在范围上界） → 违反时投影回可行域 |

**`D ≤ 0` 的处理**：`D` 是正规方程的行列式。若 `D ≤ 0`，
说明当前量化码没有足够变化（如全部映射到同一值），无法稳定求解 → 跳过该候选。

#### 14.5.4 算法本质与数学结论

**本质是交替优化，而非"先算 scale 再结束"**：

```text
给定 scale/min → 求离散 L（round + clamp）
给定 L         → 求连续 scale/min（加权最小二乘闭式解）
给定新 scale/min → 再求新 L
重复扫描候选，保留误差最小方案
```

它同时处理了四件事：4bit 离散码的取整误差、非对称范围的 min 偏移、
不同通道的相对重要性、scale/min 本身的最佳拟合。

**数学结论**：

$$\min_{L,\, scale,\, min} \; \sum_i w_i \,(min + scale \cdot L_i - x_i)^2
\quad \text{s.t.} \quad L_i \in \{0,...,15\},\; min \le 0,\; scale > 0$$

采用"离散 `L` + 连续 `scale/min`"的交替搜索近似求解。
完成后，Q4_K 上层再将 8 个子块的 scale/min 做二级量化，最终打包进 `block_q4_K`。

#### 14.5.5 子块量化完整流程图

```text
32 个 float x[0..31]
  │
  ├─ 扫描 min/max
  ├─ 构造 weights（imatrix 或启发式）
  │
  ▼
初始网格：min + scale×[0..15]
  │
  ▼
候选尺度循环（Q4_K 共 36 个候选）
  │  ├─ 用候选尺度生成 Laux[0..31]
  │  ├─ 计算 Σw、ΣwL、ΣwL²、ΣwLx
  │  ├─ 闭式求 this_scale / this_min
  │  ├─ 计算加权误差
  │  └─ 误差更小 → 提交 L / scale / min
  │
  ▼
输出：
  L[32]        每个 0..15（4bit）
  scale        子块 scale
  min          子块 min（以 -min 输出）
```

### 14.6 数字实例：一个 256 元素行完整走一遍

以无 imatrix 的 Q4_K 为例（综合 `llama-kquant-visual-guide.md` §9）：

```text
输入
  子块0: [0.10, 0.35, -0.20, 0.80, ...]（32 个）
  子块1: [1.20, -0.50, ...]  ...  子块7: [...]

Step 1  整体统计
  sum_x2 ≈ 300 → sigma2 ≈ 2.34 → av_x ≈ 1.53

Step 2  子块 0 加权量化
  weights[0..31] = 1.53 + |x| = [1.63, 1.88, 1.73, 2.33, ...]
  make_qkx3_quants 迭代得 scale[0] ≈ 0.12，min[0] ≈ 0.05
  反量化校验： 0.05 + 0.12×1 = 0.17 ≈ 0.10   （q=1）
              0.05 + 0.12×3 = 0.41 ≈ 0.35   （q=3）
              0.05 + 0.12×0 = 0.05 ≈ -0.20  （q=0，min 兜底）
              0.05 + 0.12×6 = 0.77 ≈ 0.80   （q=6）
  L[0..31] = [1, 3, 0, 6, ...]

Step 3  二级量化
  scales = [0.12, 0.15, 0.09, 0.13, ...]（8 个）
  mins   = [0.05, -0.02, 0.08, 0.01, ...]（8 个）
  d_block ≈ 0.015 → Ls = [8, 10, ...]      （round(0.12/0.015)=8）
  m_block ≈ 0.010 → Lm = [5, ...]          （round(0.05/0.010)=5）

Step 4  打包
  scales[12] 按布局填充；d = fp16(0.015)；dmin = fp16(0.010)

Step 5  写 qs
  qs = [1|(3<<4) = 0x31, 0|(6<<4) = 0x60, ...]  共 128 字节
```

**注意 `min` 的存在使量化支持非对称**（负值也能表示），这与 Q4_0 的纯对称量化本质不同。
实例中的 `-0.20 → q=0` 正是 `min` 兜底能力的体现。

### 14.7 Q4_K vs Q4_0：端侧选型对比

```text
Q4_0（block=32，对称）                     Q4_K（block=256，非对称 + 二级）
┌──────────────────────┐ ┌──────┐         ┌────┬────┬───────┬──────────────┐
│ 32×4bit 权重 (16B)   │ │scale │         │ d  │dmin│scales │ qs (128B)    │
└──────────────────────┘ └──────┘         │ 2B │ 2B │ 12B   │              │
每 32 元素 1 个 fp16 scale                └────┴────┴───────┴──────────────┘
无 min（对称）                            8 个 32 元素子块，各自 scale/min
                                         scale/min 二级量化（6bit）→ 12 字节
                                         支持 imatrix 加权
```

| 项目 | Q4_0 | Q4_K |
|------|------|------|
| block 大小 | 32 | 256（8×32 子块） |
| scale | 每块 1 个 fp16 | 二级量化 + 超级 scale |
| min | 无（对称） | 有 dmin（非对称） |
| 加权 | 无 | 有（含 imatrix） |
| 精度 | 较低 | 同 bit 更高 |
| kernel 复杂度 | 简单快 | 复杂 |
| 反量化开销 | 极低 | 低（但需解包 scales） |
| **端侧推荐** | 内存极度紧张 / 老硬件 | ✅ **主力（Q4_K_M）** |

**决策规则**：除非设备内存极端受限或后端 kernel 不支持 K-quant，
否则端侧应优先选择 K-quant 系列。Q4_K_M 相比 Q4_0 的额外容量开销很小，
但精度收益显著。

### 14.8 反量化流程

**还原语义**（概念式，非实现）：运行时读取 `block_q4_K` 还原近似的 float 值。
关键的工程事实是——**推理并不执行这个反量化过程**（见下文"注意"）。


```text
还原公式：  w ≈ dl × q - ml
            dl = d × (子块 scale 解包值)
            ml = dmin × (子块 min 解包值)

图形化（一个子块）：
  qs[]:  [4bit][4bit][4bit]...
            │     │     │
            ▼     ▼     ▼
        × dl   × dl  × dl      （子块 scale）
            │     │     │
            ▼     ▼     ▼
          - ml   - ml  - ml     （子块 min）
            │     │     │
            ▼     ▼     ▼
        近似 float 值（供整数点积使用）

注意：实际推理**不做**这个反量化到 FP32 的过程，
     而是用整数点积（q4_K × q8_K）直接算结果（见 03 §7）。
     此处的反量化仅用于：① 量化时的重量化校验；② to_float 回退路径。
```

| `general.quantization_version` | `GGML_QNT_VERSION`，量化格式版本号 |
| 各张量 `name` / `type` / `shape` / `offset` | 张量描述符（GGUF info 段） |
| 架构 K/V metadata | `n_layer`、`n_embd*`、`n_head*`、`n_swa`、`n_expert`、`rope_type`、`mla_impl`、`indexer_head_size` 等 |

**顺序约束**

```text
① 张量数据段按 GGUF 规范顺序排列（由 gguf_add_tensor 的调用顺序决定）
② --keep-split 时按 (split_idx, offset) 排序，保证分片连续性
```

**完整性与一致性约束**

```text
① 张量类型必须与 ggml_blck_size 兼容（ne[0] % blck_size == 0）→ 否则触发 fallback（§15.5）
② 量化后必须满足 gguf_get_tensor_size(...) == gguf_set_tensor_data 的 size
   → 实现层有断言强制校验，尺寸不符即失败
③ 数据段写入后按 GGUF_DEFAULT_ALIGNMENT 补齐 padding（zeros() 写零）
④ 输出文件删除 split 元数据（除非 --keep-split），避免分片信息不一致
```

#### 15.2.2 实体：imatrix（重要性矩阵）

**属性**：`张量名 → 每行重要性（float 数组）`

**约束（源码级强制）**

```text
① size == tensor->ne[0] * tensor->ne[2]
   → 即"每行"重要性 × expert 数（MoE 每个 expert 一份独立 imatrix，见 §15.3）
② 必须是有限浮点数：NaN / Inf 直接 throw
   → imatrix 载入时逐个检查所有元素
③ 尺寸不匹配时的行为：对多数张量直接 throw，仅放过 token_embd
   → 尺寸不匹配时直接报错终止
```

**尺寸不匹配的处理为何如此严格？** 源码注释给出了答案：

> "this is a significant error and it may be good idea to abort the process if this happens,
> since many people will miss the error and not realize that most of the model is being
> quantized without an imatrix"

即：静默降级为"无 imatrix 量化"会产出质量明显更差的模型，而用户往往不会察觉。
**只对 `token_embd` 豁免**是因为它在极低 bit ftype 下总会被特殊处理，
尺寸天然不匹配（这是已知且无害的情形）。

#### 15.2.3 实体关系（数据流视角）

```text
      ┌──────────────┐
      │  原始模型     │  architecture / n_layer / n_embd / n_head_kv / n_expert
      └──────┬───────┘
             │ 决定
             ▼
      ┌──────────────┐        ┌─────────────────┐
      │   张量        │◄───────│  imatrix        │
      │ name/shape   │  按名   │ name → float[]  │
      │ category     │  匹配   │ size=ne0*ne2    │
      │ target_type  │        └─────────────────┘
      │ allows_quant │
      │ requires_im  │◄─────── ftype（决定强制要求，见 §11.3.7）
      └──────┬───────┘
             │ 逐张量量化
             ▼
      ┌──────────────┐
      │  量化产物     │  GGUF + per-tensor type + BPW / quant size
      └──────────────┘
```

### 15.3 预遍历的设计价值

**⑦ 预遍历是整个架构中"提前失败"原则的体现**：

```text
预遍历做完所有类型决策与 imatrix 需求检查，
在**尚未写出任何数据**时就发现：
  - 某张量需要 imatrix 但未提供 → throw（而非产出半成品）
  - --dry-run 时则记录 will_require_imatrix 并在结尾告警
```

这比"边量化边发现"安全得多——端侧模型量化可能耗时数十分钟到数小时，
提前失败避免浪费。

### 15.4 并行量化与分块策略

**分块模型**：量化以**张量**为调度单位，张量内部再按**行**切分为 chunk 并行处理。

```text
张量（例如 4096 × 4096）
  │
  ├─ 分块参数：
  │    chunk_size  = max(n_per_row, 16384 元素)   ← 下限保证线程有足够工作量
  │    nchunk      = ceil(ne[0]*ne[1] / chunk_size)
  │    nthread_use = min(用户线程数, nchunk)      ← 线程数不超过 chunk 数，避免空转
  │
  ├─ 工作窃取调度：counter += nrows_per_chunk（互斥锁保护）→ 天然负载均衡
  │
  └─ MoE 特殊处理：按 ne[2]（expert 维度）**外层再切一层**
       → 每个 expert 独立量化，各自使用其专属的 imatrix 切片
```

**三个设计点的由来**：

| 设计点 | 取值 | 原因 |
|--------|------|------|
| chunk 下限 | 16384 元素 | 小张量上线程调度开销可能超过并行收益 |
| 线程数上限 | `min(nthread, nchunk)` | 无此约束时多余线程会空转等待 |
| expert 维度独立 | `ne[2]` 循环 | MoE 每个 expert 有独立 imatrix，不能混合 |

**expert 切分的连带影响**：这决定了量化分块接口的 `imatrix` 长度约定为
`n_per_row × ne[2]`——即 imatrix 是**按 expert 分片**存储的（见 03 §7.1）。

**量化后的即时校验（内建契约）**：

每个 chunk 量化完成后**立即**校验，而非等到全部结束：

```text
校验失败 → 置 valid=false → 抛出 "quantized data validation failed"
         → **不写出任何损坏的 GGUF**
```

校验是**量化的内建契约**而非可选诊断。这是可靠性 NFR 的关键落点（见 §16.2）：
与其产出一个"能加载但输出乱码"的模型，不如在量化阶段直接失败。
校验的完整实现见 [04 §10](04-ggml-quants源码详细分析.md)。

### 15.5 形状兜底（fallback）机制

量化类型要求 `ne[0] % blck_size == 0`。当张量形状不兼容时：

| 目标类型（块 256/128/64） | 兜底类型（块 32） |
|--------------------------|------------------|
| IQ1_S / IQ1_M / IQ2_XXS / IQ2_XS / IQ2_S / IQ3_XXS / IQ3_S / IQ4_XS | IQ4_NL |
| Q2_0 / Q2_K / Q3_K / TQ1_0 / TQ2_0 | Q4_0 |
| Q4_K | Q5_0 |
| Q5_K | Q5_1 |
| Q6_K | Q8_0 |
| 若兜底类型仍不整除（极罕见，`ne[0]` 不被 32 整除） | **F16**（并告警） |

**关键点**：兜底目标是**块大小 32 的类型**（几乎总能整除），并按"比特预算不大幅下降"选择。
`qs.n_fallback` 计数器会在结束时汇总：

```text
WARNING: N of M tensor(s) required fallback quantization
```

**端侧含义**：出现 fallback 意味着部分张量**实际 BPW 高于预期**，模型体积会比 dry-run 估算略大。
`--dry-run` 会正确统计 fallback（因为它走同一条决策链），故估算仍然可靠。

### 16.2 关键 NFR 的实现详解

**性能（NFR-002 / NFR-003）**

```text
① 带宽优化：decode 是带宽受限 → 降低权重 BPW 直接降带宽
② 多线程：量化与推理均支持（llama-quantize <nthreads>、llama-cli -t）
③ offload：GPU 层 -ngl，NPU 专用算子
④ workspace/图复用：graph buffer 复用
⑤ 预热与重复：bench 需 warmup + 多次（P50/P95）
⑥ KV 量化：长上下文场景下 attention 读 KV 的带宽大幅下降
```

**可靠性（NFR-008）**

```text
① 量化后 ggml_validate_row_data 校验，失败即抛异常（不写文件）
② imatrix 缺失或含非有限值即报错
③ GGUF 写出校验 tensor_size 一致
④ require_imatrix 在 --dry-run 时也标记，避免误以为会成功
⑤ 预遍历提前失败，不产出半成品
```

```text

② struct tensor_type_option 与 tools/quantize/quantize.cpp 保持同步
③ 预遍历缓存 tensor_metadata，避免重复的字符串匹配
④ llama_model_quantize_default_params() 明确默认值
⑤ tests/test-quant-type-selection.cpp 把决策规则固化为回归契约
```

**`test-quant-type-selection.cpp` 值得单独强调**：`llama_tensor_get_type_impl`
是一张 ~120 行的经验规则表（涉及 ftype × 类别 × 层号 × 超参的四维组合），
任何重构都可能**静默改变**输出模型质量。该测试把决策固化为可断言的契约，
是这个模块能够被安全修改的基础设施。端侧团队在定制量化策略时，
应同步更新该测试。

## 十七、精度工程：敏感度模型与保护策略

> 本节整合 `llama-quant-analysis.md` §13.4 的敏感度分析，并映射到具体代码策略。

### 17.1 误差来源

```text
① 权重截断：低 bit 表示不了原值
② scale/zero-point 量化：block 内共享统计量的近似
③ 二级量化：K-quant 的 scale 自身被量化（引入第二层误差）
④ 反量化往返：编码与解码使用不同 scale（靠"重量化"消除，见 §14.4 Step 5）
```

**误差来源的层次结构**（对应 block 的两级设计）：

```text
┌─ 超级缩放 d / dmin（fp16 截断误差）
│  └─ 子块 scale / min（6-bit 或 4-bit 截断误差）
│     └─ 量化值 q（4-bit 取整误差）
│        └─ 反量化：w ≈ d × scale × q - dmin × min
```

**各级误差量化的经验规律**：

| 量化强度 | 典型精度影响 | 主因 |
|---------|-------------|------|
| Q8_0 | 质量几乎无损 | 8-bit 取整误差极小 |
| Q5_K / Q4_K_M | 轻微损失，可用 | 4-5 bit 取整 + 子块 scale 误差 |
| Q4_0 | 可见损失 | 32 元素单 scale，无 min，无加权 |
| IQ2 / IQ1 | 明显损失，需 imatrix | 极低 bit 下格点近似 + 需重要性引导 |

**典型精度影响是经验值而非绝对保证**——必须对目标模型与业务做实测（§19）。

### 17.2 张量敏感度排序

```text
输出层 > 归一化层 > V  >  Q/K  >  FFN
前几层 / 后几层  >  中间层
```

这个排序由**两条独立的经验规律**叠加而成：

1. **功能敏感度**：输出层直接决定 logits 分布；norm 层的缩放误差会放大到全网络；
   V 参与 attention 加权求和（误差直接进入上下文）。
2. **位置敏感度**：首尾层的表示更接近输入/输出空间，误差不易被后续层"平均掉"。

### 17.3 代码中的保护落点

| 保护策略 | 代码位置 | 具体表现 |
|---------|---------|---------|
| **不量化敏感张量** | `tensor_allows_quantization` | `_norm.weight`、1D 张量、`ffn_gate_inp.weight`、`per_layer_model_proj`、位置嵌入、`ssm_conv1d`、RWKV time_mix 系列、多模态位置编码 |
| **层位置分层** | `use_more_bits` | 首尾 1/8 层 + 每 3 层第 3 层提比特 |
| **V 类提比特** | `category_is_attn_v` 分支 | GQA≥4 时 Q3_K→Q4_K；70B 时 Q4_K→Q5_K |
| **输出层保护** | `OUTPUT` 类别分支 | IQ 系列 ftype 下输出层统一降级到 Q5_K，其余降到 Q6_K |
| **输出/tok_embd 显式控制** | `--output-tensor-type` / `--token-embedding-type` | 用户可强制类型 |
| **tied embeddings 一致性** | `has_tied_embeddings` | 词嵌入与输出层必须同类型（否则无法共享权重） |
| **imatrix 加权** | `quant_weights` 参数 | 极低 bit 时按激活重要性分配误差 |
| **形状兜底** | `tensor_type_fallback` | 保证不因形状失败，代价是局部 BPW 上升 |

### 17.4 imatrix：端侧精度工程的核心手段

**数学含义**：权重的量化误差对输出的影响被激活幅度放大：

$$\text{Error} \propto \sum_i \left( |a_i| \cdot (w_i - \hat w_i) \right)^2$$

因此 `w_i` 的量化步长应按重要性 `|a_i|` 分配。
llama.cpp 将 imatrix 值与"自身显著度"（√(块方差 + 元素幅度²)）相乘作为加权系数，
第二项避免 imatrix 在某些通道过小时完全忽略权重幅度。
融合公式与代码位置见 [04 §8.1](04-ggml-quants源码详细分析.md)。

**端侧使用建议**：

```text
① Q4_K_M 及以上：imatrix 是"可选优化"，收益 1-3% PPL
② Q3_K / Q2_K：imatrix 收益显著，建议启用
③ IQ2 / IQ1：imatrix **必需**（缺失即报错），且质量与此强相关
④ imatrix 的校准集应匹配目标业务域（车机 → 车载对话语料；翻译 → 平行语料）
```

**imatrix 生成**：

```bash
llama-imatrix -m model-f16.gguf -f calibration.txt -o imatrix.gguf
# 支持增量续算：--in-file 追加已有 imatrix
# 输出格式：--output-format {gguf,dat}，默认 gguf
```

**关键约束（源码级）**：imatrix 按张量名索引，
且要求 `size == tensor->ne[0] * tensor->ne[2]`。
尺寸不匹配时对多数张量**直接 throw**（仅放过 `token_embd`），
注释解释了原因："many people will miss the error and not realize that most of the model
is being quantized without an imatrix"。

## 十八、部署架构：CPU / GPU / NPU 三端

### 18.1 三端对比矩阵

| 维度 | CPU | GPU | NPU |
|------|-----|-----|-----|
| **主要瓶颈** | 带宽 | 显存 / 带宽 | 算子支持 |
| **量化类型支持** | 全部（Q/IQ/MXFP4/NVFP4/TQ） | 主流（K 型 + 经典 + IQ） | INT8 / INT4（固定） |
| **典型 kernel** | ggml AVX2/AVX512/NEON | CUDA / Metal / Vulkan | 厂商专用算子 |
| **QAT 需求** | 无 | 通常无 | **建议**（INT4 低 bit） |
| **校准需求** | 低 | 中 | **高**（激活量化） |
| **功耗优势** | 中 | 中 | **最高** |
| **推荐档位** | Q4_K_M / Q8_0 | Q4_K_M / Q5_K_M | INT8 / INT4 + QAT |
| **llama.cpp 接入** | 原生 | 原生（`-ngl`） | 需导出（ONNX/专用格式） |

### 18.2 CPU 端部署

**特点**：CPU 是**唯一支持全部量化类型**的后端。带宽受限，decode 性能与 BPW 强相关。

**构建**：

```bash
# x86（AVX2/AVX512）
cmake -B build -DGGML_NATIVE=ON
# ARM（手机/车机）
cmake -B build -DGGML_NATIVE=ON -DCMAKE_TOOLCHAIN_FILE=<android/linux toolchain>
```

**选型建议**：

```text
内存充足 → Q5_K_M / Q6_K
均衡     → Q4_K_M       ← 推荐
内存紧张 → Q4_0（如果设备较老，Q4_0 的 kernel 更成熟）
极致压缩 → Q2_K / IQ4_XS（后者无需 imatrix 也能工作）
```

**优化措施**：

```text
① -DGGML_NATIVE=ON 启用本机指令集
② 线程数 = 物理核心数（超线程通常无益，因为带宽受限）
③ mmap 加载（Linux/Windows 显著提升；macOS 可能反而变慢——代码中对此有明确区分）
④ 运行期 repack（见 03 §10.3）：把 q4_0/q4_K 重排为 SIMD 友好布局
⑤ 优先选择 repack 支持的类型（q4_0/q4_K/q2_K/q5_K/q6_K/iq4_nl/mxfp4/q8_0）
```

**mmap 的平台差异**：llama.cpp 在量化工具中对 mmap 的启用是按平台硬编码的——
**Linux 与 Windows 启用（热缓存下显著加速），其他平台（含 macOS）禁用**，
源码注释指出 macOS 上可能因内存管理策略反而变慢。
推理时的 mmap 另由 `llama_model_params.use_mmap` 控制，端侧应针对平台实测。

### 18.3 NPU 端部署（与 CPU/GPU 本质不同）

**核心差异**：NPU 不接受任意 GGUF 量化类型，而要求**固定的 INT8/INT4 算子**。
因此 NPU 路径是"**导出 → 转换 → 校准 → 编译**"的四步流程，而非直接加载 GGUF。

```text
┌──────────────────────────────────────────────────────────────┐
│  NPU 量化流程（区别于 CPU/GPU）                                │
│                                                                │
│  ① 导出：GGUF/权重 → ONNX（或厂商中间格式）                     │
│       ⚠️ 不支持算子会在此阶段暴露，需提前做算子清单核对          │
│                                                                │
│  ② 转换 + 量化：厂商工具链（QNN / RKNN / Vela / TensorRT）      │
│       - 权重量化：INT8 / INT4（对称/非对称由硬件决定）           │
│       - 激活量化：需**校准集**（这是 NPU 相对 CPU/GPU 的额外成本）│
│       - 算子融合与图优化                                        │
│                                                                │
│  ③ 校准：用代表性数据跑前向，统计激活范围                         │
│       - 校准集质量直接决定精度                                   │
│       - 若精度不达标 → 引入 QAT（需重训）                        │
│                                                                │
│  ④ 编译 + 加载：生成设备可执行格式，端侧推理                     │
│       - 算子缺失 → 回退 CPU（混合执行）                         │
└──────────────────────────────────────────────────────────────┘
```

**典型工具链**：

| 厂商 | 工具链 | 目标硬件 |
|------|--------|---------|
| Qualcomm | QNN / SNPE | 骁龙手机/车机 |
| Rockchip | RKNN | RK 系列嵌入式 |
| NVIDIA | TensorRT | 车规 Jetson |
| Arm | Ethos-U / Vela | Cortex-M/A + Ethos NPU |

**NPU 注意事项**：

```text
① 量化类型固定：无法自由选择 Q4_K_M / IQ2_XS，只有 INT8/INT4
② 需激活校准：额外的数据与流程成本
③ 算子覆盖是最大风险：动态 shape、特殊 attention 可能不支持
④ 混合执行：NPU + CPU 分区，需关注跨设备数据传输开销
⑤ llama.cpp 生态与 NPU 工具链之间存在"格式断层"，需专门导出环节
```

### 18.4 热切换与降级策略

```text
高内存 / 低负载        → 高精度档位（Q8_0 / Q5_K_M）
低内存 / 高温 / 低电量  → 低 bit 档位（Q4_K_M / Q4_0）
失败 / 超时            → 降级到更低档位或纯 CPU 模式
```

**实现前提**：预置多个档位的模型文件（见 §18.5 数据与模型分发），
运行时按设备状态与实测性能选择。

### 18.5 数据与模型分发

```text
① 模型分档位打包（含词表、chat template、KV 配置）
② 版本 + commit + 量化参数哈希做一致性校验
③ 差分更新（以低 bit 档位为主）
④ 端侧首启校验：加载后校验 tensor 类型与元数据，不匹配则拒绝
```

## 十九、质量与性能评估体系

### 19.1 评估指标

| 类别 | 指标 | 工具 | 端侧门限（示例） |
|------|------|------|-----------------|
| 质量 | 困惑度 PPL | `llama-perplexity` | 相比 F16 退化 < 5% |
| 质量 | 任务指标（问答/摘要/代码） | 业务测试集 | 业务定义 |
| 质量 | 逐张量 RMS 误差 | `tests/test-quantize-stats` | 定位异常张量 |
| 性能 | prompt tok/s（prefill） | `llama-bench -p` | — |
| 性能 | decode tok/s | `llama-bench -n` | ≥ 交互阈值（如 10–20 tok/s） |
| 性能 | TTFT | 端侧实测 | < 500 ms |
| 资源 | 峰值内存（RSS） | 设备侧监测 | ≤ 设备可用 |
| 资源 | 模型文件体积 | `ls -l` / `--dry-run` | ≤ 安装预算 |
| 功耗 | 平均/峰值功耗、温度 | 设备侧功耗仪 | 满载 ≤ 热限 |

### 19.2 端侧专项评估

```text
① 长上下文质量：KV 量化 + 长 ctx 下的质量退化（易被忽略，误差会累积）
② 首字延迟 TTFT：包含模型加载 vs 已加载两种场景
③ 峰值内存：权重 + KV + 激活 + 运行时工作区
④ 功率/温度：需在满载稳定后测量（而非启动瞬间）
⑤ 持续运行：长时间 decode 的热降频与内存泄漏
⑥ 并发场景：llama-server 多请求下的内存峰值
⑦ 低电量/高温状态：热切换与降级是否正确触发
⑧ 多语言 / 长尾 token：极低 bit 对稀有 token 影响显著更大
```

### 19.3 评估流程

```text
① 建校准集（与部署分布接近）
② 建测试集（含质量 + 性能两类）
③ 建立基线：F16 模型跑 PPL + 任务集，记录数值
④ 逐档位量化：Q8_0 → Q5_K_M → Q4_K_M → Q2_K → IQ 系列
⑤ 全部跑评估：所有档位的 PPL/任务指标 vs 基线
⑥ 性能实测：目标设备跑 llama-bench，记录 tok/s / 内存 / 功耗
⑦ 画"质量 vs 容量/速度/功耗"权衡图
⑧ 决策：在满足质量门限的档位中选性能最优者
⑨ 记录：commit + 量化参数 + 硬件元数据 + 报告
```

**评估手段的四个层次**：

| 手段 | 作用 | 局限 |
|------|------|------|
| 困惑度 PPL | 通用质量指标，可批量对比 | 对任务能力坍塌不敏感 |
| 任务指标 | 问答/摘要/代码/翻译（BLEU/COMET 等） | 需构造业务测试集 |
| 对比测试 | F16 vs 各档量化，逐一对照 | 人力成本高 |
| 主观评估 | 抽样对比输出 | 无法自动化 |

**重要实践**：评估必须包含**主观输出对比**（而非仅 PPL）。
低 bit 量化在 PPL 上可能只有轻微退化，但在特定任务（如长链推理、代码生成）上
可能出现明显的能力坍塌。

### 19.4 llama.cpp 的十项综合措施（总览）

把本文各章所述的机制汇总为一张"问题 → 措施"映射表，
这是 llama.cpp 能在低 bit 下保持可用质量的完整手段清单：

| # | 措施 | 解决的问题 | 本文对应章节 |
|---|------|-----------|-------------|
| 1 | **丰富的量化类型**（27 种可用，1.0–8.5 BPW 全谱系） | 不同精度/容量档位需求 | §13.2 |
| 2 | **非均匀/分层量化**（V 类、前后层、敏感张量更高 bit） | 统一低 bit 的质量损失 | §11.3.6、§17.3 |
| 3 | **重要性矩阵 imatrix**（按激活幅度加权） | 极低 bit 下的通道级误差分配 | §17.4 |
| 4 | **张量白名单/黑名单**（norm/output/gate/conv1d 排除） | 敏感或极小张量被错误量化 | §11.3.2 |
| 5 | **形状回退**（逐级降级至块 32 类型乃至 F16） | 任意模型的形状兼容性 | §15.5 |
| 6 | **dry-run 与预遍历**（先决策后执行） | 提前发现 imatrix 缺失等致命问题 | §15.3 |
| 7 | **多线程与 mmap**（按 row 分块并行；Linux/Win 启用 mmap） | 量化耗时与加载延迟 | §15.4、§18.2 |
| 8 | **与 KV Cache 量化联动**（权重 + KV + 旋转） | 端侧长上下文的内存与带宽 | §13.5、§18.2 |
| 9 | **混合精度与 MoE 特化**（MXFP4 for experts，关键层高 bit） | 稀疏大模型的容量压力 | §11.3.6 |
| 10 | **验证与回滚**（行数据校验 + 失败即抛异常） | 不产出损坏模型 | §16.2、§15.4 |

**方案间的协同关系**（不是十个独立手段，而是三层组合）：

```text
第一层：载体能力 —— 措施 1（类型谱系）
第二层：精度策略 —— 措施 2、3、4、9（非均匀 + 加权 + 排除 + 特化）
第三层：工程保障 —— 措施 5、6、7、10（回退 + 预检 + 并行 + 校验）

端侧部署在此之上叠加：措施 8（KV 量化联动）
```

### 19.5 五维权衡视图

量化越激进（BPW 越低）的后果可归纳为五个维度：

```text
容量 ↓（好）
带宽 ↓（好）
速度：端侧通常 ↑，但受反量化开销影响（可能 ↓）
精度 ↓（坏）
功耗 ↓（通常好，因数据搬运减少）
```

**功耗的机制拆解**：

```text
功耗主要来自：DRAM 带宽（权重读取） + 计算单元 + 缓存
权重量化 → 降低 DRAM 带宽 → 降低功耗
但低 bit 反量化 kernel 可能增加计算功耗
净效果取决于：带宽受限 vs 算力受限
端侧通常是带宽/内存受限 + 功耗受限 → 量化是降功耗的关键手段
```

**五维决策速查**：

| 场景 | 推荐档位 |
|------|---------|
| 精度优先、资源充足 | F16 / Q8_0 |
| 均衡 | Q4_K_M / Q5_K_M |
| 端侧内存紧张 | Q4_0 / Q2_K |
| 极致压缩、有 imatrix | IQ2 / IQ3 |

## 二十、业务范例

### 20.1 范例一：车机语音助手

```text
场景约束：内存 8GB、需常驻、响应快、上下文短（<4K）
模型：1.5B ~ 3B 指令微调模型
推荐档位：Q4_K_M
KV 配置：-ctk q8_0 -ctv q8_0（上下文短，可选 F16）
关键考量：
  ① 常驻内存受限 → 权重量化 + KV 量化
  ② 车载高温 → 需控制功耗，优先 NPU（若有）
  ③ 语音场景对首字延迟敏感 → prefill 优化
  ④ 校准集用**车载对话语料**，而非通用文本
```

### 20.2 范例二：手机端翻译 / 摘要

```text
场景约束：内存 4-8GB、安装包预算紧、离线
模型：1B ~ 2B
推荐档位：Q4_K_M 起，安装包极紧时 IQ4_XS（无需 imatrix）
KV 配置：-ctk q8_0 -ctv q8_0
关键考量：
  ① 安装包体积 → 低 bit 是刚需
  ② 翻译对精度敏感 → 必须做任务级评估（BLEU/COMET），不能只看 PPL
  ③ IQ 系列需要 imatrix → 若无校准条件，选 IQ4_XS 或 Q4_K_M
```

### 20.3 范例三：嵌入式巡检 / 质检

```text
场景约束：内存 2-4GB、算力极弱、可能无 NPU
模型：0.5B ~ 1.5B
推荐档位：Q4_0（kernel 最简）或 Q4_K_M
KV 配置：-ctk q8_0 -ctv q8_0
关键考量：
  ① 算力弱 → K-quant 的反量化开销需实测，可能 Q4_0 反而更快
  ② 任务单一 → 校准集极易获取，imatrix 收益高
  ③ 可能无 GPU → 纯 CPU 路径，关注线程配置
```

### 20.4 范例四：长上下文知识库

```text
场景约束：内存 8-16GB、上下文 32K+、RAG 场景
模型：7B ~ 8B（可能含 MLA / 稀疏注意力架构）
推荐档位：Q4_K_M 或 Q4_0（省下的内存留给 KV）
KV 配置：-ctk q8_0 -ctv q8_0（**必选**）
关键考量：
  ① 32K 上下文的 KV 内存可能超过权重 → KV 量化是刚需
  ② 稀疏注意力架构（DSV4/DSA/ISWA）可进一步降 KV 与算力
  ③ 长上下文下的质量退化必须专项评估
```

**KV 内存估算示例**（7B 模型，GQA，n_layer=32，n_head_kv=8，n_embd_head_k=128，32K ctx）：

```text
KV 元素数 = 2 × 32 层 × 32768 ctx × 8 head_kv × 128 head_dim = 2.147e9
F16  KV: 2.147e9 × 2B = 4.00 GiB
Q8_0 KV: 2.147e9 × 1B = 2.00 GiB
差值 2.00 GiB —— 足以决定端侧是否可行
```

公式中的 `2 ×` 同时覆盖 K 与 V 两份缓存。
若模型是 MHA（`n_head_kv == n_head`）而非 GQA，KV 内存会按比例放大数倍，
使长上下文在端侧直接不可行——这是 GQA/MQA 架构对端侧部署的核心价值。

**GQA 对 KV 内存的量化影响**（以 Qwen2.5-1.5B 为例，`n_head=12, n_head_kv=2`）：

```text
MHA 等效 KV（12 个 KV head）→ 1.0×
实际 GQA KV（2 个 KV head） → 1/6 ≈ 0.167×
即 GQA 使 KV 内存降至同等规模 MHA 模型的 1/6。
```

## 二十一、取舍分析

### 21.1 档位取舍：Q8_0 vs Q4_K_M vs IQ2_XS

**决策**：端侧默认 Q4_K_M，精度敏感场景 Q8_0，极致压缩 IQ2_XS。

| 选项 | 优势 | 劣势 |
|------|------|------|
| Q8_0 | 精度高、kernel 成熟、几乎无损 | 容量大、带宽高 |
| **Q4_K_M** | **容量/带宽/精度均衡** | 轻微精度损失 |
| IQ2_XS | 极致压缩（~2.3 BPW） | 需 imatrix、质量损失明显、kernel 覆盖有限、反量化慢 |

**选择依据**：端侧同时受容量/带宽/功耗约束 → Q4_K_M 是 Pareto 最优；
精度敏感 → Q8_0；容量极度受限 → IQ。

**接受代价**：部分精度损失。**缓解**：imatrix + 敏感张量高 bit + 分层策略。

**重新评估条件**：硬件升级（更大内存 / NPU 支持 INT4 QAT）或质量指标不达标。

### 21.2 PTQ vs QAT

**决策**：端侧优先 PTQ（llama.cpp 路线），NPU INT8/INT4 低 bit 时引入 QAT。

**依据**：端侧快速迭代选 PTQ；NPU 固定算子 + 质量敏感任务选 QAT。

### 21.3 统一量化 vs 分层/非均匀量化

**决策**：非均匀分层量化（llama.cpp 方式）。

**依据**：V / 前后层 / 敏感张量更多 bit，用极小容量换显著精度，优于统一低 bit。
量化证据：`Q4_K_M` 相比"纯 Q4_K"仅增加约 0.3 BPW，但精度接近 Q5_K。

### 21.4 全设备同档位 vs 按设备分档

**决策**：**按设备分档**。

**依据**：CPU/GPU/NPU 的 kernel 覆盖和量化类型支持不同，统一档位会牺牲某端。
保留多档位模型 + 运行时选择（见 §18.4 热切换）。

**代价**：安装包增大、分发复杂度上升。
**缓解**：主推 1–2 个档位，其余作为可选下载。

### 21.5 稀疏注意力引入

**决策**：长上下文端侧场景引入 SWA / DSV4 / DSA 稀疏。

**依据**：少算力少带宽。**代价**：需架构支持、kernel 成熟度、短上下文收益不明显。

### 21.6 mmap vs 全量加载

**决策**：按平台选择。

```text
Linux / Windows → mmap（显著加速，热缓存下更优）
macOS           → 全量加载（mmap 可能因内存管理策略反而变慢）
```

源码依据见 §18.2。端侧部署应实测决定。

### 21.7 KV 量化档位取舍

| 配置 | KV 体积 | 精度影响 | 适用 |
|------|--------|---------|------|
| F16 / F16 | 基准 | 无 | 短上下文、内存充裕 |
| Q8_0 / Q8_0 | 50% | 极小 | **通用推荐** |
| Q8_0 / Q4_0 | 37.5% | V 侧可见 | 内存紧张、长上下文 |
| Q4_0 / Q4_0 | 25% | 明显 | 极限压缩、需实测 |

**K 与 V 的非对称处理**：V 参与 attention 加权求和，对量化更敏感；
实践中常保留 K 为 Q8_0 而 V 降到 Q4_0。

## 二十二、最佳实践与上线检查清单

### 22.1 端侧量化最佳实践

```text
【流程】
① 永远先 --dry-run 估算体积，再实际量化
② 用 imatrix（除非 Q8/Q6 这类近无损档位）
③ 校准集必须匹配目标业务域
④ 保留 F16 基线，所有档位与基线对比
⑤ 记录 commit hash + 量化参数 + 硬件元数据

【选型】
⑥ 端侧首选 K-quant 系列（Q4_K_M），而非 Q4_0
⑦ 优先选择 kernel 覆盖广的类型（CPU 全支持，GPU/NPU 需核对）
⑧ IQ 系列只在极需压缩且有能力做 imatrix 时使用
⑨ TQ 系列只用于三值训练模型（BitNet）
⑩ 长上下文务必配 KV 量化

【验证】
⑪ 质量：PPL + 任务指标 + 主观输出，三者都要
⑫ 性能：必须在**目标设备**实测，不能只看 BPW 推算
⑬ 长上下文专项测试
⑭ 持续运行与热切换测试
```

### 22.2 关键注意事项（易踩的坑）

| 注意事项 | 说明 | 相关章节 |
|---------|------|---------|
| **不要只看 BPW** | 不同架构、不同层对量化敏感度不同，必须实测 | §9.2、§19 |
| **输出层 / embedding 敏感** | 用更高精度或不量化 | §17.3 |
| **norm 不量化** | 对精度极其敏感（缩放误差会放大到全网络） | §17.3 |
| **极低 bit 必须 imatrix** | 否则产出垃圾（IQ2/IQ1 缺失即报错） | §17.4 |
| **形状兼容** | block size 不整除会回退，甚至 F16 | §15.5 |
| **KV 量化误差** | 长上下文时误差累积，必须专项评估 | §13.5、§19.2 |
| **反量化开销** | 低 bit 可能因 kernel 慢，必须实测 | §9.2、§13.2 |
| **GQA/MQA 影响** | KV head 少 → KV 更小，KV 量化收益相对变小 | §12.2 |
| **MoE 门控不量化** | expert gate（`ffn_gate_inp`）极敏感 | §11.3.2 |
| **校准集泄露** | 用与目标业务分布不符的校准数据会**高估**质量 | §17.4 |
| **硬件算子覆盖** | 某些量化类型在特定 NPU/GPU 无 kernel，直接不可用 | §18.1 |
| **多语言 / 长尾** | 极低 bit 对稀有 token 影响大（词表尾部退化更明显） | §19.2 |

**端侧特有五项**（与云端部署的差异所在）：

```text
① 功耗/发热：实测满载温度，不能只看 tok/s
② 首字延迟：量化 + 加载策略共同影响 TTFT
③ 内存碎片：长时间运行可能碎片化（mmap 与动态分配混合时尤甚）
④ 热更新：模型更新时保持格式兼容（GGUF 版本 + 量化类型）
⑤ 多档位共存：根据内存/电量动态切换
```

### 附录 C：llama-quantize 参数速查（已核验）

```text
用法：
  llama-quantize [options] model-f32.gguf [model-quant.gguf] type [nthreads]
  或（单参数形式，自动生成输出名）：
  llama-quantize [options] model-f32.gguf type

选项：
  --allow-requantize              允许对已量化张量二次量化
  --leave-output-tensor           输出层保持原类型（不量化）
  --pure                          全体使用 default_type，禁用规则表
  --imatrix FILE                  注入重要性矩阵
  --include-weights NAME          仅对指定张量**使用** imatrix（与下一个互斥）
  --exclude-weights NAME          对指定张量**不使用** imatrix
  --output-tensor-type TYPE       强制 output 张量类型
  --token-embedding-type TYPE     强制 token_embd 类型
  --tensor-type NAME=TYPE         正则覆盖单张量（可多次，等号分隔）
  --tensor-type-file FILE         从文件批量读取覆盖规则（空格或换行分隔）
  --prune-layers L0,L1,...        物理删除指定层（逗号分隔）
  --keep-split                    保持分片数不变
  --override-kv KEY=TYPE:VALUE    覆盖 GGUF 元数据
  --dry-run                       只估算体积，不写文件
```

**`--include-weights` / `--exclude-weights` 的准确语义**（已核验）：

```text
--include-weights tensor_name   →  use importance matrix for this/these tensor(s)
--exclude-weights tensor_name   →  do not use importance matrix for this/these tensor(s)
```

**它们控制的是"哪些张量使用 imatrix"，而**不是**"哪些张量被量化"**。
两者互斥（`quantize.cpp:479`），且仅对 `--imatrix` 提供的校准数据生效。
这是一个容易望文生义的参数——源文档将其描述为"白名单/黑名单张量"，不准确。

**`COPY` 是 type 位置的特殊值**（非选项）：`llama-quantize in.gguf out.gguf COPY`
等价于 `--only-copy`（只复制不量化）。`--only-copy` 本身**不是 CLI 选项**，
而是 `llama_model_quantize_params.only_copy` 的库级字段。

**`nthreads` 是位置参数**（非 `--nthread`）：追加在 type 之后。

**退出码**：

```text
0  成功
1  失败（imatrix 缺失 / 含非有限值 / 量化校验失败 / 非法 ftype / 非法参数）
```

### 附录 D：KV Cache 配置速查（已核验）

```bash
-ctk, --cache-type-k TYPE        # K cache 类型
-ctv, --cache-type-v TYPE        # V cache 类型
--spec-draft-type-k/-v TYPE      # 草稿模型 KV 类型
```

**允许取值**（9 种）：

```text
f32, f16, bf16, q8_0, q4_0, q4_1, iq4_nl, q5_0, q5_1
```

**默认值**：`f16`（K 与 V 均为 f16）。

**Flash Attention 约束**：启用 FA 时，若 K 为量化类型，
要求 `n_embd_head_k % ggml_blck_size(type_k) == 0`。

## 一句话总结

**通用量化篇**：
> 量化的驱动力是容量、带宽、算力三类瓶颈；数学本质是用 `q = round(x/s) + z` 把连续值离散化，
> 误差上界为 `s/2`；因此**粒度（多少权重共享一个 scale）是核心决策**——
> per-tensor 快、per-channel 准、per-group 是 LLM 的选择。
> LLM 主流走 PTQ，因为训练成本悬殊、权重冗余度高、离群通道可精准保护；
> 四大算法（GPTQ 二阶补偿 / AWQ 激活感知 / SmoothQuant 难度迁移 / LLM.int8() 混合精度）
> 提供了不同角度的优化思路，而 llama.cpp 用 **imatrix + 非均匀分层**这一轻量组合近似其效果。

**端侧部署篇**：
> 端侧量化的本质是在"**能装下、跑得动、不烫手、质量可接受、首字够快**"五条约束下做多维权衡；
> llama.cpp 提供了从 L1 权重（K-quant 为主力）到 L3 KV、L6 运行时的完整能力，
> 而端侧系统的设计要点是：**用 Q4_K_M 打底、用 imatrix 精调、用 KV 量化省内存、
> 用按设备分档覆盖三端差异、用实测而非推算做决策**。

**两篇的连接**：通用原理回答了"量化为什么有效、有哪些选择"，
端侧部署回答了"在具体设备预算下怎么选、怎么验证"。
