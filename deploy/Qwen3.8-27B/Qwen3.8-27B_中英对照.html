§2仓库说明与引言Repository Notes & Introduction

本仓库包含后训练模型在 Hugging Face Transformers 格式下的模型权重与配置文件。
这些产物兼容 Hugging Face Transformers、vLLM、SGLang、TokenSpeed 等框架。

This repository contains model weights and configuration files for the post-trained model in the Hugging Face Transformers format. These artifacts are compatible with Hugging Face Transformers, vLLM, SGLang, TokenSpeed, etc.

对于希望获得托管式、可扩展推理服务而无需自行维护基础设施的用户，官方 Qwen API 服务由 Qwen Cloud 提供。其中 Qwen3.8-27B 将以托管版本形式提供，并具备更多生产级特性，例如默认 100 万 token 上下文长度、官方内置工具。更多信息请参阅 Qwen3.8-27B 概览。该服务即将上线，敬请期待后续更新。

For users seeking managed, scalable inference without infrastructure maintenance, the official Qwen API service is provided by Qwen Cloud. In particular, Qwen3.8-27B will be available as a hosted version with more production features, e.g., 1M context length by default, official built-in tools. For more information, please refer to the Qwen3.8-27B Overview. The service is coming soon. Stay tuned for updates.

继 Qwen3.5 与 Qwen3.6 系列在社区被广泛采用之后，我们很高兴地推出 Qwen3.8 —— Qwen 开源模型系列中迄今能力最强的一代。

Following the widespread community adoption of the Qwen3.5 and Qwen3.6 series, we are pleased to introduce Qwen3.8, the most capable generation in the Qwen open-model family to date.

Qwen3.8 构建于 Qwen3.5 的架构基础之上，在编码、专业工作、研究以及长程智能体任务上实现了显著提升。Qwen3.8-27B 将这些进展浓缩进一个紧凑、易于部署的稠密模型：它是一个能理解图像与视频的原生视觉语言模型，支持灵活的思考控制，旨在以更高的可靠性把复杂的多步骤任务从头到尾执行完成。

Built on the architectural foundation of Qwen3.5, Qwen3.8 delivers substantial gains across coding, professional work, research, and long-horizon agentic tasks. Qwen3.8-27B brings these advances to a compact, deployment-friendly dense model: a native vision-language model that understands images and videos, with flexible thinking control, designed to carry complex, multi-step tasks through to completion with greater reliability.

§3Qwen3.8 亮点Qwen3.8 Highlights

Qwen3.8-27B 具备以下增强特性：

Qwen3.8-27B features the following enhancements:

  • 核心能力：在编码、专业工作、研究与长程智能体任务上实现全面改进。

    Core Capabilities: Comprehensive improvements across coding, professional work, research, and long-horizon agentic tasks.

  • 智能体执行：更强的自主规划能力与更好的环境反馈处理，从而实现更可靠的端到端任务完成。

    Agent Execution: Stronger autonomous planning and better handling of environment feedback, leading to more reliable end-to-end task completion.

  • 下游兼容性：更广泛地支持主流执行框架与开发工具，更容易集成进你现有的技术栈。

    Downstream Compatibility: Broader support for popular harnesses and development tools, making it easier to integrate into your existing stack.

  • 灵活的思考控制：思考模式默认开启，并可按请求关闭；推理深度可通过 reasoning_effort 调节，历史消息中的推理上下文可通过 preserve_thinking 予以保留。

    Vision-Language Understanding: Native support for image and video understanding, from STEM diagrams and documents to hour-scale videos.

API 使用API Usage

Qwen3.8 模型默认在思考模式下运行，会在生成最终回复之前先输出以 <think>\n...<think>\n\n 标识的思考内容。若要关闭思考内容、直接获得回复，请参阅此处的示例。

Qwen3.8 models operate in thinking mode by default, generating thinking content signified by <think>\n...<think>\n\n before producing the final response. To disable thinking content and obtain a direct response, refer to the examples here.

我们推荐使用以下采样参数组合进行生成：

We recommend using the following sets of sampling parameters for generation:

Please note that the support for sampling parameters varies according to inference frameworks.

Qwen3.8 官方支持 reasoning_effort 参数，可用于调节推理深度并控制成本：

Qwen3.8 comes with official support for reasoning_effort, which can be used to adjust reasoning depth and control cost:

  • xhigh（默认值）：适用于需要深入分析的高复杂度任务。

    xhigh (default): for complex tasks demanding thorough analysis

  • medium：在准确率与速度之间取得平衡。

    medium: balancing accuracy and speed

  • low：高效推理，针对速度与成本优化。

    low: efficient reasoning optimizing for speed and cost

此外，为了开箱即用的最佳体验，所有负载默认启用 preserve_thinking。若要关闭保留思考，请参阅此处的示例。

In addition, preserve_thinking is enabled by default for all workloads for the best out-of-the-box experience. To disable preserved thinking, refer to the examples here.

在多轮智能体任务中，降低推理强度并不总能缩短整体任务完成时间。虽然每轮响应可能更快，但也可能导致分析不充分、失败增多与反复重试，反而增加总延迟与 token 消耗。

In multi-turn agentic tasks, lower reasoning effort does not always reduce overall task completion time. Although it may produce faster per-turn responses, it can also lead to insufficient analysis, more failures, and repeated retries, which may increase total latency and token consumption.

            "enable_thinking": True,   # 默认开启
            "preserve_thinking": True, # 默认开启
        },
    },
    reasoning_effort="xhigh",  # 默认为 xhigh；支持的档位为 xhigh、medium、low
    stream=True,
    stream_options={"include_usage": True},
)

reasoning_content = ""
answer_content = ""
is_answering = False
print("\n" + "=" * 20 + "Reasoning" + "=" * 20 + "\n")

for chunk in completion:
    if not chunk.choices:
        print("\nUsage:")
        print(chunk.usage)
        continue

    delta = chunk.choices[0].delta

    if hasattr(delta, "reasoning_content") and delta.reasoning_content is not None:
        if not is_answering:
            print(delta.reasoning_content, end="", flush=True)
        reasoning_content += delta.reasoning_content
    elif hasattr(delta, "reasoning") and delta.reasoning is not None:
        if not is_answering:
            print(delta.reasoning, end="", flush=True)
        reasoning_content += delta.reasoning

    if hasattr(delta, "content") and delta.content:
        if not is_answering:
            print("\n" + "=" * 20 + "Answer" + "=" * 20 + "\n")
            is_answering = True
        print(delta.content, end="", flush=True)
        answer_content += delta.content

messages.append({
    "role": "assistant",
    "content": answer_content,
    "reasoning_content": reasoning_content,
    "reasoning": reasoning_content,
})

参数要点：enable_thinking 与 preserve_thinking 通过 chat_template_kwargs 传入，默认均为 True；reasoning_effort 作为顶层参数传入，默认 xhigh；流式响应中推理内容与正式回答分别位于 delta.reasoning_content（或 delta.reasoning）与 delta.content；当 chunk.choices 为空时，该 chunk 携带的是 usage 用量信息。

Key parameters: enable_thinking and preserve_thinking are passed via chat_template_kwargs (both default True); reasoning_effort is a top-level parameter (default xhigh); in streaming, reasoning vs. answer arrive in delta.reasoning_content (or delta.reasoning) and delta.content; an empty chunk.choices carries usage.

关闭保留思考Disable Preserved Thinking

默认情况下，Qwen3.8 会保留所有历史消息中的思考块，从而在整个对话中维持完整的推理轨迹。这一行为被称为"保留思考"，它确保上下文完全连贯，对于决策一致性、减少冗余推理至关重要的智能体场景尤其有益。同时它还能提升 KV 缓存利用率，在思考与非思考两种模式下都优化了推理效率。

By default, Qwen3.8 retains thinking blocks from all historical messages, maintaining a complete reasoning trace across the conversation. This behavior, known as preserved thinking, ensures full context continuity and is especially beneficial for agent scenarios where decision consistency and reduced redundant reasoning are critical. It also improves KV cache utilization, optimizing inference efficiency in both thinking and non-thinking modes.

如果你只想保留最新一条用户消息所对应的思考块，可将 preserve_thinking 设为 False 来关闭该行为：

§8最佳实践Best Practices

为获得最佳性能，我们推荐以下设置：

To achieve optimal performance, we recommend the following settings:

1. 采样参数Sampling Parameters

我们建议使用以下采样参数组合：

We suggest using the following sets of sampling parameters:

模式Mode参数
思考模式Thinking Modetemperature=1.0, top_p=0.95, top_k=20, min_p=0.0, presence_penalty=0.0, repetition_penalty=1.0
指令（或非思考）模式Instruct (or non-thinking) modetemperature=0.7, top_p=0.80, top_k=20, min_p=0.0, presence_penalty=1.5, repetition_penalty=1.0

对于支持该参数的框架，你可以在 0 到 2 之间调节 presence_penalty，以减少无休止的重复。但使用较高的值偶尔会导致语言混杂，并使模型性能略有下降。

For supported frameworks, you can adjust the presence_penalty parameter between 0 and 2 to reduce endless repetition. However, using a higher value may occasionally result in language mixing and a slight decrease in model performance.

2. 充足的输出长度Adequate Output Length

为了在智能体任务上获得最佳表现，我们建议分配足够的输出长度，让模型生成详尽、完整的回复。对于支持对内部推理与最终输出分别设置 token 上限的框架，我们建议在 1M 上下文长度内采用如下配置：

To optimize performance on agentic tasks, we recommend allocating sufficient output length to allow the model to generate detailed and comprehensive responses. For frameworks that support separate token limits for internal reasoning and final outputs, we suggest the following configuration within the 1M context length:

  • 推理内容：将最大输出长度设为 262,144 token。

    Reasoning Content: Set the maximum output length to 262,144 tokens.

  • 最终回复：将最大输出长度设为 131,072 token。

    Final Response: Set the maximum output length to 131,072 tokens.

这些设置为复杂推理提供了必要的容量，同时为高质量最终产出留出了充裕空间。

These settings provide the necessary capacity for complex reasoning while ensuring ample space for high-quality final deliverables.

3. 处理超长文本Processing Ultra-Long Texts

Qwen3.8-27B 原生支持最长 262,144 token 的上下文。对于总长度（含输入与输出）超过该上限的长程任务，我们建议使用 RoPE 缩放技术来有效处理长文本，例如 YaRN。

Qwen3.8-27B natively supports context lengths of up to 262,144 tokens. For long-horizon tasks where the total length (including both input and output) exceeds this limit, we recommend using RoPE scaling techniques to handle long texts effectively, e.g., YaRN.

目前多个推理框架已支持 YaRN，例如 vLLM、SGLang 与 TokenSpeed。一般而言，在支持 YaRN 的框架中有两种启用方式：

YaRN is currently supported by several inference frameworks, e.g., vLLM, SGLang, and TokenSpeed. In general, there are two approaches to enabling YaRN for supported frameworks:

方式一：修改模型配置文件。 在 config.json 中，将 text_config 里的 rope_parameters 字段改为：

Modifying the model configuration file: In the config.json file, change the rope_parameters fields in text_config to:

{
    "mrope_interleaved": true,
    "mrope_section": [
        11,
        11,
        10
    ],
    "rope_type": "yarn",
    "rope_theta": 10000000,
    "partial_rotary_factor": 0.25,
    "factor": 4.0,
    "original_max_position_embeddings": 262144,
}

方式二：通过命令行参数传入。

Passing command line arguments:

vLLM：

VLLM_ALLOW_LONG_MAX_MODEL_LEN=1 vllm serve ... --hf-overrides '{"text_config": {"rope_parameters": {"mrope_interleaved": true, "mrope_section": [11, 11, 10], "rope_type": "yarn", "rope_theta": 10000000, "partial_rotary_factor": 0.25, "factor": 4.0, "original_max_position_embeddings": 262144}}}' --max-model-len 1000000

SGLang：

SGLANG_ALLOW_OVERWRITE_LONGER_CONTEXT_LEN=1 python -m sglang.launch_server ... --json-model-override-args '{"text_config": {"rope_parameters": {"mrope_interleaved": true, "mrope_section": [11, 11, 10], "rope_type": "yarn", "rope_theta": 10000000, "partial_rotary_factor": 0.25, "factor": 4.0, "original_max_position_embeddings": 262144}}}' --context-length 1000000

TokenSpeed：

TOKENSPEED_ALLOW_OVERWRITE_LONGER_CONTEXT_LEN=1 tokenspeed serve ... --hf-overrides '{"text_config": {"rope_parameters": {"mrope_interleaved": true, "mrope_section": [11, 11, 10], "rope_type": "yarn", "rope_theta": 10000000, "partial_rotary_factor": 0.25, "factor": 4.0, "original_max_position_embeddings": 262144}}}' --max-model-len 1000000

所有主流开源框架实现的都是静态 YaRN，这意味着无论输入长度如何，缩放因子都保持恒定，这可能会影响短文本上的性能。我们建议仅在确实需要处理长上下文时才修改 rope_parameters 配置，同时也建议按需调整 factor。例如，若你的应用典型上下文长度为 524,288 token，那么将 factor 设为 2.0 会更合适。

All the notable open-source frameworks implement static YaRN, which means the scaling factor remains constant regardless of input length, potentially impacting performance on shorter texts. We advise modifying the rope_parameters configuration only when processing long contexts is required. It is also recommended to modify the factor as needed. For example, if the typical context length for your application is 524,288 tokens, it would be better to set factor as 2.0.
