# 方法论：为什么这样设计

> **目标读者**：要评估这套框架是否可信、或要把它改造成自己团队流程的人  
> **前置知识**：读过 [README.md](../README.md)；有性能优化实战经验  
> **预计阅读**：15 分钟

这套框架不是「把 benchmark 脚本包了个 CLI」。它的每个设计选择都对应  
性能分析中一类具体且常见的错误。本文按「错误 → 设计」的顺序讲清楚。

---

## 1. 为什么先算理论上界，而不是先跑 benchmark

### 常见错误

拿到模型直接跑 `llama-bench`，看到 50 t/s 就开始调 kernel、  
加线程、换 batch size，折腾一周提升 3%，然后发现瓶颈根本不在那里。

### 设计：`define` 强制先算三件事

```text
① 显存预算   权重 + KV + 激活 + 运行时 ≤ 显存上限？
② roofline   算术强度 vs 拐点 ⇒ compute-bound 还是 memory-bound？
③ 理论上界   带宽 ÷ 权重体积 = tps_max
```

**为什么这能避免无效劳动**：Decode 阶段每步只处理 1 个 token，  
算术强度约 4 FLOPs/Byte，而 RTX 4090 的 roofline 拐点是 164 ——  
相差 40 倍。这意味着算力几乎完全闲置，**任何提升算力的优化（更快的  
kernel、更强的 SIMD）都不会加快 Decode**。

算完这个上界，你就知道：

- 实测 50.96 t/s vs 上界 62.60 t/s = 达成 81.4%（对**标称**带宽）
  ⇒ 看似还有 19% 空间，但标称值本身不可达
- 探针实测纯读带宽 883.8 GB/s（标称的 87.7%）⇒ 生产内核已拿到其中 **92.9%**
  ⇒ **kernel 层实际只剩约 7% 的空间**
- 想再快，只能**减少每步需要搬运的字节数**或**减少读取次数**（量化、投机解码）

这一步 3 分钟，省下的是一周。

### 代码对应

- `perfkit/config.py: theoretical_decode_tps()` —— 上界公式
- `perfkit/config.py: roofline_verdict()` —— 拐点判定
- `perfkit/commands/define.py` —— 强制在动手前打印这三件事

## 2. 为什么必须分开建模 Prefill 和 Decode

### 常见错误

把 E2E 延迟当成一个整体来优化。结果：为 Decode 做的优化  
（如降低 batch）反而拖慢了 Prefill，整体没变。

### 设计：`scope` 字段 + 阶段剖面

| 阶段      | 瓶颈类型          | 有效手段                               | 无效手段         |
| :------ | :------------ | :--------------------------------- | :----------- |
| Prefill | Compute-bound | FlashAttention、大 batch、Tensor Core | 量化权重（算力才是瓶颈） |
| Decode  | Memory-bound  | 量化、投机解码、减少回退                       | 加算力（算力本就闲置）  |

框架把 `scope` 作为任务定义的第一字段，`diagnose` 据此决定  
判定规则的优先级，`optimize` 据此筛选方案。

### 代码对应

- `task_*.yaml: task.scope`
- `perfkit/commands/diagnose.py: _rule_prefill_compute()` —— 单独标注 Prefill 的 compute-bound 属性

## 3. 为什么 KV Cache 需要单独建模

### 常见错误

把 KV Cache 当成「一点额外内存」。实际上在长上下文场景，  
它是显存中唯一**随上下文线性增长**的部分，也是 Decode 阶段  
唯一随时间增长的内存带宽开销。

### 设计：KV 专项剖面 + 精度阶梯

```text
KV 字节 = layers × ctx × n_head_kv × head_dim × 2(K,V) × bytes_per_elem
```

框架在 `define` 阶段就打印**KV 精度阶梯**（Qwen3.8-27B @ 4090 D，64K ctx）：

| KV 精度 | 64K 下 KV 总量 | 显存合计 | 安全冗余 | 可行 |
| :--- | ---: | ---: | ---: | :-: |
| F16/F16 | 4.00 GiB | 20.20 GiB | 3.79 GiB | ❌ 冗余 < 4 GiB |
| Q8_0/Q8_0 | 2.12 GiB | 18.33 GiB | 5.66 GiB | ✅ |
| Q8_0/Q4_0 | 1.62 GiB | 17.83 GiB | 6.16 GiB | ✅ |
| Q4_0/Q4_0 | 1.12 GiB | 17.33 GiB | 6.66 GiB | ✅ |

这张表直接把「KV 量化是必选项还是可选项」变成算术问题：
F16 的 KV 在 24GB 卡上装得下 64K，但**安全冗余只剩 3.79 GiB，低于 4 GiB 硬约束** ——
所以判定为不可行。注意判据是「装得下 **且** 冗余够」，只看前者会把峰值一来就 OOM 的档位标成可行。

> **这张表的数字曾经是错的，原因值得记住**：早期版本按「64 层全注意力」推 KV，
> 算出 F16 需 16 GiB，于是得出「KV 量化是 64K 的必选项」。
> 用 GGUF 元数据核验后发现这是**混合架构**（16 层全注意力 + 48 层 SSM），
> 每 token 的 KV 元素数是 32,768 而不是 131,072 —— 正好差 4 倍。
> 修正后 F16 只需 4 GiB，「必选项」变成了「冗余不够所以不可行」，结论的性质完全不同。
>
> **教训**：第一性原理公式只有在**输入是真值**时才成立。几何公式里的层数不是
> 「有多少层」，而是「有多少层有 KV」；混合架构里这两者可以差好几倍。

同时框架刻意区分 K 与 V 的量化精度（`--cache-type-k q8_0 --cache-type-v q4_0`）：Key 决定注意力检索精度，Value 更鲁棒，  
因此**不能一起降到 q4_0**。这条经验写在 `plan_*.yaml` 的  
`kv_mixed_q8q4` 卡片里，作为方案的一部分传递。

### 代码对应

- `perfkit/config.py: kv_cache_bytes()` —— 几何公式
- `perfkit/commands/define.py` —— 精度阶梯表
- `perfkit/commands/profiling.py` —— KV 随 ctx 的增长曲线

## 4. 为什么不静默校准模型与实测的差额

### 常见错误

发现模型算 6.5 GiB、实测 2.2 GiB，直接「以实测为准」把模型改掉。  
结果：根因（架构超参反推错误？台账粗估？）永远查不出来，  
下次换模型时同样的错误再来一遍。

### 设计：并列展示 + 显式对账

框架遇到不一致时输出：

```text
几何模型值  6.50 GiB
台账实测值  2.20 GiB
差额        4.30 GiB（×2.95）
可能原因    几何公式用反推的 n_head_kv=8 / head_dim=128；...
核验方式    perfkit define --from-gguf <model.gguf>
影响        差额直接影响显存预算的安全冗余判定（5.4 GiB vs 1.1 GiB）
```

并且**验收判定优先采用实测值，模型值只用于边界判断** ——  
既不掩盖差额，也不让差额污染结论。

差额消除后（比如通过 `--from-gguf` 拿到真值），重新运行框架自动收敛。

### 代码对应

- `perfkit/config.py: reconcile()` —— 对账表
- `perfkit/gguf.py` —— GGUF 元数据解析，根治差额
- `perfkit/commands/verify.py: _cell()` —— 每个 KPI 单元格独立标注口径

## 5. 为什么不选择性引用参考文档

### 常见错误

参考文档里 §3.1 说 Prefill 2900 t/s、§4.4 说 85.5 t/s（差 34 倍）。  
写报告时挑一个对自己结论有利的引用 —— 如果结论是「Prefill 很快」，  
就引 2900；如果是「Prefill 是瓶颈」，就引 85.5。

这是**结论先于证据**，是性能分析中最严重的错误。

### 设计：`source_conflicts` 显式记录

```yaml
source_conflicts:
  - id: prefill_tps
    claim_a: {value: 2900, source: "§3.1"}
    claim_b: {value: 85.5, source: "§4.4"}
    ratio: 33.9
    likely_cause: "§3.1 未标注 prompt 长度与并发配置..."
    adopted: claim_b
    action: "用 live 模式重测 Prefill 曲线"
```

报告 §1.5 并列展示两个口径、比值、可能原因与消除方式。  
并且在 §6 明确指出：**`prefill_tps` 未达标不是性能缺陷，  
而是 KPI 目标本身取自未经验证的声明**。

诚实地报告「这个目标从一开始就不可达」，比伪造达标更有价值。

### 代码对应

- `task_*.yaml: source_conflicts`
- `perfkit/commands/report.py` —— §1.5 章节与 §6 未达标归因

## 6. 为什么每个瓶颈结论都要带「反证条件」

### 常见错误

「Decode 慢，因为它是 memory-bound」—— 这句话本身没错，  
但它无法被证伪，因此不是科学结论，只是复述常识。

### 设计：`counter_evidence` 必填

```python
{
    "type": "memory_bound",
    "evidence": ["达成带宽 820.6 / 1008.0 GB/s = 81.4%", ...],
    "reasoning": "...",
    "counter_evidence": "若 SM 利用率 >90% 且带宽利用率 <60%，则应改判 compute_bound",
}
```

有了反证条件，结论就变成可检验的预测：

- 如果实测 SM 利用率 95%、带宽 40% ⇒ 结论错误，应改判 compute_bound
- 如果实测 SM 利用率 20%、带宽 82% ⇒ 结论成立

**这是判断一份性能报告是否可信的最快方法**：看它有没有写  
「什么情况下这个结论会被推翻」。

### 代码对应

- `perfkit/commands/diagnose.py` —— 每条 `RULES` 的返回值都含 `counter_evidence`

## 7. 为什么方案卡片要同时写收益和代价

### 常见错误

报告里只写「MTP 投机解码 +64.5%」，不写它 +1.28 GiB 显存、  
与多槽位并发冲突、接受率随任务类型波动。

结果：生产环境上线后 OOM，或者发现并发场景下反而更慢。

### 设计：方案卡片的固定字段

```yaml
- id: spec_mtp
  gain: {decode_tps: 1.60, vram_gib: 1.28}    # 收益
  cost: 显存 +1.28GiB；Draft 必须全层卸载       # 代价
  risk: 与多槽位并发存在资源竞争；接受率强依赖任务类型   # 风险
  rollback: 去掉 -md / --spec-type 参数         # 回滚
  source: "[M] 49.21 → 87.27 t/s（单流）"      # 可复现来源
```

`verify` 阶段会自动从这些字段生成**副作用清单**，  
每条副作用都带「影响」与「缓解措施」。

**收益与代价成对出现**是方案能被生产环境安全采纳的前提。

### 代码对应

- `plan_*.yaml: plans[].{gain,cost,risk,rollback}`
- `perfkit/commands/verify.py: side_effects()`

## 8. 为什么「优化基线」不是「优化后配置的子集」

### 常见错误

把「优化后配置」的某个子集当基线，于是部分优化收益被预支到基线里，  
导致后续优化看起来没效果，或者收益重复计算。

### 设计：`optimization_baseline` 独立定义

```yaml
optimization_baseline:
  id: B0_baseline
  startup_flags: [-ngl 99, --parallel 1, --ctx-size 8192, "--flash-attn on"]
  rationale: >
    8K ctx 是端侧 LLM 的默认起步配置。基线保持可用且朴素，
    长上下文（64K）作为待验证的**优化项**而非基线的一部分。
```

基线是**可用的朴素生产配置**，不是「最优配置删掉几项」。  
这样每一项优化都有独立的、可归因的收益：

| 优化项          | 相对基线的独立收益         |
| :----------- | :---------------- |
| 上下文 8K → 64K | +700% 容量          |
| KV 量化        | 使 64K 在 24GB 卡上可行 |
| 双槽位并发        | 系统吞吐 +28.3%       |

### 代码对应

- `plan_*.yaml: optimization_baseline`
- `perfkit/commands/verify.py: build_comparison()` —— 两侧 bundle 显式命名

## 9. 为什么探针要按 q4_0 布局测而不是 fp32

### 常见错误

用 fp32 数组测「内存带宽」，然后拿这个数字反推 Decode 速度。  
得到的结果会**低估约 7 倍**。

### 原因

| 数据布局 | 每权重字节 | 26.9B 参数的实际访存量 |
| :--- | ---: | ---: |
| fp32（错误） | 4.0 B | 需要 107.6 GB（根本不是这个量） |
| q4_0（正确） | 0.5625 B | 15.13 GB |

在固定带宽下，能喂的 token 数差 7 倍。所以探针必须按真实的  
量化布局（32 权重 / 18 字节块）来测。

### 另一个常见错误：用拷贝带宽反推

`cudaMemcpy` 的读写各占一半带宽，而 Decode 是**只读权重**。  
用拷贝带宽反推会低估约 2 倍。因此 `cuda_bw_probe.cu` 单独测  
「纯读带宽」并明确标注这一点。

### 第三个常见错误：用逐字节求和测「顺序读带宽」

朴素写法是 `for (i...) sum += buf[i];`（逐字节）。编译器会把它退化成  
标量加载循环，测出的不是内存带宽而是**标量加载速率** ——  
在 i7-4770HQ 上实测：逐字节 13.1 GB/s vs 64 位字长 + 8 路累加器 17.4 GB/s，  
差 33%。数字看起来合理，但比真值低三分之一。

两个修正：

1. 按 **64 位字长**读，让编译器用向量化加载；
2. 用 **多个独立累加器**（实测 8 路）—— 单个累加链会被指令延迟串行化，  
   打不满访存。实测 1 路 vs 8 路差 1.8 倍。

### 第四个常见错误：只测匿名缓冲区

`malloc` 的缓冲区与 llama.cpp 实际访问的 **mmap 权重文件**在访存行为上不同  
（页表、大页、page cache 命中路径都不同）。因此探针提供 `stream-file` 模式  
直接 mmap 模型文件 —— 这是最贴近生产形态的口径。  
两者在实测中差异不大（17.29 vs 16.43 GB/s），但**口径正确性**比数值本身更重要：  
报告里写的每个数字，都要能说清它是怎么测出来的。

### 代码对应

- `cpp/ggml_probe.cpp` —— CPU 侧：`stream-file` / `stream` / `gemv` 三测
- `cpp/cuda_bw_probe.cu` —— GPU 侧：纯读 vs 拷贝 vs GEMV 三测
- `perfkit/commands/probe.py` —— 后端决定用哪个探针与什么参数

## 10. 为什么 CPU 与 GPU 必须分开建模

### 常见错误

把 GPU 那套分析模板直接套到 CPU 上：读「显存」、算「PCIe 回退代价」、  
看「SM 利用率」、把「零回退」列为硬约束。  
这些在 CPU 上要么无意义，要么会得出**方向相反**的结论。

### 三处本质差异

| 维度     | 独显 GPU                    | CPU                  |
| :----- | :------------------------ | :------------------- |
| 内存带宽归属 | 独立显存，不受主机影响               | **与主机所有进程共享**        |
| 回退代价   | 昂贵（PCIe 往返，单层即吃掉大半预算）     | **不存在回退**（权重本就在系统内存） |
| 调优第一参数 | `-ngl`（卸载层数）、`--parallel` | **线程数**（且最优值通常是物理核数） |

### 实测证据（Qwen2.5-1.5B @ i7-4770HQ）

**线程数存在最优值**：

| 线程            |     1 |     2 |         4 | 8（逻辑核） |
| :------------ | ----: | ----: | --------: | -----: |
| Decode (t/s)  |  9.49 | 15.18 | **17.85** |  13.03 |
| Prefill (t/s) | 32.03 | 55.28 | **78.42** |  75.53 |

8 线程反而比 4 线程慢 27% —— 超线程共享执行单元与访存端口，  
在访存密集的 GEMV 上形成竞争。**CPU 后端的第一个调优动作应该是扫线程数。**

**负载敏感度**（同一配置、不同时刻）：

| 系统负载 | Decode (t/s) |
| :--- | -----------: |
| < 2  |        17.85 |
| ≈ 90 |   9.19（-49%） |

这意味着：**CPU 后端的性能数字如果不带系统负载，就是不可解释的。**  
框架因此把采集时的负载写进 `baseline.json` 的 `environment`，  
报告 §0 据此判断数据可否引用。

### 设计：后端抽象层

框架把上述差异收敛到 `perfkit/backends.py`，每个后端回答四个问题：

```python
class Backend:
    def accel_flags(self) -> list[str]      # 加速器卸载参数（CPU 必须钉死 -ngl 0）
    def mem_snapshot(self)                  # 怎么读内存（nvidia-smi / getrusage）
    def bandwidth_probe_command(self, ...)  # 用哪个探针（cuda_bw_probe / ggml_probe）
    def fallback_is_cheap(self) -> bool     # 回退代价模型（决定报告怎么表述）
```

**为什么 CPU 必须显式写 `-ngl 0`**：这不是「默认值」，而是**必须钉死**。  
开发机是 MacBook Pro，装了 Metal（Intel Iris）—— 不写 `-ngl 0` 时  
llama.cpp 会静默走 GPU，与「验证 CPU 可用性」的目标直接相悖。  
这是「配置默认值」与「显式声明意图」的区别。

**为什么 `fallback_is_cheap()` 会改变报告的结论**：  
CPU/统一内存后端返回 `True` 时，报告 §3.8 的表述从  
「PCIe 往返代价，单层吃掉 77% 预算」改为「同步开销，单层仅占 0.9%」，  
「零回退」也不再被列为硬约束。同一份代码，两种正确的表述。

## 11. 为什么硬件剖面要同时报带宽与算力（以及一个容易犯的错）

### 常见错误一：只报带宽利用率

「达成带宽 820.6 / 1008 GB/s = 81.4%」——这句话回答了「内存子系统饱和了吗」，  
但没回答「算力用到了几成」。读者会问：既然算力才用了 1.7%，是不是把它用起来就能提速？

答案是**不能**，原因在 roofline：Decode 的算术强度只有 3.3 FLOPs/Byte，  
远低于 4090 的拐点 163.9。在这个区间里，**带宽先把算力卡住了** ——  
无论算力多强，可达上界都只有「强度 × 带宽」那么大。所以必须把两侧并列给出，  
才能说明「算力低不是缺陷」。

### 常见错误一·补：把「标称带宽」当成可达上限

上一条说「达成 81.4%，看起来还有 19% 空间」—— 这个 19% 是**假的**。
厂商标称的 1008 GB/s 含 ECC/刷新/行冲突等不可达开销，本机探针实测纯读只有
**883.8 GB/s（标称的 87.7%）**。用可达带宽做分母，生产内核已经拿到 **92.9%**。

**同一个 50.96 t/s，两种分母给出完全相反的结论**：

| 分母 | 利用率 | 读出来的结论 |
| :--- | ---: | :--- |
| 标称 1008 GB/s | 81.4% | 「还有 19% 空间，值得调 kernel」 |
| 实测纯读 883.8 GB/s | 92.9% | 「只剩 7%，调 kernel 是无效劳动」 |

**正确做法**：理论上界用**标称**带宽（那是物理上限，回答「离天花板多远」），
优化空间的判断用**实测可达**带宽（那是工程上限，回答「还能争取多少」）。
两者必须并列给出，且各自标明分母是什么。

### 常见错误二：把「算力达成率」当成独立证据

这是本框架在实现过程中**自己踩过的坑**，值得记下来：

第一版实现里，「算力侧判定」用了这样一个比值：

```text
算力达成率 = 实测达成算力 ÷ (算术强度 × 带宽)
```

看起来是在检验「算力有没有被浪费」。但展开这个式子：

```text
(FLOPs / step_s) ÷ (FLOPs / wb × 带宽)
= wb / (step_s × 带宽)
= 带宽利用率
```

**它恒等于带宽利用率。** 这不是巧合 —— 在访存受限区间内，  
算力完全由带宽决定，两者是同一个约束的两种写法。

于是那个「判定」实际上是把带宽结论换个说法重复了一遍，  
还会在带宽利用率低时给出误导性的「算力侧另有损失」结论  
（早期在一份构造数据上就误报过：带宽 18.9% ⇒ 算出「算力达成率 19%」⇒
判「算力侧另有损失」，但真实原因是那份数据是构造值，与算力无关）。

### 修正后的做法

硬件剖面现在报四个量，并明确标注哪个才是线索：

| 量                           | 用途                       |
| :-------------------------- | :----------------------- |
| 单步 FLOPs（理论）                | 分子；标注为下界（不含 kernel 实现浪费） |
| 实测达成算力                      | 回答「硬件算力被用到了几成」           |
| 对**峰值**的利用率                 | 低是必然的，但要让读者看到这个数         |
| **未被权重读取解释的时间** = 1 − 带宽利用率 | **这才是线索**：时间还有多少花在访存之外   |

最后一项指向「KV 读 / launch / 回退 / 采样」等具体方向，但**不擅自下结论** ——  
它只说「需进一步定位」，具体是什么要看别的剖面。  
诚实地报告「这个比值不是独立证据」，比用它凑出一个听起来很专业的判定要好。
