## 1. 第 0 步：环境准备

**目标**：让「这台机器上测出来的数字」变成一句可被他人检验的话。

**动作**

1. 采集硬件与软件画像：设备型号、内存容量与**标称带宽**、算力、
   驱动版本、引擎版本与 commit、编译器与关键编译标志、OS。
2. 构建一个最小可运行 demo，确认环境真的能用（不是「应该能用」）。
3. 如果要做带宽类分析，跑一次**带宽探针**，拿到这台机器的实测带宽。
   标称值与实测值用途不同，都要留：
   - 标称值 → 上界公式的分母
   - 实测值 → 达成率

**判据**：换一台同型号机器，按记录能复现出同一环境。

**常见错误**

| 错误 | 后果 |
|:---|:---|
| 只记「RTX 4090」不记驱动/CUDA 版本 | 换驱动后性能变化无法归因 |
| 把实测带宽填进「标称峰值」字段 | 上界算错，后面所有达成率都错 |
| 编译架构标志写错 | 静默退化到 JIT，性能掉一截且看不出来 |
| 不记录采集时的系统负载（共享内存的后端） | 同一配置两次测量差 2 倍，无法解释 |

## 2. 第 1 步：问题定义

**目标**：把「优化一下」变成「在 X 条件下，把 Y 指标从 A 提到 B，且不违反 Z」。

**必产出**

1. **画像**：模型结构超参（层数、hidden、KV heads、head_dim、词表、
   上下文上限）+ 设备画像。这些是后续所有估算公式的输入，填错会一路错下去。
2. **资源预算**：先确认「装不装得下」，再谈优化。
   `权重 + 缓存 + 运行时缓冲 ≤ 容量上限？安全冗余够吗？`
3. **理论边界**：算出物理上界（例如 `带宽 ÷ 权重体积 = 最大 t/s`）。
   这一步决定了「还有多少空间」——如果已达上界 82%，那么继续做底层微调的
   收益上限只有 18%。
4. **KPI 表**：每个指标给出 key / unit / direction / target / **定义**。
   定义必须写清口径（含不含采样？P95 还是均值？哪个场景？）。
5. **验收标准**：
   - `must_pass`：硬性达标项
   - `should_pass`：期望项
   - `guardrail`：质量与稳定性红线，**任一违反即回滚**

**判据**：目标可量化、可验收、且口径唯一。

**关键设计**：把 KPI 绑定到**具体场景**。同一个指标在不同条件下可以相差
数倍（短上下文的解码速率 17.5 t/s vs 16K 上下文 4.2 t/s），
不绑定场景的「decode_tps」是个没有意义的数字。

## 3. 第 2 步：基线

**目标**：建立优化前的真实性能，且**可复现**。

**必产出**

1. **基线配置**：这是「可用的朴素生产配置」，不是「优化后配置删掉几项」。
   区别很重要 —— 后者会把部分优化收益预支到基线里，导致后续收益重复计算。
2. **场景矩阵**：覆盖典型负载（短输入短输出 / 长上下文 / 长生成 /
   并发 / 持续负载）。每个场景给定 prompt 长度、生成长度、并发数。
3. **测量协议**：工具与版本、测量点（进程内计时 / 端到端墙钟）、
   统计口径（重复几次、取均值还是中位数）、每个参数的含义。
4. **逐场景复现命令**：能直接复制粘贴跑出同样数字的命令。

**判据**：数据可复现、覆盖场景全、口径已声明。

**常见错误**

- 拿「纯解码吞吐」和「端到端墙钟速率」直接比较（两者可差 35%）
- 不同场景的深度不同却直接相减（比较的是上下文长度，不是优化方案）
- 只测一个场景就下全局结论

## 4. 第 3 步：剖面与瓶颈定位

**拆成两个动作**（换硬件时只需重跑前者；调规则时不必重采数据）。

### 4.1 采集剖面

按需选择维度，每个维度回答**一个不同的问题**：

| 维度 | 回答什么 | 典型数据 |
|:---|:---|:---|
| 资源剖面 | 整机资源用尽了吗？ | 达成带宽/算力、利用率、剩余空间 |
| 阶段剖面 | 时间花在哪个阶段？ | 各阶段吞吐与耗时拆解 |
| 结构剖面 | 时间花在哪类算子上？ | 各算子占比（字节占比 ≈ 耗时占比，访存受限时） |
| 增长剖面 | 随规模增长的那部分有多大？ | 随上下文/批量线性增长的开销 |
| 异常剖面 | 有没有非预期的路径？ | 回退、重试、同步、错误率 |

### 4.2 定位瓶颈

用**决策树**而非直觉。每条规则是一个纯函数：`(剖面, 定义) → finding | None`。

finding 的结构（详见 `evidence-chain.md`）：

```json
{
  "type": "memory_bound",
  "severity": "primary",
  "confidence": "high",
  "evidence": ["达成带宽 830.9 / 1008.0 GB/s = 82.4%"],
  "reasoning": "算术强度 3.32 << 拐点 163.89，算力几乎闲置",
  "counter_evidence": "若 SM 利用率 >90% 且带宽利用率 <60%，应改判 compute_bound"
}
```

**判据**：根因明确、可归因、且带有反证条件。

### 4.3 四件产出物

| 产出物 | 回答什么 | 常见缺失 |
|:---|:---|:---|
| ① 性能 Profile 报告 | 时间/带宽花在哪 | 只报总量，没有分维度 |
| ② Hot Kernel 列表 | 先动谁 | 只给占比，不给累计/覆盖率/收益上限 |
| ③ 执行路径分析 | 数据从哪搬到哪 | 漏掉回退路径与 Host-Device 同步 |
| ④ 根因分析报告 | 为什么、能否被推翻 | 只有结论，没有证据链与反证条件 |

> ①②是**数据**，③④是**结论**。数据可以重采，结论必须可检验。
> 把四者混成一段文字，读者就无法判断哪部分是观测、哪部分是推断。

**一条硬经验**：不要只报一侧。例如访存类分析里只报带宽利用率，
读者会问「算力才用了 1.7%，用起来是不是就能提速」。
必须同时给出算力侧，并说清「算力低是带宽限死的必然结果」。
（但注意：算力达成率与带宽利用率在 roofline 框架下**恒等**，
不能当作两个独立证据 —— 详见 `evidence-chain.md`。）

## 5. 第 4 步：方案

**目标**：把根因翻译成可执行的配置。

**每张方案卡片必须四件套齐全**：

```yaml
- id: some_optimization
  gain:   {metric: 1.60, resource: 1.28}    # 收益（倍数或增量）
  cost:   显存 +1.28GiB；必须全层卸载        # 代价
  risk:   与多槽位并发存在资源竞争            # 风险
  rollback: 去掉参数即可，无副作用            # 回滚
  source: "[M] 实测 50.47 → 80.8~104.5"     # 可复现来源
```

**收益与代价成对出现**是方案能被生产环境安全采纳的前提。
只写收益的方案在评审时会被打回，更糟的是上线后才暴露代价。

**组合方案（bundle）**：单张卡片只解决一个问题，生产配置必须是
「多张卡片共存且互不冲突」的一整套参数。组装 bundle 时要回答：

1. 哪些方案能共存？（有些会争抢同一资源，必须二选一）
2. 每个组合的代价是什么？
3. 选哪个？（依据验收标准）

**判据**：收益可测量、回滚可执行。

## 6. 第 5 步：验证

**目标**：客观验证收益与副作用。

**三条硬要求**

1. **同条件对比**：同硬件、同驱动、同引擎版本、同测试集、
   **同测量深度**。任何一项变化都要显式记录，否则收益不可归因。
2. **逐 KPI 标注口径**：每个单元格独立标注来源
   （`measured` / `derived` / `model` / `config` / `todo`）。
   达标判定只采信 `measured`。
3. **副作用清单**：每条优化都列出它的代价与缓解措施。

**收益归因**：给出「启动参数的净变化」diff + 每项变更的来源实测。
让读者能看出「这条收益来自哪个参数、依据是哪份数据」。

**判据**：收益达标且无质量回退。

---

## 7. 第 6 步：复盘

**目标**：把这次的判断变成下次的资产。

**四块内容**

| 块 | 内容 | 为什么重要 |
|:---|:---|:---|
| 取舍 | 选择 X / 放弃 Y / 因为 Z | 记录「为什么没选另一条路」，避免重复论证 |
| 风险 | 触发条件 / 影响 / 应对 | 把已知风险显式化，而不是留在某个人脑子里 |
| 经验 | 可复用的判断规则 | 这是最值钱的部分，但要写成**可检验**的形式 |
| 下一步 | 方向 / 预期收益 / 优先级 / 前置条件 | 让闭环能真正滚起来 |

**关键**：复盘内容属于**项目级知识**，应该写在配置里而不是硬编码进
报告模板 —— 换项目时它应该随配置一起替换。

**判据**：稳定、可规模化、经验已沉淀。

## 8. 常见错误速查

| 步 | 错误 | 症状 | 修复 |
|:---:|:---|:---|:---|
| 0 | 标称值与实测值混用 | 达成率 >100% 或异常低 | 两个字段分开存 |
| 1 | KPI 不绑场景 | 同一指标前后差数倍 | 给 KPI 加 `scenario` 字段 |
| 1 | 没算理论边界就动手 | 折腾一周提升 3% | 先算 `带宽 ÷ 体积` |
| 2 | 基线是「优化后删几项」 | 收益重复计算 | 基线独立定义为朴素可用配置 |
| 3 | 结论没有反证条件 | 无法被推翻，等于没说 | 每条 finding 必填 `counter_evidence` |
| 3 | 只报一侧（如只报带宽） | 读者误判优化方向 | 两侧并列 |
| 4 | 方案只写收益 | 上线后 OOM / 变慢 | 四件套齐全 |
| 5 | 前后条件不同 | 收益不可归因 | 逐项记录差异 + 口径标记 |
| 5 | 用估算值判定达标 | 结论不可信 | 只采信 measured |
| 6 | 复盘硬编码在报告里 | 换项目后内容无关 | 写进配置 |
