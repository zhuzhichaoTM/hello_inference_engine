## 1. 为什么结论必须可证伪

「Decode 慢，因为它是访存受限的」——这句话本身没错，但它无法被证伪，
因此**不是科学结论，只是复述常识**。它无法指导决策：
如果下周有人说「我们应该加算力」，你无法用这句话反驳他。

改成可证伪的形式：

```text
结论：Decode 受显存带宽限制
预测：若给这台机器换上带宽翻倍的显存，Decode 速率应接近翻倍
反证：若 SM 利用率 >90% 且带宽利用率 <60%，则应改判 compute_bound
```

现在它变成了一个**可检验的预测**。任何人拿新数据都能验证或推翻它。
这是判断一份分析报告是否可信的最快方法：
**看它有没有写「什么情况下这个结论会被推翻」。**

## 2. finding 数据结构

```json
{
  "type": "memory_bound",
  "subtype": "kv_cache_pressure",
  "severity": "primary",
  "confidence": "high",
  "evidence": [
    "达成带宽 830.9 / 峰值 1008.0 GB/s = 82.4%",
    "距理论上界仅差 17.57%",
    "单步 19.814 ms 中权重读取占绝对主导"
  ],
  "reasoning": "Decode 每步只处理 1 个 token，算术强度 3.32 远低于 roofline 拐点 163.89。算力几乎闲置，时间全部花在把权重从内存搬到计算单元上。",
  "counter_evidence": "若 SM 利用率 >90% 且带宽利用率 <60%，则应改判 compute_bound"
}
```

字段要求：

| 字段 | 要求 |
|:---|:---|
| `type` | 瓶颈类型，取自固定枚举（见下） |
| `severity` | `primary` / `secondary` / `phase_scope` / `watch` / `error` |
| `confidence` | `high` / `medium` / `low`，标准见 §3 |
| `evidence` | **必须带具体数字**。没有数字的「证据」不是证据 |
| `reasoning` | 解释为什么这些数字构成该结论。要写清因果，不是复述 |
| `counter_evidence` | **必填**。什么证据会推翻它 |

**瓶颈类型枚举**（覆盖端侧全谱）：

```text
compute_bound        算力受限
memory_bound         访存受限（Decode 常态）
io_bound             存储/网络受限
launch_bound         调度启动开销受限（GPU 小 kernel）
power_thermal_bound  功耗/热受限（端侧独有）
scheduling_bound     调度/排队受限
capacity_bound       容量受限（装不下）
precision_risk       精度风险（不是性能瓶颈，是质量风险）
```

## 3. confidence 分级标准

不要凭感觉填。用「证据强度」定：

| 级别 | 判据 |
|:---|:---|
| `high` | 有**直接实测**支撑，且指标越过明确阈值（如带宽利用率 ≥75%） |
| `medium` | 有实测支撑但未越阈值，或依赖推导链（实测 → 物理模型 → 结论） |
| `low` | 依赖反推/估算值，或数据来自单一来源未经交叉验证 |

## 4. 反证条件的三种写法

### 写法 A：阈值反转（最常用）

```text
若算力利用率 >90% 且带宽利用率 <60%，则应改判 compute_bound
```

适用于：瓶颈类型判定。

### 写法 B：数据来源反转

```text
若实测 KV 增量远小于模型预测值，说明存在前缀复用命中
```

适用于：模型推算与实测存在差额时。

### 写法 C：条件边界

```text
若持续负载 30 分钟后吞吐保持率 >95%，说明散热充足，
该结论应降级为观察项而非主瓶颈
```

适用于：风险类结论（热、稳定性）。

## 5. 一个反面案例：算力达成率与带宽利用率恒等

这是本方法论在实践中**真实踩过**的坑，值得完整记下来，
因为它演示了「看起来合理的指标其实没有信息量」这种情况。

### 第一版做法

硬件剖面只报带宽利用率，于是补了一个「算力达成率」：

```text
算力达成率 = 实测达成算力 ÷ (算术强度 × 带宽)
```

看起来是在检验「算力有没有被浪费」。判定逻辑是：

- 达成率 ≥70% ⇒ 算力侧没问题
- 达成率 <50% ⇒ 存在算力侧损失

### 问题

展开这个式子：

```text
(FLOPs / step_s) ÷ (FLOPs / wb × 带宽)
= wb / (step_s × 带宽)
= 带宽利用率
```

**它恒等于带宽利用率。** 这不是巧合，而是访存受限的定义：
该区间内算力完全由带宽决定，两者是同一个约束的两种写法。

后果有两层：

1. 那个「判定」实际上是把带宽结论换个说法重复了一遍，
   读者会以为看到了两个独立证据
2. 更糟的是它会**误报**。在一个带宽利用率仅 18.9% 的案例上，
   它算出「达成率 19%」→ 判「算力侧另有损失」。
   但真实原因是那份数据本身是构造的示例值，与算力无关

### 修正后

报四个量，并**明确标注哪个才是线索**：

| 量 | 用途 |
|:---|:---|
| 单步 FLOPs（理论） | 分子；标注为下界（不含 kernel 实现浪费） |
| 实测达成算力 | 回答「硬件算力被用到了几成」 |
| 对**峰值**的利用率 | 低是必然的，但要让读者看到这个数 |
| **未被解释的时间** = 1 − 带宽利用率 | **这才是线索**：时间还有多少花在访存之外 |

最后一项指向「KV 读 / 启动开销 / 回退 / 采样」等具体方向，
但**不擅自下结论** —— 它只说「需进一步定位」，具体是什么要看别的剖面。

并且在报告里显式写出这个恒等关系，避免读者误以为拿到了两个证据。

### 教训

**当一个指标的公式可以化简成另一个已有指标时，它没有信息量。**
写判定规则前先把公式展开一遍 —— 这一步通常只要一分钟。

## 6. 证据链的组织方式

一份分析报告的证据链应该让人能**从结论反查到原始数据**：

```text
结论（主瓶颈是 X）
  ├─ 证据 1：实测指标 Y = a / b
  │    └─ 来源：baseline.json 的 scenarios.long_ctx.decode_tps
  │         └─ 复现命令：llama-bench -m ... -d 8192 -r 3
  ├─ 证据 2：...
  └─ 反证条件：若 Z 成立则改判
```

三个要点：

1. **每个数字都能追到一次具体测量**（而不是「经验值」）
2. **每次测量都有可复制的命令**
3. **口径标记随数字走**（`measured` / `derived` / `model` / `todo`）

实现上，这通常意味着：

- 实测数据集中放在一个「台账」里，带 `source` 与 `command` 字段
- 报告里的每个数字标注它的口径
- 台账里没记命令时，框架按场景参数**重建**一条并显式标注 `reconstructed`
  —— 重建命令 ≠ 原始命令，不标注就变成伪造复现记录
