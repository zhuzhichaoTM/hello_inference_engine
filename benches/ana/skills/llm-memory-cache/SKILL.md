# 内存与缓存治理 / 成本与能效优化

## 这个技能的核心判断

内存问题的特殊性在于：**它是硬约束，没有「降级运行」这一档**。

CPU 用满了会变慢，内存用满了会**崩溃**。所以内存治理的目标不是
「用得少」，而是「**在峰值时刻仍有余量**」。

成本问题的特殊性在于：**最省钱的配置往往不是最快的配置**。
能效最优工作点通常低于吞吐峰值点。

本技能做三件事：

1. **把内存算成预算表**（权重 + 缓存 + 运行时 ≤ 容量 − 冗余）
2. **把增长与泄漏分开**（稳态高 vs 随时间涨，处置方式完全不同）
3. **把成本归因到可优化的项**（字节数 / 冗余计算 / 回退 / 空转）

## 七步在本技能下的形态

| 步 | 本流程下做什么 | 与其他流程的差异 |
|:---:|:---|:---|
| 0 | 采集**内存相关的设备事实**：总量、配额、可用余量 | 端侧要区分物理内存与 App 配额 |
| 1 | 内存预算表 + 峰值定义 + 冗余要求 | KPI 是「峰值内存」与「安全冗余」 |
| 2 | 建立峰值基线（覆盖 Prefill 峰值，不只稳态） | **必须覆盖峰值时刻** |
| 3 | 内存分解 + 增长归因（容量 vs 泄漏） | 增长剖面是核心 |
| 4 | 方案：KV 量化 / 上下文裁剪 / 前缀复用 / 槽位调整 | 每项都要给出内存收益与质量代价 |
| 5 | 验证：峰值是否下降、是否引入新峰值 | 峰值验证要用压测而非采样 |
| 6 | 沉淀预算模型与缓存策略 | 预算模型可复用于新模型 |

## 内存预算表

```text
权重（量化后，常数）
+ KV Cache（随上下文线性增长 —— 唯一会变的部分）
+ 激活 / 临时张量（随 batch 与序列长度变）
+ 运行时缓冲（引擎自身开销）
= 峰值
```

**必须留安全冗余**，且冗余按后端定：

| 后端 | 典型冗余 | 理由 |
|:---|:---|:---|
| 服务器 GPU | ≥4 GiB | 抗并发峰值 + 长 prompt |
| CPU / 统一内存 | 1~2 GiB | 与主机其他进程共享 |
| 移动 SoC | ≥0.5 GiB（按配额比例） | 系统强杀超配额进程 |

### KV Cache 是最需要算准的一项

```text
KV 字节 = 层数 × ctx × KV heads × head_dim × 2(K,V) × 每元素字节数
```

三个容易错的地方：

1. **多槽位时 KV 要乘槽位数**（或总上下文不变、单槽减半）
2. **K 与 V 可以不同精度** —— 实践中 K 保高精度、V 压得更狠
3. **反推的架构超参要核验** —— 用模型文件元数据，
   否则算出的 KV 可能差数倍

### 用精度阶梯把「量化是否必要」变成算术

列出同一上下文下不同 KV 精度的容量与冗余：

| KV 精度 | KV 总量 | 合计 | 安全冗余 | 可行 |
|:---|---:|---:|---:|:---:|
| F16/F16 | 16.00 GiB | 32.39 GiB | -8.40 GiB | ❌ |
| Q8_0/Q8_0 | 8.50 GiB | 24.89 GiB | -0.90 GiB | ❌ |
| Q8_0/Q4_0 | 6.50 GiB | 22.89 GiB | 1.10 GiB | ✅ |
| Q4_0/Q4_0 | 4.50 GiB | 20.89 GiB | 3.10 GiB | ✅ |

**结论立刻可见**：在这个上下文下，KV 量化不是「优化项」而是
「可行性的前提」—— 不量化就装不下。

反过来，小模型短上下文下 KV 只占几百 MiB，量化收益有限，
不值得引入精度风险。**同一条经验不能跨规模照搬。**

## 增长 vs 泄漏：处置方式完全不同

| 现象 | 特征 | 根因 | 处置 |
|:---|:---|:---|:---|
| **容量不足** | 稳态就高，不随时间变 | 预算不足 | 降档 / 缩上下文 / 量化 |
| **泄漏** | 随时间单调增长 | 引用未释放 / 缓存无上限 | 修代码 |
| **碎片化** | 峰值远高于分解之和 | 分配器碎片 | 调整分配策略 |
| **峰值尖刺** | 特定操作时突增 | Prefill 的注意力矩阵 / 大 batch | 分块 / 限制 batch |

**区分方法**：跑一段持续负载，观察内存曲线。

- 平稳 → 容量问题
- 单调上升 → 泄漏
- 锯齿上升 → 碎片化

## 缓存策略

### KV Cache 前缀复用

多轮对话中，历史部分的前缀是重复的。复用它可以完全跳过重复的 Prefill：

- **收益**：TTFT 显著下降（与复用长度成正比）
- **代价**：需要客户端保持稳定 session / 缓存 key；缓存本身占内存
- **判据**：命中率。命中率低说明请求之间前缀差异大，收益有限

### 缓存与内存的权衡

缓存是**用内存换时间**。设计时要同时给出：

```text
缓存条目数 × 单条大小 ≤ 可分配的缓存预算
缓存预算 + 权重 + 激活 ≤ 峰值上限 − 冗余
```

**常见错误**：缓存无上限增长，最终把内存吃光。
缓存必须有淘汰策略（LRU / TTL / 优先级）。

## 成本与能效

### 成本的三个可优化项

| 项 | 归因方式 | 优化手段 |
|:---|:---|:---|
| 每 token 的字节搬运 | 权重体积 + KV 读写 | 量化 / 投机解码 |
| 冗余计算 | 重复 Prefill、无效重试 | 前缀缓存 |
| 空转与回退 | 等待、跨设备搬运 | 调度优化 / 消除回退 |

### 能效（端侧必测）

```text
tokens/Joule = 产出 token 数 ÷ 总能耗
```

**端侧的关键指标不是峰值吞吐，而是持续负载下的稳态吞吐与能效。**
峰值性能只能维持数十秒，之后必然降频。

| 指标 | 含义 | 为什么重要 |
|:---|:---|:---|
| 峰值吞吐 | 短时间最好情况 | 几乎无意义（用户不会只用 30 秒） |
| 稳态吞吐 | 持续负载下的速率 | 用户实际体验 |
| 降频比 | 稳态 ÷ 峰值 | 散热设计是否撑得住 |
| tokens/Joule | 能效 | 决定续航影响 |

**能效最优工作点通常不是吞吐最高点**：降频运行可能吞吐低 15%
但能效高 30%。如果业务是续航敏感型，应该主动选择低功耗工作点。

### 成本与能效的判据

给出：

- **每 token 成本**：算力 + 内存 + 能耗的摊销
- **能效曲线**：不同负载下的 tokens/Joule
- **最优工作点**：在什么负载/频率下能效最高
- **端侧续航影响**：每千 token 消耗多少电量

## 常见错误

| 错误 | 后果 | 修复 |
|:---|:---|:---|
| 只测稳态内存 | 漏掉 Prefill 峰值，上线后 OOM | 压测覆盖峰值时刻 |
| 冗余按统一值设 | 端侧按服务器标准留 4 GiB 会浪费配额 | 按后端定冗余 |
| 把泄漏当容量问题 | 加内存只是延后崩溃 | 先看内存曲线是否单调 |
| 缓存无上限 | 缓存吃光内存 | 必须设淘汰策略 |
| KV 量化收益跨规模照搬 | 小模型上得不偿失 | 按实际 KV 占比判断 |
| 用峰值吞吐评估能效 | 得出错误结论 | 必须测稳态 |
| 只报内存下降不报质量代价 | 方案无法被安全采纳 | 收益与代价成对 |
