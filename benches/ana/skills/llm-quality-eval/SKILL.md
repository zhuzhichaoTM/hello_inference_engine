# 质量评测与版本回归

## 这个技能的核心判断

质量评测最容易犯的错不是「测不准」，而是**测了却不敢下结论**：

- 「PPL 从 5.42 涨到 5.51，好像有点退化」—— 涨了多少算退化？
- 「换了新引擎，回答看起来还行」—— 「还行」不是判据
- 「质量下降了」—— 但下降来自权重量化、KV 量化、还是模板变更？

本技能做三件事：

1. **把质量守门量化成阈值**（如「PPL 相对劣化 ≤2%」）
2. **把劣化归因到具体来源**（逐项隔离，一次只变一个变量）
3. **把守门项固化成红线**（任一违反即回滚，不进入「再观察观察」）

## 七步在本技能下的形态

| 步 | 本流程下做什么 | 与其他流程的差异 |
|:---:|:---|:---|
| 0 | 固定评测环境（分词器/模板/推理参数必须钉死） | 这三项本身就是常见的劣化来源 |
| 1 | 定义质量 KPI + 阈值 + **分层样本集** | 不是一个测试集，而是按能力维度切分 |
| 2 | 建立质量基线（原始档位/原始版本） | 基线必须包含**多档位**，否则无法判断劣化是否可接受 |
| 3 | 劣化归因：逐项隔离 | 关键在「一次只变一个变量」 |
| 4 | 方案：升档 / 换 KV 精度 / 换评测口径 | 质量方案的「收益」是质量，「代价」是速度与内存 |
| 5 | 回归验证：新旧同条件对比 | 必须同样本、同参数、同引擎版本 |
| 6 | 沉淀守门项与评测集 | 下次回归直接复用 |

## KPI 与阈值设计

| KPI | 口径 | 典型阈值 | 说明 |
|:---|:---|:---|:---|
| PPL / 困惑度 | 固定测试集上的困惑度 | 相对基线劣化 ≤2% | 最通用的守门指标 |
| 任务准确率 | 分层评测集上的得分 | 各维度无显著下降 | 比 PPL 更贴近真实能力 |
| 长上下文检索 | needle-in-haystack 命中率 | 各深度均 ≥95% | **KV 量化的主要风险点** |
| 输出一致性 | 同一输入多次输出的稳定性 | 结构化输出格式合法率 | 与温度/采样相关 |
| 多后端一致性 | 同模型不同后端的输出差异 | 无系统性偏移 | 排查算子精度问题 |

**阈值必须写成可判定的形式**：

```yaml
guardrail:
  - ppl_delta_pct <= 2.0        # 困惑度相对劣化不超过 2%
  - long_ctx_retrieval >= 0.95  # 长上下文检索命中率
  - no_format_regression: true  # 结构化输出格式无回退
```

**为什么用「相对劣化」而不是绝对值**：不同模型的 PPL 基线相差很大
（1.5B 可能 12，27B 可能 5），绝对值阈值无法跨模型复用。

## 分层样本集：比一个大测试集更有用

一个混合测试集只能告诉你「总体掉了 3%」，无法告诉你是哪方面掉了。
按能力维度切分后，劣化会自己暴露位置：

| 维度 | 样本特点 | 能暴露什么问题 |
|:---|:---|:---|
| 事实知识 | 短问答 | 权重量化的全局影响 |
| 多步推理 | 数学/逻辑 | 中间步骤的精度累积损失 |
| 代码 | 生成 + 补全 | 结构化输出的格式遵循 |
| 长文本 | 多段摘要/检索 | **KV 量化**的影响（关键） |
| 多语言 | 中英混合 | 分词器与嵌入层量化 |
| 格式遵循 | JSON/Schema 约束 | 采样与 logit 处理 |

**长文本维度是 KV 量化的唯一有效检验**：KV 量化对短上下文几乎无影响，
问题只在长上下文检索时暴露（「答非所问」「忽略中段信息」）。

## 劣化归因：一次只变一个变量

质量下降几乎从不是单一原因。归因的方法是**逐项隔离**：

```text
基线（原始档位，原始引擎，原始模板）
  ├─ 只换权重量化档位  → Δ1
  ├─ 只换 KV 精度      → Δ2
  ├─ 只换引擎版本      → Δ3
  ├─ 只换对话模板      → Δ4
  └─ 组合全部          → Δ_total（≈ Δ1+Δ2+Δ3+Δ4，超出部分说明有交互效应）
```

**注意量化的两个方向可能相反**。实践中出现过：

| 阶段 | F16 KV | q8_0 KV | 变化 |
|:---|---:|---:|---:|
| Decode | 7.22 t/s | 7.89 t/s | **+9.3%** |
| Prefill | 34.65 t/s | 11.48 t/s | **-67%** |

量化救 Decode（访存密集）但伤 Prefill（算力密集）。
**只报 Decode 提升会掩盖 Prefill 的严重退化。**

## 版本回归的做法

版本回归 = 把第 2 步和第 5 步做两遍，条件完全相同。

**必须显式记录「什么变了」**：

```text
变更清单
├─ 模型：Q4_K_M → Q5_K_M           ← 一次只变一项
├─ 引擎：commit abc → def
├─ 驱动：580.76 → 581.10
└─ 配置：--parallel 2 → 4
```

**一次只变一项。** 同时升级引擎和换量化档位，出问题后无法归因 ——
你会花两天才排除掉一个本可以五分钟确认的因素。

**回归的三种结论**：

| 结论 | 条件 | 动作 |
|:---|:---|:---|
| 放行 | 所有 KPI 达标 + guardrail 全通过 | 灰度 → 全量 |
| 有条件放行 | 部分 should_pass 未达标但不违反红线 | 记录已知退化，限定场景 |
| 回滚 | 任一 guardrail 违反 | 立即回滚，根因分析后重来 |

## 常见错误

| 错误 | 后果 | 修复 |
|:---|:---|:---|
| 阈值是「感觉差不多」 | 无法判定，每次都要重新讨论 | 量化成相对劣化百分比 |
| 只测一个混合测试集 | 不知道哪方面掉了 | 分层样本集 |
| 短上下文测完就下结论 | 漏掉 KV 量化的长上下文问题 | 必须加长上下文检索 |
| 一次改多项 | 无法归因 | 逐项隔离 |
| 只报 Decode 提升 | 掩盖 Prefill 退化 | 两阶段都报 |
| 用估算值判定质量 | 结论不可信 | 质量指标必须实测 |
| 回归环境不固定 | 差异来自环境而非版本 | 钉死分词器/模板/推理参数 |

## 与其他技能的关系

- 方法论底座：`seven-step-closure`
- 性能优化（质量守门是其约束条件）：`llm-perf-optimization`
- 硬件适配（换后端后要重新验质量）：`llm-backend-adaptation`
- 内存治理（KV 量化同时影响质量与内存）：`llm-memory-cache`

## 判据总结

给出：

- **质量基线**：各档位 / 各版本的 PPL 与分层得分
- **劣化归因**：Δ 分解到具体来源（权重 / KV / 引擎 / 模板）
- **守门结论**：PASS（放行）/ REVIEW（有条件放行）/ ROLLBACK
- **已知退化**：哪些场景下会退化、退多少、如何缓解
