# 大模型推理性能分析与优化

## 这个技能的核心判断

性能优化最贵的一课是：**大部分优化动作是无效劳动**。

Decode 阶段每步只处理 1 个 token，算术强度约 3~4 FLOPs/Byte，
而一张现代 GPU 的 roofline 拐点在 160 以上 —— 相差 40 倍。
这意味着算力几乎完全闲置，**任何提升算力的优化都不会加快 Decode**。

所以第一步不是动手，而是**算出物理上界**：

```text
Decode 理论上界 (t/s) = 内存带宽 (GB/s) ÷ 每步需搬运的字节数 (GB)
```

拿到这个数，你立刻知道还剩多少空间：

| 达成率 | 含义 | 该做什么 |
|:---|:---|:---|
| > 80% | 已触及物理天花板 | 只能**减少搬运的字节**（量化/投机/减回退） |
| 60~80% | 接近天花板 | 先查有没有回退、有没有调度浪费 |
| < 60% | 还有明显空间 | 值得做 kernel 与配置层面的优化 |

这一步三分钟，省下的可能是一周。

## 七步在本技能下的形态

本技能是 `seven-step-closure` 在「性能分析与优化」流程下的具体实现。
配套框架 `perfkit` 把七步固化成可执行命令：

| 步 | 命令 | 产出 |
|:---:|:---|:---|
| 0 环境准备 | `scripts/collect_env.sh` + `perfkit probe` | 环境画像 + 本机实测带宽 |
| 1 问题定义 | `perfkit define` | 画像 / 内存预算 / roofline / KPI |
| 2 性能基线 | `perfkit baseline` | 基线数据 + 测量协议 |
| 3 剖面与定位 | `perfkit profiling` + `perfkit diagnose` | 四维剖面 + Hot Kernel 列表 + 执行路径 + 根因报告 |
| 4 方案 | `perfkit optimize` | 方案卡片 + bundle 对比 + 启动脚本 |
| 5 验证 | `perfkit verify` | 前后对比 + 收益归因 + 副作用 |
| 6 复盘 | `perfkit report` + `perfkit visualize` | 报告 + 图表 |

一键：`python3 -m perfkit all --config <配置目录> --run <run_id>`

命令细节见 `references/cli-reference.md`。

## 开工前的三个判断

### 判断一：装得下吗

先算内存预算，再谈优化：

```text
权重 + KV Cache + 运行时缓冲 ≤ 可用内存？安全冗余够吗？
```

**KV Cache 是唯一随上下文线性增长的部分**，而权重是常数。
上下文越长，KV 占比越高。长上下文场景下 KV 量化往往不是「优化项」
而是「可行性的前提」—— 不量化就装不下。

### 判断二：瓶颈在带宽还是算力

用 roofline 判定：

```text
算术强度 = 每 token FLOPs ÷ 每 token 搬运字节数
拐点     = 峰值算力 ÷ 峰值带宽
强度 < 拐点 ⇒ 访存受限（Decode 常态）
```

**一个必须避免的坑**：不要只报带宽利用率。读者会问「算力才用了 1.7%，
用起来是不是就能提速」。必须同时给出算力侧，并说清「算力低是带宽限死的
必然结果」—— 该强度下的可达算力上界 = `强度 × 带宽`，
峰值算力根本用不上。

### 判断三：测量条件受控吗（「测量有效性条件」是什么意思）

前后对比必须**同条件**：同硬件、同驱动、同引擎、同测试集、**同测量深度**。

- 同一个配置在不同上下文深度下 Decode 可差 4 倍（17.5 → 4.2 t/s）。
  用 depth=0 的值去比 depth=8192 的值，比较的是上下文长度，不是优化方案
- 共享内存的后端（CPU / 统一内存）性能**强依赖机器空闲度**：
  同一配置空闲时 17.85 t/s、负载 90+ 时 9.19 t/s（-49%）。
  这类数据必须连同采集时的系统负载一起报告

报告 §0.1 的「测量有效性条件」就是在回答**「这些数字能不能直接引用」**：
它给出准入条件（如「1 分钟负载 < 物理核数」）、违反的后果、
以及本次采集的实测负载。读到这一节时要做的是——
若负载超标，优先引用低负载窗口的数据；必须用时标注条件；
有条件时在空闲窗口复测。

## 优化手段的四条路径

按「改动成本 ÷ 收益确定性」排序，这也是路线推荐的顺序：

| 路径 | 做法 | 收益来源 | 代价 |
|:---|:---|:---|:---|
| **kernel** | 让同样的搬运更高效 | 提升带宽达成率 | 改动大、收益确定性中 |
| **speculative** | 减少搬运**次数** | 一次验证产出多个 token | 需草稿模型、接受率波动 |
| **quantization** | 减少每次搬运的**字节数** | 权重位宽下降 | 精度损失 |
| **kv_cache** | 减少 KV 的容量与读写 | 长上下文同时受益 | 长上下文检索精度 |
| **ondevice** | 热/功耗策略（端侧） | 稳态吞吐与能效 | 需真机验证 |
| **precision_guard** | 不是优化动作，是验收红线 | — | — |

**关键洞察**：当带宽已达上界 80% 以上时，前三条路径中
kernel 的空间只剩 20%；而 speculative 不减少单次读取量而是减少**读取次数**，
收益量级更大（实测 +64.5%）。**这就是主攻方向的选择依据。**

## 方案卡片必须四件套齐全

```yaml
- id: spec_mtp
  gain:     {decode_tps: 1.60, vram_gib: 1.28}    # 收益
  cost:     显存 +1.28GiB；Draft 必须全层卸载       # 代价
  risk:     与多槽位并发存在资源竞争                 # 风险
  rollback: 去掉 -md / --spec-type 参数即可          # 回滚
  source:   "[M] 实测 50.47 → 80.8~104.5 t/s"      # 可复现来源
```

只写收益的方案在评审时会被打回，更糟的是上线后才暴露代价。

## 第 3 步的四件产出物（缺一不可）

业务地图对「瓶颈定位」规定了四件产出。它们不是四种写法，而是四个**不同层次**：

| 产出物 | 回答什么 | 最低要求 |
|:---|:---|:---|
| ① 性能 Profile 报告 | 时间/带宽花在哪 | 四维剖面：硬件（带宽/算力）、阶段（Prefill/Decode）、算子、KV |
| ② Hot Kernel 列表 | 先动谁 | 按单步字节/耗时**降序**；给出覆盖率、累计占比、优化收益上限 |
| ③ 执行路径分析 | 数据从哪搬到哪 | 每步搬运量分解、Cache 层次、回退路径、Host-Device 同步 |
| ④ 根因分析报告 | 为什么慢、能否被推翻 | 根因树（排除法）+ 证据链（标口径）+ 反证条件 + 路线推导 |

三条硬要求：

1. **Hot 列表必须写清粒度**。replay 模式只能给到「算子类」，
   不能伪装成 kernel 级；要 kernel 名就用 nsys 采集 live 数据。
2. **覆盖率必须交代**。各算子占比之和应等于 100%（含嵌入层）；
   差多少、差在哪里，要写出来，不能留一个「其他」了事。
3. **根因报告必须有反证条件**，且反证条件必须能在下一步被检验。
   无法检验的，列为待采集，不能当作「已排除」。

## 多硬件后端的差异

性能分析的结论**强依赖后端**。同一个「Decode 慢」在不同后端上
根因完全不同：

| 维度 | 独立显存 GPU | CPU / 统一内存 |
|:---|:---|:---|
| 带宽归属 | 独立显存，不受主机影响 | **与主机所有进程共享** |
| 回退代价 | 昂贵（跨总线往返） | **不存在回退**（权重本就在系统内存） |
| 调优第一参数 | 卸载层数、并发槽位 | **线程数**（最优值通常是物理核数） |
| 长上下文衰减 | 缓降 | **剧烈**（KV 与权重抢同一份带宽） |

**不要套用模板**。把 GPU 那套分析直接搬到 CPU 上，会得出方向相反的结论
（例如把「零回退」列为硬约束 —— 而 CPU 后端根本没有回退这个概念）。

细节见 `references/hardware-backends.md`。

## 判定规则与反证条件

瓶颈判定走决策树，每条结论都带反证条件。规则清单见
`references/bottleneck-rules.md`。

核心规则速览：

| 类型 | 触发条件 | 反证条件 |
|:---|:---|:---|
| `memory_bound` | 带宽利用率 ≥60% | 算力利用率 >90% 且带宽 <60% ⇒ 改判 compute_bound |
| `capacity_bound` | 安全冗余 < 要求值 | 实测峰值远低于预测 ⇒ 预测过于保守 |
| `power_thermal_bound` | 设备标记会降频 | 持续负载后保持率 >95% ⇒ 降级为观察项 |
| `launch_bound` | 启动开销占比 ≥5% | kernel 间隙 <2µs ⇒ 不是瓶颈 |
| `precision_risk` | 用了低比特量化 | PPL 劣化 <1% 且长上下文无回退 ⇒ 风险可接受 |

**没有反证条件的结论不是结论** —— 它无法被推翻，因此不构成知识。
