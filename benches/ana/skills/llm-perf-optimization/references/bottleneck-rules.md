## 1. 规则的设计原则

每条规则是一个**纯函数** `(剖面数据, 定义数据) → finding | None`。纯函数意味着
规则本身无状态、可单测、可任意顺序执行。

三条约束：

1. **evidence 必须带具体数字**。没有数字的「证据」不是证据
2. **counter_evidence 必填**。没有反证条件的结论无法被证伪，不构成知识
3. **规则要能说「不适用」**。例如 kernel 启动开销规则在 CPU 上必须直接
   返回 `None`，而不是算出一个虚假的「次要瓶颈」——
   后者会把优化方向引向「减少算子数量」这种在 CPU 上收益极低的方向

第 3 条容易被忽略但很重要：**误报比漏报更危险**，因为漏报只是少一条线索，
误报会主动把你带错方向。

## 2. 规则全表

### `memory_bound` 访存受限

**触发**：带宽利用率 ≥ 60%

**证据模板**

```text
达成带宽 830.9 / 峰值 1008.0 GB/s = 82.4%
距理论上界仅差 17.57%
单步 19.814 ms 中权重读取占绝对主导
```

**归因**：Decode 每步只处理 1 个 token，算术强度远低于 roofline 拐点。
算力几乎闲置，时间全部花在把权重从内存搬到计算单元上。

**反证**：若算力利用率 >90% 且带宽利用率 <60%，则应改判 compute_bound。

**严重度**：利用率 ≥75% ⇒ primary；60~75% ⇒ secondary。

---

### `capacity_bound` / `kv_cache_pressure` KV 压力

**触发**：KV 占单步耗时的比例 ≥ 5%

**证据模板**

```text
ctx=65536 时 KV=6.5 GiB，每步需读写 13.0 GiB
占单步耗时 45.88%
KV 随 ctx 线性增长：容量与上下文长度成正比，而权重是常数
```

**归因**：KV Cache 是内存中唯一随上下文线性增长的部分。

**反证**：若实测 KV 增量远小于模型预测值，说明存在前缀复用命中。

**严重度**：占比 ≥15% ⇒ primary。

---

### `capacity_bound` / `vram_margin_thin` 内存冗余不足

**触发**：安全冗余 < 设备要求的最小值

**证据模板**

```text
峰值合计 22.03 GiB / 可用内存 23.99 GiB
安全冗余仅 1.96 GiB（设备要求 ≥4.0 GiB）
其中 KV 6.50 GiB，权重 15.33 GiB
```

**归因**：内存是硬约束而非软约束 —— 一旦越过就崩溃，没有「降级运行」这一档。

**反证**：若实测峰值远低于预测，说明预测过于保守。

**注意**：要求值取自设备配置，**不同后端差异很大**。服务器 GPU 可能要求
4 GiB 冗余，端侧按 App 内存配额可能只要求 0.5 GiB。

---

### `power_thermal_bound` / `thermal_throttling` 热降频（端侧独有）

**触发**：设备画像标记 `thermal_throttle: true`

**证据模板**

```text
设备标记 thermal_throttle=true（TDP 8W，电池供电）
端侧持续负载必然降频：峰值性能只能维持数十秒
机身温度上限（体感阈值）通常远低于 SoC 允许的结温
```

**归因**：端侧与服务器的核心差异 —— 性能天花板不由芯片决定，
而由散热与电池决定。因此「峰值吞吐」几乎无意义。

**反证**：若持续负载后吞吐保持率 >95%，说明散热充足，降级为观察项。

---

### `launch_bound` Kernel 启动开销

**触发**：启动开销占单步耗时 ≥ 5%，**且设备类型为 GPU/NPU**

**证据模板**

```text
64 层 × ~10 kernel ≈ 640 次 launch
按 4µs/次估算 launch 开销 ≈ 2.56 ms
占单步 12.9%
```

**归因**：GPU 对大量小 kernel 的启动开销敏感。当单步耗时降到几十毫秒量级时，
launch 开销从「可忽略」变成「可观」。

**反证**：若 profiler 显示 kernel 间隙 <2µs，则 launch 不是瓶颈。

**⚠️ 后端门槛**：CPU 上不存在 kernel launch（算子就是函数调用，纳秒级）。
这条规则在 CPU 后端必须直接返回 `None`。

---

### `compute_bound` / `prefill_phase` 阶段限定

**触发**：始终产出（作为阶段标注）

**归因**：Prefill 是唯一算力密集的阶段。优化它的手段（在线注意力、
更大 batch、张量核心）与 Decode 完全不同，必须分阶段对待。

**反证**：若 Prefill 也受带宽限制（极短 prompt），则并入 memory_bound。

---

### `precision_risk` 精度风险

**触发**：使用了低比特量化

**证据模板**

```text
主模型 Q4_K_M（4.81 bit/权重）
KV Cache K=8.5bit / V=4.5bit
```

**归因**：W4 + KV-V4 属于激进组合。权重侧影响全局质量，
KV 侧主要影响长上下文检索与中段信息保留。

**反证**：若 PPL 相对劣化 <1% 且长上下文任务无回退，则风险可接受。

**注意**：这是「优化副作用」的预警，**不是性能瓶颈**。它不产出优化方案，
只产出守门项（验收红线）。

## 3. 常见误判与修正

### 误判一：把「算力利用率低」当成缺陷

**现象**：报告写「算力利用率仅 1.7%」，读者推断「用起来就能提速」。

**修正**：必须给出「该算术强度下的可达算力上界」= `强度 × 带宽`。
在这个上界下，算力利用率低是**必然结果**，不是缺陷。

**但要小心**：不要用「达成算力 ÷ 可达上界」作为算力侧的独立证据 ——
这个比值在数学上**恒等于带宽利用率**。详见
`seven-step-closure/references/evidence-chain.md` §5。

正确做法是报「**未被解释的时间**」= 1 − 带宽利用率，
它指向「KV 读 / 启动开销 / 回退 / 采样」，但只标「需进一步定位」，
不擅自归因到算力。

### 误判二：把 CPU 当 GPU 分析

**现象**：在 CPU 后端报告里写「SM 利用率」「PCIe 往返代价」
「零回退是硬约束」。

**修正**：这些概念在 CPU 上要么不存在，要么方向相反：

- CPU 没有 SM
- CPU 不存在回退（权重本就在系统内存），「零回退」不是约束
- CPU 的第一调优参数是**线程数**，且最优值通常是物理核数
  （超线程共享访存端口，8 逻辑线程可能比 4 物理核慢 27%）

### 误判三：用不同深度的数据做前后对比

**现象**：基线取 depth=0 的 17.5 t/s，优化后取 depth=8192 的 7.2 t/s，
得出「优化后慢了 59%」。

**修正**：前后对比必须**同深度**。同深度对照才能把「优化方案」
从「上下文长度」这个变量里隔离出来。

实现上：给 bundle 的 `measured` 加 `n_depth` 字段，
报告对比表加「测量深度」列并提示。

### 误判四：用纯解码口径与端到端口径直接比较

**现象**：benchmark 工具报 13.15 t/s，端到端工具报 8.4 t/s，说「不一致」。

**修正**：两者口径不同。前者是纯解码吞吐（不含采样、不含首 token 排队），
后者是端到端墙钟（含传输、排队、采样）。相差 35% 属正常。
**引用时必须标明来源。**

### 误判五：把估算值当实测用于达标判定

**现象**：用几何公式算出的显存值判定「显存超标」，触发回滚。

**修正**：达标判定**只采信实测值**。模型值仅用于可行性边界判断。
每个 KPI 单元格都要独立标注口径（`measured` / `derived` / `model` /
`config` / `todo`）。

## 4. 规则缺口怎么补

当某类瓶颈反复出现但决策树没有对应规则时，说明有缺口。补规则的流程：

```text
流程中暴露的问题
    ↓
是数据缺口？ → 补台账 / 跑 live 采集
    ↓ 否
是方案缺口？ → 加方案卡片（plan_*.yaml）
    ↓ 否
是规则缺口？ → 加 diagnose 规则
    ↓ 否
是能力缺口？ → 回到知识层补（硬件架构 / 算子 / 量化原理）
```

判断「是规则缺口」的标志：剖面上有明显的异常数字，
但 `findings` 里没有任何一条提到它。

**补规则时同时要补两处**：

1. `RULES` 里加判定函数（产出 finding）
2. `ROUTE_RULES` 里加映射（结论 → 优化方向 → 理由）

只加前者的话，结论会出现在报告里但优化路线不会包含对应类别。
