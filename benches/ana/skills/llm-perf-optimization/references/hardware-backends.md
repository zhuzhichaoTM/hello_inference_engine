## 1. 为什么后端差异不能忽略

性能分析的结论**强依赖后端**。同一句「Decode 慢」在不同后端上：

- 根因不同（GPU 可能是启动开销，CPU 几乎必然是对存带宽）
- 有效手段不同（GPU 调卸载层数，CPU 调线程数）
- 甚至**概念的适用性不同**（CPU 上不存在「回退」）

把 GPU 那套分析模板直接套到 CPU 上，不是「不够精确」，
而是**会得出方向相反的结论**。

因此框架把硬件差异收敛成一层**后端抽象**：每个后端回答四个问题 ——
加速标志怎么传、内存怎么读、用哪个带宽探针、回退代价模型是什么。
其余部分（七步流程、判定规则、报告结构）完全复用。

## 2. 五类后端的差异对照

| 维度 | `gpu` 独立显存 | `cpu` | `hybrid` 统一内存 | `soc` 移动 SoC | `npu` |
|:---|:---|:---|:---|:---|:---|
| 加速标志 | `-ngl 99` | **`-ngl 0`** | `-ngl 99` | `-ngl 0` | 无标准接口 |
| 内存称呼 | 显存 | 内存 | 统一内存 | App 内存配额 | 加速器内存 |
| 内存怎么读 | nvidia-smi | getrusage + vm_stat | getrusage | 厂商 profiler | **无标准接口** |
| 带宽探针 | 纯读带宽探针 | mmap 真实文件 + GEMV | 顺序读 | 同 CPU | 无 |
| 回退代价 | **昂贵**（跨总线） | **不存在回退** | 廉价（同物理内存） | 廉价 | — |
| 调优第一参数 | 卸载层数、并发槽位 | **线程数** | 卸载层数 | 线程数 / NPU 分区 | 算子覆盖 |

### 为什么 CPU 必须显式写 `-ngl 0`

这不是「默认值」，而是**必须钉死**。开发机（MacBook Pro）装了 Metal
（Intel Iris），不写 `-ngl 0` 时推理引擎会**静默走 GPU** ——
与「验证 CPU 可用性」的目标直接相悖，而且不会报错。

这是「配置默认值」与「显式声明意图」的区别。默认值可能被环境改变，
显式声明不会。

### 为什么「回退代价」会改变结论

CPU / 统一内存后端的回退代价是**廉价或不存在**的（权重本就在同一块物理内存）。
这直接影响两条结论：

1. 报告里「跨设备回退代价」一节的表述：从「跨总线往返，单层吃掉 77% 预算」
   改为「同步开销，单层仅占 0.9%」
2. 「零回退」是否被列为硬约束：GPU 上是，CPU 上**不是**（因为不存在回退）

同一份代码，两种正确的表述。

## 3. 三个「结论会反转」的具体案例

### 案例一：算力利用率低 —— 缺陷还是必然？

| 后端 | 实测 | 峰值 | 对峰值利用率 | 结论 |
|:---|---:|---:|---:|:---|
| GPU | 2.759 TFLOPS | 165.2 | 1.7% | **正常**：可达上界仅 3.3 TFLOPS |
| CPU | 0.063 TFLOPS | 0.28 | 22.7% | **正常**：可达上界仅 0.08 TFLOPS |

两者都在访存受限区，算力低都是必然的。但如果只报「对峰值利用率」，
读者会以为存在巨大的优化空间。

**正确做法**：给出「该强度下的可达算力上界」作为参照，
并说明「提升算力无法加快 Decode」。

### 案例二：线程数 —— 越多越快？

| 线程 | 1 | 2 | 4 | 8（逻辑核） |
|:---|---:|---:|---:|---:|
| Decode (t/s) | 9.49 | 15.18 | **17.85** | 13.03 |
| Prefill (t/s) | 32.03 | 55.28 | **78.42** | 75.53 |

**8 逻辑线程反而比 4 物理核慢 27%。** 超线程共享执行单元与访存端口，
在访存密集的矩阵-向量乘上形成竞争。

**教训**：CPU 后端的第一个调优动作应该是**扫线程数**，
而不是调参数量化。而且最优值通常是物理核数，不是逻辑核数。

### 案例三：长上下文衰减 —— 缓降还是断崖？

| 上下文深度 | GPU (27B) | CPU (1.5B) |
|:---|---:|---:|
| depth 0 | — | 17.74 t/s |
| depth 2K | — | 13.03 t/s |
| depth 8K | 46.8 t/s | 7.22 t/s |
| depth 16K | 44.5 t/s | 4.19 t/s |
| depth 32K | 43.5 t/s | — |
| depth 64K | 43.5 t/s | — |

GPU 上 Decode 速率随上下文**缓降**（46.8 → 43.5，-7%）；
CPU 上则是**断崖**（17.74 → 4.19，-76%）。

**原因**：GPU 有独立显存带宽，KV 读写只与权重读取竞争同一块显存；
CPU 的内存带宽与主机所有进程共享，KV 增长直接挤压权重读取的可用带宽。

**后果**：同一条「限制上下文长度」的建议，在 CPU 上是硬需求，
在 GPU 上只是可选优化。

## 4. 新增一类后端的做法

```python
# perfkit/backends.py
class MyAccelBackend(Backend):
    kind = "myaccel"
    label = "自研加速器"
    memory_label = "加速器内存"
    utilization_label = "NPU 利用率"

    def accel_flags(self) -> list[str]:
        return ["-ngl", "0", "--device", "myaccel"]

    def mem_snapshot(self):
        # 没有标准接口时返回 None —— 报告会显示「—」而不是编造数字
        return None

    def bandwidth_probe_command(self, probe_bin, size_gib=2.0):
        return [probe_bin, "--mode", "stream"]

    def fallback_is_cheap(self) -> bool:
        return True    # 决定报告表述与「零回退」是否为硬约束

    def notes(self) -> list[str]:
        return ["该后端特有的注意事项，会写进报告的设备画像"]

BACKENDS["myaccel"] = MyAccelBackend
```

然后把 `device_*.yaml` 的 `kind` 设成 `myaccel`。**流程代码零改动。**

### 探针结果同样受负载影响

带宽探针测的是硬件，但在**共享内存带宽的后端**上（CPU / 统一内存），
探针与真实推理一样会被外部负载压低。实践中出现过：

```text
负载下采集：探针报 13.7 GB/s，内核效率 6.7%
真实推理反推：19.9 GB/s
```

探针值**低于**真实推理反推值，说明探针是在负载下采的 ——
而内核效率那一项也会因此失真（分子被压低）。

因此框架把探针采集时的系统负载一并落盘（`output/_env/probe.json`
的 `environment` 段），报告 §0 的探针表会显示该负载并给出提示。
**引用探针数字前先看负载**。

### 基类钩子的保守默认值

| 钩子 | 默认 | 含义 |
|:---|:---|:---|
| `accel_flags()` | `[]` | 不传加速标志 |
| `mem_snapshot()` | `None` | 无标准采集手段 |
| `bandwidth_probe_command()` | `None` | 无可用探针 |
| `default_threads()` | `None` | 不指定线程数 |
| `fallback_is_cheap()` | `False` | 保守假设回退昂贵 |

**宁可返回 `None` 让上层标注「待采集」，也不要返回一个看起来合理的
编造值** —— 后者会污染整条证据链，而且不会被任何人发现。

### 验证

```bash
python3 -m perfkit query --backends --config configs/my-hw
```

输出会显示当前配置解析到哪个后端、加速标志、内存称呼、回退代价、
探针命令，以及该后端特有的注意事项。
