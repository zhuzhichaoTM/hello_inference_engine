# 故障定位与恢复 / 安全与可靠性治理

## 这个技能的核心判断

故障处置最常见的两个错误：

**错误一：跳过恢复直接找根因。** 服务还在挂，团队却在争论
「到底是内存泄漏还是配置问题」。**恢复优先于归因** ——
先让服务可用（回滚 / 重启 / 降级），再从容定位。

**错误二：修好了但不沉淀。** 同类故障三个月后再来一次，
因为这次的判断只留在几个人的记忆里。**故障的产出不是「修好了」，
而是「一个能自动拦截同类问题的检查项」。**

## 七步在本技能下的形态（快节奏版）

故障场景时间压力大，七步要压缩但不省略：

| 步 | 本流程下做什么 | 时间预算 |
|:---:|:---|:---|
| 0 | **恢复优先**：回滚到上一个可用配置 / 重启 / 降级 | 分钟级 |
| 1 | 定义「恢复正常」的判据（不是「看起来好了」） | 分钟级 |
| 2 | 采集故障现场：日志时间线 + 资源曲线 + 请求样本 | 分钟级 |
| 3 | 根因定位：现象 → 分类 → 验证 | 小时级 |
| 4 | 修复方案 + 回滚方案 | 小时级 |
| 5 | 验证修复有效且无新问题 | 小时级 |
| 6 | **沉淀检查项**：让同类问题下次自动被拦截 | 天级 |

**关键**：第 0 步与第 3 步不能混。先恢复，再定位。
在服务不可用时做根因分析，判断质量会显著下降。

## 现象 → 根因分类表

从现象反推是最高效的路径。按现象查表，而不是从所有可能性里筛：

| 现象 | 优先怀疑 | 验证方法 |
|:---|:---|:---|
| 进程崩溃 / 被系统杀 | **OOM**（容量不足）、内存配额 | 看内存曲线是否触顶；查系统日志有无强杀记录 |
| 请求返回 400 | 上下文超限（prompt 超 `ctx-size`） | 看报错里的 token 数与配置的上下文 |
| 请求超时 | 排队积压 / 单步耗时上升 | 看并发数与队列长度；看单步耗时趋势 |
| 响应变慢但无错误 | 资源竞争（外部负载）/ 热降频 / 缓存失效 | 看系统负载；看温度与频率 |
| 输出乱码 / 重复 | 采样参数 / 模板错误 / 上下文污染 | 对比同输入的多次输出；检查模板 |
| **答非所问 / 忽略中段** | **KV 量化精度** / 上下文被截断 | 跑长上下文检索测试；查 KV 精度档位 |
| 输出格式不合法 | 采样温度过高 / 结构化约束缺失 | 降低温度试；加格式约束 |
| 首字延迟突增 | Prefill 变慢（上下文变长 / 缓存失效） | 看 prompt 长度分布；看前缀缓存命中率 |
| 吞吐突然减半 | 回退到低效路径（CPU / 无加速） | **查是否有层回退**；查加速标志是否生效 |
| 显存占用持续上涨 | 内存泄漏 / 缓存无上限 | 看内存曲线是否单调 |

**「答非所问」这一条要特别注意**：它看起来像模型能力问题，
实际上最常见的原因是 KV 量化（V 侧压得太狠）或上下文被静默截断。
不要一上来就怀疑模型。

## 三个必须检查的「静默失效」

有些故障不报错，只是变慢或变差 —— 这类最难发现。三个必查项：

### 1. 层回退（fallback）

配置写了全层卸载，但实际有层跑在 CPU 上。

**为什么静默**：引擎会正常工作，只是慢。不报错。

**代价**：跨总线往返单层即可吃掉显著预算。实践中出现过
「单层往返占单步解码预算 77%」。

**检查**：引擎启动日志里的卸载层数；或用性能剖面反推
（若实测远低于理论上界，先怀疑回退）。

### 2. 加速标志未生效

编译时架构标志写错，静默退化到 JIT 编译。

**为什么静默**：能跑，只是慢一截。

**检查**：编译日志；启动日志里的后端信息。

### 3. 测量条件污染（共享内存后端）

同一配置在空闲机器与繁忙机器上差 2 倍。

**为什么静默**：数字看起来合理，但不可解释。

**检查**：采集时记录系统负载；报告中标注负载条件。

## 安全与隐私风险清单

按攻击面组织，每项给出风险等级与整改建议：

| 面 | 风险项 | 典型缓解 |
|:---|:---|:---|
| **输入侧** | Prompt 注入 / 越狱 | 输入过滤、系统提示隔离、输出校验 |
| | 超长输入 | 长度上限 + 截断策略 |
| | Unicode 混淆 / 恶意 JSON | 规范化 + 严格解析 |
| | 工具参数注入 | 参数白名单 + 类型校验 |
| **输出侧** | PII 泄露 | 脱敏 / 敏感词过滤 |
| | 结构化输出不合法 | Schema 校验 + 重试 |
| | 越权工具调用 | 权限边界 + 人工确认 |
| **模型资产** | 权重被提取 / 篡改 | 加密 + 完整性校验 + 安全执行环境 |
| **设备侧** | 沙箱逃逸 / 权限提升 | 系统沙箱 + 最小权限 |
| | 密钥泄露 | 密钥管理服务 + 轮换 |

**端侧特有**：数据不出端是端侧的核心价值主张，
所以「本地处理」既是隐私优势也是约束 —— 不能在排查问题时
随手把用户数据传到外部服务。

## 复盘：故障的真正产出

故障复盘的四块内容与通用复盘相同，但**第 4 块特别重要**：

| 块 | 内容 |
|:---|:---|
| 时间线 | 何时发生、何时发现、何时恢复、每步做了什么 |
| 根因 | 直接原因 + 根本原因（通常不止一层） |
| 处置 | 有效的动作、无效的动作（后者同样有价值） |
| **检查项** | **能自动拦截同类问题的具体检查** |

**检查项要具体到可执行**：

```text
✗ 「加强内存监控」          —— 无法执行
✓ 「请求前校验：prompt_tokens + max_tokens ≤ 服务端 ctx-size
   ，超限直接返回 400 并提示实际可用值」  —— 可执行
```

**为什么这一块最值钱**：它把「人记住了」变成「系统拦住了」。
人的记忆会流失，检查项不会。

## 常见错误

| 错误 | 后果 | 修复 |
|:---|:---|:---|
| 先定位后恢复 | 服务长时间不可用，判断质量也下降 | 恢复优先 |
| 只看日志不看资源曲线 | 漏掉容量类根因 | 三者对齐（日志/曲线/调用链） |
| 怀疑模型能力而不查配置 | 白折腾模型 | 先查 KV 精度与上下文截断 |
| 修好就走 | 同类故障复发 | 沉淀检查项 |
| 检查项写成「加强监控」 | 无法执行，等于没写 | 具体到可执行的判断 |
| 复盘只记「谁的责任」 | 团队开始隐藏问题 | 记流程与系统的缺口，不记人 |

## 判据总结

给出：

- **恢复动作**：立即执行什么（回滚/重启/降级）
- **根因**：直接原因 + 根本原因，附验证方式
- **修复方案**：改什么、怎么验证有效、怎么回滚
- **检查项**：能自动拦截同类问题的具体检查（可执行的形式）
- **风险清单**（安全类）：风险项 / 等级 / 整改建议 / 复核方式
